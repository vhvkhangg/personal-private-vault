## Source findings and resolved design questions

1. **The browsing gap is real.** [SavedResourceController](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/web/controller/SavedResourceController.java), lines 68–79, returns a recent list or a singleton hash result, not a page. [SavedResourceRepository](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/infrastructure/persistence/SavedResourceRepository.java), lines 20–21, has only the unfiltered recent ordering. [GlobalSearchQuery](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/search/query/GlobalSearchQuery.java) requires nonblank text and caps offset; search orders by relevance. Vault's controller has ID/metadata/lifecycle operations, not a saved-resource browser. None replaces the proposed time-ordered, kind-filtered Inbox. The literal `/inbox` route must coexist with `/{id}` and be covered by HTTP routing/OpenAPI checks.
2. **An existing public qualification API is sufficient.** Reuse [VaultSearchOperations.filterQualifyingActiveEntries](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/vault/search/VaultSearchOperations.java) with an empty required-tag set. [VaultSearchService](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/vault/internal/application/search/VaultSearchService.java), lines 44–60, already accepts bounded candidate IDs and excludes missing/trashed entries in one batch query. Feed's [module descriptor](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/package-info.java), lines 35–41, already allows `vault::search`; [FeedSearchService](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/application/search/FeedSearchService.java), lines 142–193, demonstrates batch qualification and continued scanning. No new Vault API, cross-owner SQL projection, entity/repository import or module edge is justified. Do not copy the existing search/ranking engine to obtain a new read method.
3. **Qualify before deciding page completion.** Read bounded Feed-owned keyset batches and qualify each batch, preserving Feed order. Continue until `limit + 1` eligible rows or genuine source exhaustion; never stop merely because one candidate batch is all trashed, and never fixed-overfetch then report false exhaustion. Return at most `limit` items; emit a cursor from the last **returned** tuple only when an additional qualifying item was found. A candidate scan may advance internally past rejected rows, but must not place the public cursor beyond an eligible lookahead item. Use strict `(saved_at, id)` descent and database-read timestamp precision. This is a read-path acceptance constraint, not a new shared pagination subsystem.
4. **Bounds and live-list semantics are explicit.** Keep each candidate/qualification batch at most 100 IDs, below Vault's existing 601-ID ceiling. Retain only the bounded response/lookahead and current batch, with no load-all, full count or metadata call per row. Total work can grow with the number of trashed candidates; no constant-query-count or latency claim is made. A page is a live read, not a cross-request snapshot or RAG publication authority: trash committed before qualification is excluded; a later trash/restore or insertion may change subsequent reads. Newer saves above the cursor require restarting from the first page. No source reservation, write lock or guarantee of visibility at network-send time is added.
5. **Cursor validation is structural, not a new security credential.** Use one bounded owner-local token carrying a version, saved-time/positive-long-ID tuple and normalized optional kind; reject malformed encoding, oversized input, invalid fields/version/range or filter mismatch with a safe 400. Cap encoded length at 512 characters before decoding. A structurally valid edited tuple is another seek position subject to the same authenticated query and Vault qualification; do not claim cryptographic tamper detection. This explicitly clarifies the prospective design's broad word “tampered”; no frozen credential or security contract is relaxed. No signing key, stored cursor session or new dependency is needed. Limit may change between requests; kind must match.
6. **Reuse existing error and URL behavior.** [FeedExceptionAdvice](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/web/advice/FeedExceptionAdvice.java) maps `InvalidSavedResourceException` to 422; [ApiExceptionHandler](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/ApiExceptionHandler.java), lines 212–218, already maps `IllegalArgumentException` to a safe 400 / `INVALID_ARGUMENT`. Normalize malformed cursor input to that existing structural-validation path, without echoing its contents; do not reuse the 422 business exception or add an advice/exception hierarchy. Other decoder failures must not accidentally escape as generic 500. [Manual-save DTO](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/web/dto/CreateManualSavedResourceRequest.java) and [SavedResourceService](../../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/application/SavedResourceService.java) validate blank/length, not an HTTP-only scheme. Preserve that acceptance. URLs/titles/raw metadata remain untrusted JSON data; there is no fetch, redirect or executable rendering in this slice. Safe navigable schemes belong to the later explicitly approved frontend contract, before actual browser opening is built.
7. **Trash filtering is additive.** Current ID/hash/recent service reads do not qualify Vault lifecycle. Preserve those accepted operations, including lookup of a trashed duplicate and stable 409 on resave; only the new Inbox list is active-only. This is an authenticated Owner lifecycle choice, not a claim that trash is an authorization boundary. Restoring an entry makes it eligible again at its original saved-time position.
8. **No schema amendment is needed for the selected behavior.** The frozen DBML/V1 have shared Vault identity, URL-hash uniqueness and `saved_at`, but no read/archive fields. Migration inventory shows existing kind/title/external-ID/trigram indexes, not a saved-time composite index. Query-plan/runtime suitability is **NOT_VERIFIED**, with focused evidence due during implementation; a scan/sort on a small owner dataset alone does not authorize a migration. If actual evidence requires an index or another frozen-boundary change, stop for the smallest explicit Owner amendment instead of silently adding it.
