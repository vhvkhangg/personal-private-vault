# GDI26 — Concrete OAuth callback, token custody and failure rules

**Chosen by Owner D04=A / D07=A on 2026-11-05; design accepted for preparation in [independent re-review 2](reviews/2026-11-05-gdi26-independent-pre-handoff-re-review-2.md).** This document defines the *specific S1 design for handoff*, not a deployed OAuth client or approved real Google token use. All implementation/runtime proof remains NOT_RUN.

## 1. Provider boundary, exact URI and auth flow

- **Environment:** initial localhost backend on port 8080; propose **one fixed callback** `GET http://localhost:8080/api/v1/drive/oauth/callback` (register exact URI in Google Cloud OAuth client). HTTPS callback/domain is separately validated before remote use; do not construct callback URI from untrusted Host or forwarded headers. Google requires exact redirect match and permits HTTP for localhost. See [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server).
- **OAuth client and scopes:** one Google Cloud **web-application OAuth client ID/secret** for both independent Google accounts. Request `openid`, `email`, `https://www.googleapis.com/auth/drive.file`; `access_type=offline`; PKCE `S256`, random high-entropy state, OIDC nonce. No `drive`, `drive.readonly` or `drive.metadata.readonly` scope. Do not silently include prior broader scopes.
- **Initiation:** authenticated PPV-JWT `POST /api/v1/drive/connections/{slot}/authorize`, slot **only 1 or 2**. Bind pending state to current PPV owner, target slot, cookie proof, PKCE verifier, nonce and fixed redirect URI in a **bounded ephemeral in-memory** map (max 4, TTL 5m, one active attempt per slot; newer attempt invalidates older). This S1 localhost design is for a single active backend process; process restart intentionally invalidates pending attempts. Multi-instance OAuth routing is not authorized by D07, and is separately evaluated before remote deployment.
- **Browser binding:** the initiation endpoint emits `Set-Cookie` with random proof; `HttpOnly`, `SameSite=Lax`, short TTL, path limited to OAuth callback, `Secure` under HTTPS; for localhost HTTP, browser-specific secure-cookie exception and delivery must be verified in a real browser. Cookie never contains Google code or refresh token. On callback, consume state exactly once and require constant-time cookie proof match, expiry, slot and nonce/PKCE context **before** exchanging code. Reject missing cookie, expired state, replay, wrong slot, unknown account and restart-loss; no remote call on failed guard. An API client and browser with different cookie jars **cannot** complete this callback. This is a deliberate S1 usability limitation until S3 browser UI.
- **Public callback:** add **one exact GET permit** to existing Spring Security matcher; no generic `/api/v1/drive/**` permit. Google navigation does not carry the original JWT. The callback's one-use server state + cookie is its mandatory authorization gate, not another PPV login flow. Return generic static success/failure text or fixed same-origin destination; **never redirect to a client-controlled URL or emit token/code in URL/HTML**. All other Drive endpoints retain PPV JWT bearer requirement. PPV's existing stateless JWT/CSRF model otherwise stays unchanged.
- **Exchange and identity:** server-side code exchange to configured Google token endpoint using exact registered redirect and PKCE verifier over verified TLS; validate ID-token signature using Google issuer/JWKS, expected issuer, audience, expiry, nonce, nonblank `sub`; `email` is display-only. Validate granted Drive scope and required identity scopes; reject reduced grants. Unrecognized Google `sub` in an occupied slot is **not** a silent account replacement. Unique Google `sub` cannot occupy both slots, including concurrent callbacks. No login to PPV using Google OIDC is created.

## 2. Secrets and encrypted persistence

- **Config default OFF:** `ppv.drive.enabled=false`. Disabled startup must not load client credentials/keys, create active OAuth callbacks or make Google calls; endpoints may be absent and security matcher must not unintentionally expose an active handler.
- **Cloud credentials:** supply `PPV_DRIVE_OAUTH_CLIENT_ID`, `PPV_DRIVE_OAUTH_CLIENT_SECRET` securely (prefer environment/secured local secret file), and exact `PPV_DRIVE_OAUTH_REDIRECT_URI`. No secrets committed to Git, emitted in logs, fixture receipts or documentation. Client ID is not secret; secret is.
- **Token key custody:** `PPV_DRIVE_TOKEN_KEY_FILE` points to an existing **32-byte AES-256-GCM key** in a protected file outside Git and PostgreSQL, with OS owner-only ACL. Startup when Drive enabled and key missing/short/unreadable **fails closed** before any callback/provider call. Preserve backups of key separately from encrypted DB backup; missing old key makes stored ciphertext unusable, not a reason to store plaintext.
- **Encryption format:** random unique 96-bit GCM nonce per write, 128-bit authentication tag, explicit encoding format/key ID, with authenticated associated data including connection slot and verified Google `sub`/credential epoch (prevents ciphertext swapping). Persist ciphertext + nonce/tag, no durable access token. Never use local PPV JWT signing secret as token key. A key change **without** re-encryption cannot decrypt old tokens; no automatic key rotation is promised. Operator recovery is explicit reconnect, with local credential invalidation and acknowledgement that remote revoke may need to be performed in Google account security settings.
- **Durable row:** new Drive-owned `drive_connections` table, no OAuth fields in `external_accounts`, `settings`, or `authentication.refresh_tokens`. See [schema proposal](drive-api-ui-and-storage-plan.md). Persist only required metadata, verified `sub`, granted scope, status, encrypted refresh token and credential epoch; no file bodies. Database backups containing ciphertext are confidential; key and backup restore are controlled operationally.

## 3. Exact token lifecycle and races

- **First connect** only succeeds with valid `sub`, authorized scopes and a usable refresh token. If Google omits the refresh token on a first grant, return reconnect-required rather than falsely report connected.
- **Same-subject reconnect** may preserve an existing **valid** stored refresh token when Google omits one; may not replace a different-subject slot. A revoked/invalid credential needs fresh user consent and a usable refresh token before `CONNECTED`.
- **On `invalid_grant`:** mark `RECONNECT_REQUIRED`, remove unusable encrypted credential locally and make no further new Drive calls until fresh grant. A refresh response without `refresh_token` must not erase a still-good value.
- **Disconnect:** invalidate/remove local credential and pending starts first, invalidate cached scoped metadata, then attempt exactly **one bounded, best-effort** remote Google revoke of the captured old token. Does not delete Drive files. Distinguish the local result from `REQUEST_ACCEPTED` (HTTP 200, **not** full propagation), `FAILED` (conclusive non-success) and `UNCERTAIN` (request may have arrived, e.g. timeout/connection loss). Never silently retry an old revoke after allowing a new same-subject grant.
- **Concurrency:** each durable credential has a random **credential epoch**. Refresh/replace/disconnect compare-and-set against current slot+epoch in a short SQL transaction; never hold an SQL row lock during Google network I/O. Stale refresh/callback response cannot revive deleted/replaced credential. Keep slot/sub uniqueness enforced in PostgreSQL and map database conflicts to sanitized stable API errors. Stop *new* dispatch after disconnect's local invalidation; already in-flight remote Google calls may finish, must not restore local access or falsely claim cancellation. **Local epoch/CAS is not a substitute for the remote project-grant fence below.**
- **Errors:** sanitized provider errors; 401 one bounded token refresh; `invalid_grant` requires reconnect, 403 permission differs from quota, 429/5xx bounded retry policy with Retry-After where safe; no raw Google response, file name, URL, auth code, token, PKCE verifier, state or cookie logged. No periodic refresh or background jobs in S1.


### 3.1 PH-03 — same-subject/project revoke ↔ reconnect ordering (S1 mandatory)

**Provider contract:** Google OAuth token revocation can invalidate **all tokens/granted scopes for the same user and Google Cloud project**, not only the old refresh token, and may propagate after HTTP 200. See [Google token revocation](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke). This is a *provider-side* effect; PPV cannot solve it using slot-scoped SQL CAS alone. Do not promise instantaneous revocation completion, guaranteed future validity or safety across arbitrary provider propagation delays.

1. **Reserve before deletion/send:** under one short bounded *in-process* lifecycle guard, atomically register a revoke fence keyed by `(Google OAuth project, verified google_sub, disconnect generation)` before committing the slot's local credential removal. The fence reservation and short local delete transaction linearize under the same guard used by callbacks for their final credential-commit check: a callback cannot slip a same-subject credential commit into the gap between fence creation and local deletion. On local database failure, roll back/release the fence and **do not** send revoke. The fence coordinates both slots, even when the new callback targets a different slot. Two slots mean at most two subject fences; no persistent jobs or generic queue. Do not hold the in-process guard, SQL lock or SQL transaction across Google HTTP. Preserve the accepted exactly-one-active-backend-process S1 boundary.
2. **While old revoke is outstanding:** immediately report the slot as locally disconnected, reject same-slot new authorize starts (retryable `REVOCATION_PENDING`) and reject any callback for the *same subject/project* at the final credential-commit gate, regardless of slot. The other subject is unaffected. The Google `sub` of a different-slot callback may become known only after a code exchange: recheck the subject fence **before** persisting/returning `CONNECTED`; consume/reject the one-use attempt with a sanitized browser result and never revoke that newly exchanged token as cleanup (which would revoke the whole project grant again). Do not claim the new grant was usable.
3. **Reject stale attempts even after HTTP returns:** any OAuth authorization attempt created **before or during** the applicable old revocation must not commit a credential, even if its callback arrives later. Track a bounded per-subject revocation generation/cutoff in the in-memory lifecycle guard and recheck under that same lifecycle guard while executing the short final local credential-commit transaction; a successful new consent must be **initiated after** the old revoke request has terminated and after the local fence admits a new start. Check the valid freshly issued refresh token with a bounded provider operation before reporting `CONNECTED`; if this fails, return `RECONNECT_REQUIRED`, never pretend it succeeded. This post-check does **not** certify permanent validity against Google's eventual propagation.
4. **Completion and timeout:** after a terminal HTTP 200, record **only** `REQUEST_ACCEPTED`, end the active request and admit a *new explicitly owner-initiated* consent flow; **do not** start another revoke of the old token. After definitive failure or an ambiguous timeout/transport failure, report `FAILED`/`UNCERTAIN` respectively, keep an in-memory `REVOKE_UNCERTAIN` quarantine keyed by subject/project (bounded by two) and reject same-subject credential acceptance in either slot. Do not auto-retry, auto-clear a timeout, or schedule background work. Remote revocation is best-effort; local disconnect succeeds independently.
5. **Recovery / restart boundary:** an uncertain outcome requires the Owner to inspect/revoke PPV project access in Google Account security settings, then initiate fresh consent only *after* the earlier revoke operation has ceased and the deployment is in a clean controlled state. A process restart intentionally drops ephemeral fences and pending OAuth state; **restart alone is not evidence that an in-flight remote revoke finished**. No automatic OAuth grant or previous credential is restored after the local delete. Provider behavior after an uncertain request or even HTTP 200 cannot be proven finally from this API; any later `invalid_grant` must atomically downgrade to `RECONNECT_REQUIRED` with no stale credential resurrection. A stronger crash-durable/permanent guarantee would require a separately reviewed persistence/protocol change; this S1 does not claim it.
6. **Readout:** the existing DELETE response and authenticated GET connection-status route report local `DISCONNECTED` separately from the best-effort remote state `PENDING | REQUEST_ACCEPTED | FAILED | UNCERTAIN` **while the process retains that bounded information**. A synchronous DELETE may wait up to the explicit transport budget; when it times out, it returns local success plus remote `UNCERTAIN`, not global success or `CONNECTED`. The GET route may report a transient in-memory status for a deleted slot; after restart it must not fabricate historical remote success. Exact API response bodies/error codes and bounded timeout values are fixed by the S1 executable handoff, without new routes or stored secrets. The browser callback displays only a generic retry/failure result on fence rejection.

**Interleaving to reject:** U@slot1/E1 R1 → local disconnect + `REVOKE_IN_FLIGHT(U, project)` → OAuth U/R2 in same slot **or slot2** → callback after code exchange **must not commit/claim CONNECTED** → old revoke releases or remote grant is later invalidated. Keep unrelated V@slot2 unaffected and preserve prior slot/epoch CAS checks.
