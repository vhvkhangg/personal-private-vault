# GDI26-S2 — four bounded backend routes, provider operations and file I/O

**Proposed API; not implemented or approved until a reviewed executable handoff.** All paths are private, PPV bearer-JWT required, root `ApiResponse` on JSON routes, and no new public OAuth matcher. The existing S1 GET callback remains the only special browser route. Exact DTO/request spelling is for Codex refinement under the chosen behavior; do not add frontend or Picker.

| Method/path (proposal) | Operation | Response / state |
| --- | --- | --- |
| `POST /api/v1/drive/connections/{slot}/root-folder` | `ensureDriveRootFolder` | Create/reconcile one app root; return minimal root status, no token; `READY` only after remote verification; `PENDING/UNKNOWN` sanitized outcome. |
| `GET /api/v1/drive/connections/{slot}/files?limit=25&cursor=...` | `listDriveRootFiles` | Direct binary files; bounded 1–50 page, selected fields `id,name,mimeType,size,modifiedTime`, opaque next cursor, no broad search. |
| `POST /api/v1/drive/connections/{slot}/files` | `uploadDriveRootFile` | Multipart `file` **plus required `Idempotency-Key` header**, max **50MB/file** / existing 55MB total request. Same action/key can return its completed result or sanitized pending/unknown status, **never** create a second provider file ID. |
| `GET /api/v1/drive/connections/{slot}/files/{fileId}/download` | `downloadDriveRootFile` | Binary attachment streaming response, no JSON file bytes, no token/Google URL to browser. |

Expected routes: S1 baseline 235 OFF / 239 ON; **S2 adds four**, thus projected 243 with both flags ON. Independent route inventory must confirm exact counts and no unexpected open security route. `ppv.drive.files.enabled=false` is a **proposed extra OFF-by-default gate** under S1's `ppv.drive.enabled=false` default; no S2 endpoint/provider transport should initialize when only S1 is enabled. Enabling S2 without S1 must fail configuration validation. New activation is **not** granted by acceptance.

## List (direct children only)

- Always resolve slot -> current S1 verified subject/epoch and revoke fence -> READY root binding, then remote-verify the root with its **mandatory** markers. (The separate `ensure` route may begin from ABSENT; see the operation matrix in [folder lifecycle](folder-lifecycle-and-persistence.md#ph-01-operation-specific-authority--one-transition-contract).) Use `files.list` with exact query **`'<root_id>' in parents and trashed = false`**, fields/pageSize/nextPageToken. Filter to app-created binary entries with **mandatory** exact `appProperties.ppvKind=file`, `ppvRootBinding=<current root binding UUID>`, `ppvCreatedId=id` and a nonempty bounded `ppvUploadAction`; verify `parents` is the current root, `trashed=false`, MIME/type and safe sizes. Skip native Workspace editors, folders, shortcuts and entries with absent/mismatched/malformed proof. Request the *internal* provider fields explicitly, including `id,name,mimeType,size,modifiedTime,parents,trashed,appProperties`, but project only safe name/type/size/time/id to the user. **Do not rely on the filename to confer authority.** Query direct children only; no recursion.
- Finite provider page requests per HTTP call (proposal: **max two**), independent page size at most 50, and bounded metadata body/entry/name lengths. If results are filtered out, an empty visible page **may still carry next cursor**; do not loop indefinitely to fill a page. A provider `nextPageToken` is untrusted, opaque: either sign/bind/expire client cursor to subject + folder binding epoch + query or server-side hold a short-lived bounded cursor. Do not accept a page token from slot V for slot U.
- Include only safe metadata, never raw `webContentLink`, `exportLinks`, access tokens, email, root Google sub, appProperties, or provider stack traces. Google file listing is not a replacement for PPV's own global Search module.

## Upload (original byte stream)

- Server receives a **single** original file via `multipart/form-data`. Existing Boot multipart limits `50MB` file/`55MB` request are authoritative; validate Content-Length if known and enforce actual bytes while reading, reject empty filename/controls/traversal/header injection, bound displayed UTF-8 filename, use safe default `application/octet-stream` for untrusted MIME. Empty content may be allowed if a file name is valid; no content sniffing/AV assurance is asserted. Client-supplied size/type/name never proves provider outcome.
- Resolve connected subject+root; verify actual root with Google before upload. Create provider binary file **under root** using `parents=[rootId]` and the **required root/file-ID/action-bound appProperties** defined in [folder lifecycle](folder-lifecycle-and-persistence.md#ph-02-creation-provenance-proof-not-a-file-name-convention). Do not pass a client parent ID, arbitrary URL or Google access token through REST. Only Google fixed HTTPS Drive endpoints are allowed. Use **streaming/spooling**, not a whole-50MB heap buffer; bound concurrent streams, connection/read/body deadlines and response metadata. Reusing S1 OAuth client's tiny JSON response-buffer limits for 50MB content is forbidden.
- **PH-03 — mandatory stable upload action and loss-of-response contract:** each `POST upload` MUST include a stable client-created `Idempotency-Key` in format `yyyyMMddTHHmmssZ.<UUIDv4>` (UTC action creation time and random UUID, ASCII, bounded length; reuse the **identical** key for every retry of that action). A new intentional upload must use a **new key**, including if bytes/name happen to match. On a new, unrecorded key only, require timestamp no older than 10 minutes and no more than 2 minutes in the future; an unrecorded stale key fails `UPLOAD_KEY_EXPIRED` **before provider mutation**, even after a completed-intent record was pruned. An already-recorded key may be reconciled later irrespective of timestamp age. The authenticated Owner, S1 verified `google_sub`, current root `root_binding_id` and key form the immutable action scope; another root/account's key is not a valid authority or cross-account lookup.

Spool at most 50 MB on protected temporary disk while computing **server-observed** SHA-256, MD5, actual byte length and normalized safe filename/MIME. These values form a durable immutable request fingerprint; **never trust a client digest**. A PostgreSQL unique insert admits one winner for `(google_sub, root_binding_id, idempotency_key)`; a same-key different fingerprint is **409 `UPLOAD_KEY_CONFLICT`** with **zero provider create**. Concurrent same-key requests share this ledger row; nonwinners may receive `UPLOAD_IN_PROGRESS` or reconciliation results, never allocate another provider ID. Enforce finite admission for pending and retained intents. This is a **small upload-intent ledger**, not a full file catalog (see [folder lifecycle](folder-lifecycle-and-persistence.md#ph-03-durable-upload-intent-and-provider-id)).

For the winning row, allocate one Google `files.generateIds` ID and persist it **before** dispatch. Persist `DISPATCHED` in a short transaction **before any provider upload starts**; no SQL lock around network I/O. Google `files.create` must carry the pre-generated ID, exact root parent and appProperties bound to root/provider ID/action digest. On clean verified completion, CAS to `COMPLETED` and return the same provider ID on a matching retry **after rechecking current S1/root/file permission**. On timeout, response loss, disconnect or process crash after `DISPATCHED`, persist/restore `RECONCILIATION_REQUIRED` and **never replay `files.create`**, even with the same ID, as an automatic retry. Later replays of the *same* multipart request and key only perform a bounded `files.get(provider_file_id)` check: verify root-bound metadata, required markers and original length+checksum; then return the known result or `UPLOAD_OUTCOME_UNKNOWN` (no second mutation). A single 404 or absent checksum is not evidence of permanent noncreation. If no valid S1 authority/root exists, the retry fails closed without provider work but leaves its intent intact.

**Lifetime:** retain unresolved/unknown or dispatched intents without automatic TTL eviction; do not free the provider ID on 404/timeouts. Retain terminal results for **at least 30 days**, then allow bounded pruning; old missing keys are rejected by the timestamp-freshness rule, not silently treated as new uploads. Proposal: at most **8 nonterminal intents and 1024 retained intent records per root**; when full, reject *new* actions before Google mutation, while still allowing existing-key status/reconciliation and S1 disconnect. Prune only eligible terminal records, never uncertain/dispatched ones. A newly supplied valid key after a different intentional upload is a **new** action, not an automatic retry. This is a within-key durable duplicate-prevention guarantee, **not** an exactly-once transaction shared with Google. No new HTTP route or background job is necessary: repeat the identical multipart POST with the same key to reconcile; explicit operator intervention for permanently unknown actions is documented, not silent deletion/overwrite.
- No conversion to Docs/Sheets/Slides, no update-overwrite, duplicate-name normalization or overwrite-by-filename, no **persistent resumable upload session or restart-continuation feature** required by D10 (Google resumable upload protocol remains appropriate for >5MB); if provider enforces other semantics, Codex must record bounded fallback, not silently widen scope.

## Download (authorized binary only)

- Before provider content call, `files.get` metadata for requested `fileId` **using that slot's Google credential**; enforce `parents` contains exactly authorized root, `trashed=false`, **all mandatory root/file-ID/action-bound `appProperties`**,  non-folder, non-shortcut, non-Google-native MIME and readable size (proposed max 50MB per response for bounded S2 scope). Reject file moved outside root even if `drive.file` still grants access. The API must not accept external URL or caller-provided Google account identity.
- Stream `files.get?alt=media` to authenticated PPV client with `Content-Disposition: attachment` and safe encoded filename, content type `application/octet-stream` or safe validated MIME, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`. Do not enable `acknowledgeAbuse` automatically, do not follow shortcuts or export Google-native documents. Enforce actual-byte cap even if Content-Length is absent/false; terminate/close streams on disconnect or size/deadline failure. For already-committed output headers a downstream stream failure **cannot reliably become JSON**; document truncated-response behavior.
- Metadata check and remote media GET are separate calls; recognize the TOCTOU gap if provider changes parent/bytes between them. Revalidate current local authority before dispatch and on completion where feasible, stop continuing after disconnect; **do not promise rollback of already-streamed bytes**. A deterministic test must demonstrate no *new* file-content dispatch after invalid authority, without claiming remote cancellation of in-flight bytes.

## Upload response/retry summary (same four-route API)

| Incoming upload and durable action state | HTTP/API result | Google create action |
| --- | --- | --- |
| No key, malformed key, or unrecorded stale/future-dated key | 400 `UPLOAD_KEY_REQUIRED/INVALID` or 409 `UPLOAD_KEY_EXPIRED` | **None** |
| New valid key, current S1/root, under bounded capacity | Calculate fingerprint, unique-insert `PREPARING`, reserve/persist provider ID, dispatch at most once; 200/201 only after remote verification | **One** only |
| Same key, same fingerprint, `PREPARING/RESERVED/DISPATCHED` | 409 `UPLOAD_IN_PROGRESS` or `UPLOAD_OUTCOME_UNKNOWN`; do not promise response arrives | **None** |
| Same key, different fingerprint or other root/account | 409 `UPLOAD_KEY_CONFLICT` or authorization failure, never look up another account's intent | **None** |
| Same key, completed and still authorized/in-root | 200 with original provider ID after safe provider/local checks | **None** |
| Same key, `RECONCILIATION_REQUIRED` after lost Google or PPV response/restart | `files.get` exact reserved ID only; 200 on fully matching verified file, otherwise 409 `UPLOAD_OUTCOME_UNKNOWN` | **None** |
| New valid key while stale/unknown intents hit capacity | 503 `UPLOAD_CAPACITY_EXHAUSTED`; existing intent remains recoverable | **None** |

A 2xx response subsequently lost by the caller is handled via the same durable key, not a new provider identity. Provider `409` for a pre-generated ID is not by itself success: perform exact `files.get` verification. A deliberately **new key** may represent a user-intended second copy; PPV does not silently deduplicate distinct user actions. S2 excludes automatic deleting/overwriting provider files or resume-after-restart transfer sessions.

## Provider errors and budgets

- `401/invalid_grant`: use accepted S1 current-epoch-specific downgrade; never use another slot's token. `403` insufficient scope/permissions/quota, `404` missing/inaccessible, `429` rate limited, `5xx`, timeouts and malformed/oversize metadata: map to **stable sanitized codes**, with no leaks or false 200. Bounded non-mutating reads may use conservative retries if justified; **no automatic blind mutation retry** on folder/file create.
- Validate and cap HTTP response bodies, header sizes, multipart limits, redirect behavior, decoded metadata and length. No arbitrary provider URL overrides, SSRF via `fileId`, redirecting `Authorization` across hosts, or unbounded temp-file accumulation. Implementer must define exact budgets in handoff and run controlled slow-stream/headers-only/partial-response tests, including cleanup of temporary spool files.
- Google `drive.file` alone does not guarantee all content inside a folder is visible; D06 excludes silently imported external files. Generic format acceptance is **not** a guarantee Drive supports upload of every source MIME, quota, policy, abuse flag or huge existing file.
