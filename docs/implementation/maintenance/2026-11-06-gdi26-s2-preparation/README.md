## Selected product behavior

- **Two slots, two independent verified Google subjects.** PPV creates one root `PPV` folder per account **in that account's My Drive** and retains its opaque binding; no scanning folders by name or cross-account switching.
- **D08=A:** direct-child regular file listing only. No nested-folder create/browse, recursive index, alias, shortcut traversal, manual insertion discovery or Google Picker.
- **D09=A:** raw binary files, e.g. PDF, images, videos, ZIP, Markdown, DOCX and XLSX **as original bytes**. Google-native Docs/Sheets/Slides conversion/export is not implemented; do not confuse an Office binary file with a Google-native document.
- **D10=A:** max **50 MB per upload**. Google recommends multipart for files up to 5 MB and resumable protocol for larger transfers; D10 does not require **persistent restart/resume UX**, but the provider transport must follow the documented size guidance. Current `backend/src/main/resources/application.yml` sets `spring.servlet.multipart.max-file-size=50MB` and `max-request-size=55MB`; stream/spool boundedly, with no persisted resumable session, restart-continuation feature or blind mutation retry in S2.
- **Still excluded:** Media S3 replacement, share/delete/rename/move/copy, cross-account transfer, auto-sync, RAG, S3 frontend Explorer and Phase 16. `drive.file` is not a folder-level Google OAuth restriction; **the backend must enforce the allowed folder independently**.

## PH-01..03 corrected technical proposal (independently reviewed for preparation)

- **PH-01:** first ensure uses authenticated current S1 subject/epoch/revoke fence but **no existing READY root**. It reserves ABSENT→PENDING, reconciles by one reserved ID, and promotes to READY only after complete provider metadata and final S1/root CAS. All file content routes require READY. See [state matrix](folder-lifecycle-and-persistence.md#ph-01-operation-specific-authority--one-transition-contract).
- **PH-02:** `appProperties` are **required** for roots and binaries, and bind `ppvKind`, random `root_binding_id`, expected provider `id`, and (for files) action-key digest. Cross-account U→V, copied/wrong-ID, missing-marker and moved-out negatives fail closed; public DTOs omit private markers. See [provenance rule](folder-lifecycle-and-persistence.md#ph-02-creation-provenance-proof-not-a-file-name-convention).
- **PH-03:** upload requires a stable timestamped-UUID `Idempotency-Key` on the **existing** multipart route; one minimal Drive-owned upload-intent ledger maps `(subject, rootBinding, key, server-computed fingerprint)` to **one pre-generated provider ID** before create dispatch. An identical retry after lost Google/PPV response or restart returns the verified same file or a safe unknown, **never** allocates a second ID. Unknown intent never silently expires; completed records may be pruned after 30 days because aged keys cannot be newly admitted. See [upload retry contract](file-api-and-io.md#upload-responseretry-summary-same-four-route-api).
- **Schema boundary adjustment:** propose **two Drive-owned metadata tables in one additive S2 migration** (root binding + bounded upload-intent), not a general file catalog, new endpoint, distributed lock, background job or persistent Google resumable-session feature. S1 V25 and S1 acceptance stay unchanged; actual migration/ADR/canonical DBML work is for a later authorized S2 handoff.
