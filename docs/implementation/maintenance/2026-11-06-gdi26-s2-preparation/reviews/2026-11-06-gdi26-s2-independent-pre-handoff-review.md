## Findings

### GDI26-S2-PH-01 — first-root creation cannot satisfy the universal READY predicate

**MEDIUM / OPEN; S2-03/04/05.** [security-and-concurrency.md:5](../security-and-concurrency.md) requires a corresponding READY root and successful provider verification **for every operation**. [folder-lifecycle-and-persistence.md:16](../folder-lifecycle-and-persistence.md) instead requires ensure to work with no binding, reserve PENDING, then create/reconcile; the first route in [file-api-and-io.md](../file-api-and-io.md) exposes that operation.

The first valid ensure begins with no READY root. Applying the universal authorization predicate rejects it; exempting ensure wholesale could also exempt the required current S1 subject/epoch/fence checks. The documents therefore do not provide one executable authority rule for their first observable feature.

**Smallest correction:** state operation-specific predicates: authenticated current connected subject/epoch/fence for ensure; exact durable intent and expected provider identity for create/reconcile; READY/current root plus file proof only for content operations. Keep the final local authority/CAS check and unknown-outcome retention. Do not require an existing READY folder before its first creation or let ensure bypass S1 authority.

**Preparation closure proof:** one consistent transition/authorization table covering ABSENT, PENDING, RECONCILIATION_REQUIRED and READY; trace first U/V ensure, repeated/restarted ensure, disconnect while create is paused and rejected file access before READY. Specify future deterministic tests; do not run implementation tests now.

### GDI26-S2-PH-02 — creation provenance is optional in the design but mandatory in acceptance

**MEDIUM / OPEN; S2-06/08/13/15.** [folder-lifecycle-and-persistence.md:7](../folder-lifecycle-and-persistence.md) makes appProperties optional, while line 32 requires rejection when they are missing. [file-api-and-io.md:16](../file-api-and-io.md) offers a private marker only as an example; line 29 makes an app-created marker mandatory for download. Acceptance requires excluding externally inserted files and cross-account content, without selecting a consistent proof or declaring what metadata Google must return for that proof.

A matching parent plus project-wide “created by PPV” marker does not establish that the file was created for **this root/account**. As a preparation counterexample, a previously PPV-created U file manually placed in V's managed root can satisfy both checks if the marker is global, despite the required manual-insertion/cross-account exclusion. This is an authorization-design counterexample, not a claim of observed live Google disclosure. A fake returning plausible metadata cannot be rejected based on an ownership fact the backend neither retains nor requests.

**Smallest correction:** choose and consistently document root/file provenance separately. For example, use a stable server-chosen **root-bound** private creation marker for files, checked alongside current subject/root/parent; durable preallocated root intent can supply root provenance. An equally simple evidence-backed mechanism is acceptable. Define absent/mismatched proof as fail-closed where proof is required; align optional-root-marker wording and negative cases. Distinguish provider authorization fields from the smaller public DTO projection. No full file catalog, broader OAuth scope or new connector framework is required.

Google supports app-private properties, so availability need not remain a speculative branch. Their existence is not itself a substitute for PPV's chosen ownership predicate. [Google custom properties](https://developers.google.com/workspace/drive/api/guides/properties)

**Preparation closure proof:** a single consistent predicate and field inventory for ensure/list/upload/download; future tests for absent/wrong marker, U-created file inserted into V root, ordinary external file, moved-out file and malformed provider metadata. Do not invent a Google subject field on the File resource or trust email/name as account authority.

### GDI26-S2-PH-03 — upload response-loss recovery has no defined request identity or durable outcome rule

**MEDIUM / OPEN; S2-11 and the declared lost-response obligation.** [file-api-and-io.md:9,24](../file-api-and-io.md) proposes a file-only multipart operation, one new provider ID per upload attempt, an optional Idempotency-Key, and unspecified follow-up/manual reconciliation; it explicitly leaves what happens when the caller loses the response to the handoff. [security-and-concurrency.md](../security-and-concurrency.md) and acceptance nevertheless require safe correlation/no silent duplicate after accepted-but-lost upload responses. The one proposed durable root row does not currently describe an upload-intent identity/lifetime or recovery operation.

Concrete contract gap: Google accepts file F; PPV's HTTP response is lost; the caller repeats the same multipart POST. With neither a required stable caller key nor a retained mapping/recovery rule, the service may allocate G and create a second file. Pre-generating F's ID protects a retry **of F**; it does not identify a later PPV request as the same action. Merely naming UPLOAD_OUTCOME_UNKNOWN cannot deliver correlation when that response itself never arrived.

**Smallest correction:** select one bounded mechanism for identifying the same upload action and retaining/reconciling its provider ID and outcome, including simultaneous requests, fingerprint mismatch, response loss and restart/expiry. A bounded outstanding intent per root is a possible simpler alternative to a file catalog; this review does not mandate a new table, endpoint or persistent resumable session. State exactly how the existing route/header contract obtains and reuses the action identity, what repeated requests return, and when a genuinely new action may proceed. Do not claim restart-safe duplicate prevention from memory-only correlation or release an ambiguous intent merely because a timeout/404 occurred. If a deliberately weaker product guarantee is chosen instead, obtain an explicit Owner disposition rather than silently dropping S2-11.

**Preparation closure proof:** a finite state/request table and updated schema/edit-boundary proposal demonstrating one provider identity for simultaneous/repeated same-action requests, no reallocation after lost response, safe payload mismatch rejection and explicit restart/expiry handling. This is a technical contract correction under the selected scope, not a requirement for resume UI, background jobs or distributed exactly-once delivery.

## Source-backed feasibility and necessity

The open Google pre-generated-ID question is **resolved at documentation level**: Google's v3 upload guide permits ordinary binary resources and explicitly permits the folder MIME type; reuse of an already-created ID conflicts instead of creating a duplicate. `files.generateIds` supports drive.file. This supports the planned root identity without a name scan or fallback architecture. It does not resolve PH-03's PPV request-to-ID mapping. [Pre-generated IDs](https://developers.google.com/workspace/drive/api/guides/manage-uploads#use_a_pre-generated_id_to_upload_files), [v3 generateIds](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/generateIds)

Google describes multipart for small uploads and resumable transport above 5 MB. A request-local resumable session followed by bounded content transfer is compatible with D10's exclusion of persisted restart/resume UX. Validate the returned session URI against the selected fixed Google HTTPS origin/path before any credential-bearing request; session URIs must remain private. Blob download uses files.get with alt=media, whereas Workspace export is a separate operation and stays excluded. These are documented feasibility facts, **not live provider acceptance**.
