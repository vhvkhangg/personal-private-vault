# GDI26-S2 — end-to-end authority, concurrent operations and negative proof

## PH-01 — operation-specific admission, never a folder-name check

**Common predicate for every S2 request, including initial ensure:** authenticated PPV singleton Owner JWT; exact slot 1/2; current S1 `CONNECTED` credential with verified Google `sub`, captured `credential_epoch`, usable `drive.file` and no subject/project revoke PENDING/UNCERTAIN fence. Reject before external mutation if stale/fenced. A first `ensure` on `ABSENT` intentionally **does not require READY**; it may reserve one unique durable root intent (subject, preallocated file ID, root binding ID) and only then issue one Google create. `PENDING` or `RECONCILIATION_REQUIRED` permits only bounded same-ID reconciliation; `READY` permits revalidation, never automatic recreation. Final `READY` publication requires current S1 epoch/fence and root-row CAS **again**.

**Additional predicate for list/upload/download only:** subject U has a `READY` root binding, verified *now* by Google under U's credential for `id,type,parents,trashed,appProperties` and root-binding markers, then direct-child file proof for list/download and mandatory upload marker+durable action for create. No `READY` => no file access, not even while first ensure is pending. The exact per-state matrix is [canonical folder lifecycle](folder-lifecycle-and-persistence.md#ph-01-operation-specific-authority--one-transition-contract); the [upload retry matrix](file-api-and-io.md#upload-responseretry-summary-same-four-route-api) is separate. All checks are under the **same Google subject's OAuth context**. Never accept a caller `sub`, parent/root ID, URL, access token or untrusted endpoint. OAuth `drive.file` is file-scoped grant visibility, **not** a Google-enforced PPV folder sandbox.

A cached metadata list result, an `Idempotency-Key`, a private `appProperties` marker, file name, mimeType, folder name or request cursor never grants authority by itself. Provider file ID, actual root parent, root-specific marker (`ppvRootBinding`), file kind (`ppvKind=file`), and `ppvCreatedId=id` are **joint mandatory checks** for direct-child files. Newly uploaded content must not be exposed through PPV once moved out of the managed folder (despite continued Google project visibility). A folder with the same display name but different file ID remains forbidden.

## Reuse S1 revocation/reconnect semantics

- Existing `SubjectLifecycleManager` enforces **subject/project** outstanding revocation fence and quiescence; do not rebuild it in a parallel S2 authority hierarchy. Only use a current validated token from S1 Drive-private credential custody, preserving `google_sub`, slot and `credential_epoch` CAS. No shared access token storage or token/refresh credential in client responses, root rows, logs or URL query.
- Before provider dispatch and before publishing successful JSON metadata/status, recheck local slot/subject/epoch, fence and root binding version. Disconnect immediately removes local S1 credential authority; queued future work refuses dispatch. Remote operation already accepted may still complete — an upload that finishes remotely after local disconnect is **AMBIGUOUS**, not a falsely successful in-scope operation or proof of compensating deletion.
- The root binding outlives local disconnect by design but must never resurrect a credential. Reconnect U in a different slot can only access U's bound folder after fresh S1 verified grant and metadata validation. V's token cannot read U root or a U fileId, even if provider fake accidentally returns metadata.
- No SQL transaction held through network I/O, stream body or callback. Short root **and upload-intent** row insertions/reservations and CAS finalization only. Use bounded concurrent operation admission; no distributed queues or locks. S1 one-JVM policy is a **selected topology, not verified deployment evidence**. If a second live backend exists, this design's in-process grant fence is not a substitute for cross-JVM safety; activation remains held.

## Failure handling and resource limits

- **Unknown root create:** durable PENDING root ID prevents new parallel root; provider response arriving after timeout must not overwrite a newer binding. Reconcile by the same ID, fail closed if unresolved. Do not use a single immediate Drive 404 as proof that an earlier write can never commit.
- **PH-03 unknown upload:** request must carry client-stable timestamped UUID `Idempotency-Key`; a unique, retained `(google_sub,root_binding_id,key)` row binds fingerprint, exactly one pre-generated provider ID and `DISPATCHED` before any upload I/O. Retry with same key/payload (including after lost PPV response/restart) **never allocates or dispatches a second create**; only exact-ID read-only reconciliation can move unknown to COMPLETED. Wrong fingerprint is 409. Unresolved rows never expire automatically; terminal records may be pruned only after 30 days, and an unrecorded aged key is rejected from its embedded timestamp. No delete compensation (D05), no credential/file bytes in ledger, no background scanning.
- **Moved folder/file:** re-fetch current provider metadata; reject before dispatch. Renaming folder display name alone does not change identity; check immutable ID, type, valid parent and app marker rather than name only.
- **Partial download:** enforce actual bytes/time limit; close provider/client streams. Avoid leaking OAuth auth header on redirect or emitting provider diagnostics in response; no assumption of provider atomicity.
- **App disabled:** missing `PPV_DRIVE_ENABLED` or new `PPV_DRIVE_FILES_ENABLED` keeps routes/provider bean absent. Flyway migrations still apply normally independent of flags; no Drive file I/O in OFF context. Feed scheduler OFF and RAG indexing INACTIVE stay unchanged.
- **Input/resource bounds:** slot 1/2 only; page size 1–50; finite metadata size/page count; upload <=50MB, request <=55MB; candidate download size capped before dispatch and actual bytes capped while streaming; finite concurrent streams and HTTP deadlines; close streams/spool promptly. No user-driven N+1 metadata checks across unbounded collections.

## Mandatory deterministic adversarial scenarios

1. U and V concurrently list/upload/download: only their own root and file IDs, including U file ID sent to slot V. Provider test deliberately returns a plausible cross-account ID; backend still rejects it.
2. U disconnects or regrants while a root-create, upload, list or download is paused; no new provider dispatch afterward and no stale final success. Explicitly classify remote file completion as unknown where irrevocable.
3. Google parent metadata mutates from U root to outside between list and download; direct GET to moved file rejects even if visible under `drive.file`.
4. Root creation delayed and two same-subject callers race; at most one durable create intent/remote identity. One timeout + late success must be reconciled by original provider ID, not name search or automatic new ID.
5. Simultaneous upload requests use the **same** stable key; provider accepts F but Google response or PPV HTTP reply is lost; restart then re-send same key/body: exactly F is retained and verified (or unknown), never G. A second request with same key but altered bytes/name/MIME gets 409, while a genuinely new key is a separate action. Inject a bypass that allocates new ID on replay and prove the test fails. Test an expired/pruned original key is rejected, not reallocated.
6. Provider metadata returns wrong MIME/parents/**mandatory root or file appProperties**, copied U-created file under V root, file-ID mismatch, malicious file name/Content-Disposition, oversized JSON or content-size mismatch; no unsafe browser output.
7. API JWT invalid, slot 3, raw provider cursor cross-slot, Google-native export attempt, nested folder, shortage of quota, unsupported MIME, `429`/`403`/`404`/`5xx`: bounded safe rejection.
8. Restart or reconnect with a persisted root pending/READY or `DISPATCHED/RECONCILIATION_REQUIRED` upload intent and no S1 connection: no file operations or ghost authority; no automatic retry of ambiguous mutation. Retained U binding cannot be attached to V.
9. Portability snapshot/export excludes integration credential and personal subject/root binding unless a separate accepted rule explicitly authorizes its inclusion; migration is additive and unconditional.

**Acceptance proof:** real Spring security and POST multipart response tests, controlled fake Drive HTTP server with stream barriers/metadata mutations, real PostgreSQL Testcontainers plus migration/unique/CAS checks, source-hash qualified S1 test reuse (not a claim that S1 was rerun), and targeted Modulith/API/docs tests. No live Google accounts, credentials or actual network access are needed for preparation; operator live test is a separate gate.
