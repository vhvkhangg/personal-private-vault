# GDI26-S2 — one app-created My Drive root per subject

**Binding goal:** verified Google subject `U` has at most **one local active/uncertain root binding** regardless of slot, disconnect/reconnect or a second `POST ensure` request. Google folder creation is an **external mutation**: a local SQL lock or epoch-CAS alone cannot promise exactly-once creation after timeout. Implement bounded **at-most-one deliberate root creation identity** with provider reconciliation and clear uncertainty, not magical cross-system atomicity.

## Specific reviewable proposal

- Root located directly under the user's **My Drive root**; name `PPV`; MIME `application/vnd.google-apps.folder`. Do not match other folders named `PPV` or adopt manually created folders. Use Google `files.generateIds` to allocate a provider ID **before** create: Google documents pre-generated IDs for `application/vnd.google-apps.folder` and ordinary binary upload, under `drive.file`. Codex must verify the exact chosen transport and response behavior, not treat support as runtime proof. Store this planned ID **durably before dispatch** and use it for lookup/reconciliation. **Mandatory** app-private `appProperties` on the root: `ppvKind=root`, `ppvRootBinding=<server-generated random UUID>`, `ppvCreatedId=<pre-generated root_file_id>` (nonsecret, not a Google subject). Persist `root_binding_id UUID UNIQUE NOT NULL` alongside the reserved `root_file_id` before the create dispatch. Request the exact root `id,mimeType,parents,trashed,appProperties` fields using U's credential and check every field; resolve U's actual My Drive root ID through the same credential rather than comparing against a client-provided folder name. Missing/wrong root marker is **always denied**; the marker supplements current verified `google_sub`, binding epoch and provider parent proof.
- Add separate Drive-owned `drive_folder_roots` metadata relation keyed by `google_sub` (stable verified identity, not slot); proposed fields `google_sub VARCHAR(255) PK`, `root_file_id VARCHAR(255) UNIQUE`, `root_binding_id UUID UNIQUE NOT NULL`, `status VARCHAR(32)` in `PENDING|READY|RECONCILIATION_REQUIRED`, `binding_epoch UUID UNIQUE`, `created_at/updated_at TIMESTAMPTZ`, optional safe nonsecret diagnostic class. **No refresh/access token** in this table. Store root metadata independently because S1 disconnect **deletes** its `drive_connections` row, while D05 disallows deleting remote files and D06 requires no silent duplicate on reconnect. Exclude sensitive connection/root metadata from Portability export unless existing accepted rules explicitly authorize it.
- Alternative of nullable `root_folder_id` in `drive_connections` is smaller but **loses the binding on S1 local disconnect** and cannot by itself prevent a new root for the same subject after reconnect. The separate per-subject row is the smallest robust default for D06. Codex may propose an equally simple verified-equivalent alternative during pre-handoff, not an unreviewed schema fork.
- Do not retroactively edit V25, original frozen Schema v1, S1 credential statuses, S1 reviews. One additive S2 Flyway migration (tentatively V26 only after checking current migration head); update canonical additive DBML/ADR/diagram only in a future approved implementation handoff. The preparation contains **no SQL migration**.

## PH-01: operation-specific authority — one transition contract

The common gate is a **current authenticated Owner JWT + slot 1/2 + S1 CONNECTED credential with verified `google_sub`/`credential_epoch` + no subject/project revoke PENDING/UNCERTAIN fence**. It applies to *every* S2 operation, including first ensure. Only **list/upload/download** additionally require a `READY` binding verified against fresh provider metadata. `ensure` does **not** require a pre-existing READY root; it has stricter durable-intent/remote-proof rules instead. The initial no-root case is therefore reachable without weakening S1 checks.

| Durable state for subject U | `POST ensure` after common S1 gate | `GET list`, `POST upload`, `GET download` |
| --- | --- | --- |
| `ABSENT` (no binding row) | Preallocate one provider root file ID plus random `root_binding_id`; persist `PENDING` via unique U insert **before** one provider `files.create` dispatch; other concurrent callers adopt only that row/ID, never another creation | **Deny `ROOT_NOT_READY`**; never auto-create on a content request |
| `PENDING` | Never allocate/send another `files.create`; same-ID provider `files.get` reconciliation only, or report pending with no usable root | **Deny `ROOT_NOT_READY`** |
| `RECONCILIATION_REQUIRED` | Same-ID read-only reconciliation; 404/timeout/403 alone does not release the ID; report sanitized unknown/unavailable | **Deny `ROOT_NOT_READY`** |
| `READY` | Reverify same U/root ID, exact My Drive parent, folder MIME, `trashed=false`, **mandatory** root markers; return same ID/handle if current | Permit only **after** fresh root verification **and** file-specific checks |
| S1 disconnected, reconnect required, revoked/fenced or changed credential epoch (any binding state) | **Deny** before new Google mutation; retain binding/uncertainty for later same-U connection | **Deny** (no ghost authority) |

Ensure's initial remote mutation uses U's current token and immutable provider-intent metadata. After provider response or read-only reconciliation, a short CAS transaction checks both root binding epoch and current S1 slot/U/credential epoch/fence **again** before committing `READY`. A stale request may leave an unresolved durable intent but cannot confer file access or reset the root. Do not hold SQL locks through HTTP. Remote existence with wrong ID/type/parent/marker or inaccessible metadata is not authorization.

## Create/ensure state machine

1. Owner JWT, exact slot 1/2, S1 `CONNECTED` with `drive.file`, and no current subject/project `PENDING/UNCERTAIN` revocation fence. Capture `google_sub` and `credential_epoch`; derive account-specific API authority from current connection, **never from caller-provided email/sub/root ID**.
2. If `READY`: query Google `files.get(root_file_id)` with selected fields; verify same account's permitted scope, `mimeType=folder`, `trashed=false`, proper My Drive parent, **mandatory** root-bound `appProperties` and `ppvCreatedId` matching the durable planned provider ID. Return the stable root status/ID (or safer opaque handle). If moved/deleted/permission-lost/wrong metadata: fail closed `ROOT_UNAVAILABLE`, no silently-created replacement; do not fall back to name search.
3. If no binding: reserve one durable `PENDING` row by unique `google_sub` and chosen provider ID **before** `files.create`. Concurrent callers see existing PENDING or wait/reconcile rather than creating another ID. The provider call is **outside SQL transaction**. Verify result identity/parent/type and still-current subject/epoch before transitioning to READY under short CAS. If the row or connection changed during request, never publish usable root authority; preserve reconciliation metadata rather than claim the remote operation did not happen.
4. If create response timeout/closed stream/5xx is ambiguous, retain `PENDING` or mark `RECONCILIATION_REQUIRED`. On a later **explicit Owner action**, look up the same provider ID and verify exact metadata **including all mandatory appProperties**. Never blindly issue another create with a new ID or automatically retry the ambiguous mutation. If a real provider/client failure prevents ID allocation, reject before any folder `files.create`; do **not** use an unreserved ID, scan Drive by name or widen OAuth scope. Unexpected provider incompatibility blocks the future handoff/implementation until independently reviewed.
5. On definitive non-creation with evidence, an explicit new attempt may create one root with a new unique identity, but no ambiguous prior creation may be in flight or later materialize. The handoff must spell out and test precise release criteria; do not claim immediate negative `404` proves irreversible non-creation after a delayed create.
6. If remote folder was moved, trashed, removed or converted, return sanitized `ROOT_UNAVAILABLE / RECONCILIATION_REQUIRED` rather than delete or move it. No app-initiated cleanup/deletion; no owner folder recreation without an evidence-backed explicit recovery step.

## PH-03: durable upload intent and provider ID

S2 introduces exactly **one additional minimal Drive-owned metadata relation** `drive_upload_intents` alongside `drive_folder_roots`, in the **same prospective single additive V26 migration**; no physical migration is supplied at preparation time. This is an *upload action ledger*, not a file catalog and not a Google resumable-session store. `drive_connections` V25 is unchanged, and no upload intent is FK-linked to a disconnect-deleted slot/credential row.

| Proposed field / key | Invariant |
| --- | --- |
| `(google_sub,root_binding_id,idempotency_key)` **composite unique/PK** | One PPV upload action per verified subject/current root and caller-stable key. The key uses `yyyyMMddTHHmmssZ.<UUIDv4>`; newly admitted timestamps must be within [-10 minutes,+2 minutes] of server time. Once recorded, retries with the *same* key need not be recent. |
| `request_fingerprint CHAR(64)`, `content_md5 CHAR(32)`, `size_bytes BIGINT`, `safe_name`, `mime_type` | Immutable **server-computed** SHA-256 over raw bytes **plus** normalized safe name/MIME/actual size in the request fingerprint; MD5 and size are used for provider original-byte reconciliation. No file bytes or OAuth secrets persisted. A changed payload/metadata on the same key fails before provider mutation. |
| `provider_file_id VARCHAR(255) UNIQUE NULL` | Exactly one generated provider ID bound to an action before `files.create`. A null ID means **no upload dispatch is allowed**. Never allocate a different ID to a row whose first dispatched attempt is ambiguous. |
| `status` (`PREPARING`, `RESERVED`, `DISPATCHED`, `RECONCILIATION_REQUIRED`, `COMPLETED`, `FAILED_DEFINITIVE`) | Finite lifecycle below; `intent_epoch UUID`/CAS and `root_binding_epoch UUID` prevent stale finalization. Failed definitive means verifiably no provider mutation or stable pre-dispatch input failure, not an inferred 404. |
| `created_at`, `updated_at`, `completed_at` | Auditable retention without raw token, email, upload body or session URL. This relation and root binding are **excluded from Portability export**, without treating a full database backup as secret-free. |

**First request / concurrency:** validate current S1 subject+epoch/fence, READY root plus markers, file size/name and key; spool and hash bounded bytes. Then unique-insert `PREPARING`, one winning caller per tuple; simultaneous losers compare the retained fingerprint and return status, never allocate another ID or send mutation. The winner calls Google `files.generateIds`, persists `RESERVED` with that ID, then CAS-persists `DISPATCHED` **before** first provider upload request. A crash during `PREPARING/RESERVED` proves *this implementation* had not dispatched any bytes, so the same row can be resumed with the already chosen ID (or assigned once if still null); it cannot allocate a second ID after `DISPATCHED`. No SQL transaction or root lock is held during provider network/stream I/O. Actual Google provider support for this exact binary upload transport and 409 conflict must be proven by Codex against primary docs and fake tests.

**After dispatch:** provider success is accepted as `COMPLETED` only if provider returns/GET confirms exact ID, parent=root, mandatory file markers, binary type, size and available `md5Checksum` matching the spool; check fresh S1 subject/epoch/fence, root READY+binding epoch and intent CAS at final publication. Otherwise persist `RECONCILIATION_REQUIRED` and report `UPLOAD_OUTCOME_UNKNOWN` (never false 2xx). HTTP response loss to PPV **or to the caller**, timeout, late success, crash, 409 reserved-ID conflict or file GET 404 all retain the same ID; a replay of the **same** key and body performs **read-only** exact-ID reconciliation, not a second `files.create` or a new resumable upload session. Unavailable checksums or wrong metadata cannot authorize `COMPLETED`. Uncertain upload may have modified remote storage; no delete/move/cleanup compensation is permitted.

**Bounded retention/recovery:** allow at most eight nonterminal intents and 1024 total retained action rows per root. Pending/ambiguous `DISPATCHED` or `RECONCILIATION_REQUIRED` rows **never expire or get pruned automatically**, even after restart; full capacity rejects only **new** actions. `COMPLETED`/`FAILED_DEFINITIVE` rows stay for at least **30 days** before eligible pruning. A key absent after pruning is too old to meet first-admission timestamp freshness and is **rejected**, not reinterpreted as a new action. An Owner who intentionally wants a second copy must issue a genuinely new timestamped UUID key. A permanently unresolved action needs explicit operator investigation; negative GET/404 alone never proves it is safe to release or retry its provider ID. No periodic reconciler, Google Drive file catalog, queue, new HTTP endpoint or restart-resumable Google transport is authorized by this preparation.

**Prospective proof matrix:** same-key identical concurrent POSTs; same key altered bytes/name/type; loss of Google 2xx, loss of PPV 2xx, restart after `DISPATCHED`; old remote request later landing; root U vs V, root binding changed, disconnect/revoke fence while paused; provider 404/missing checksum/wrong marker and correct later GET; completed intent pruned then old key rejected; eight-unknown capacity saturation without evicting uncertainty. A test-only bypass that allocates G on repeat after F was accepted must make an assertion fail. Do not count these as runtime passes in preparation.

## Lifetime and privacy semantics

- Disconnect preserves only the **minimal local Google subject-to-root binding** to avoid duplicate remote folders; it deletes S1 credential authority according to accepted S1 behavior. There is **no file index** or token cached in the root row. Reconnecting U in either slot rechecks the same binding, while a different subject V cannot receive U's root or file metadata. The table is private integration metadata, not a new public Account entity.
- If Owner later wants local subject/root metadata erased at disconnect, that privacy change should be a separately discussed contract: erase+disconnected state loses a deterministic reuse anchor; it does **not** authorize remote folder deletion. Current proposal is to preserve minimal metadata while minimizing exposure and backup/export scope.
- Provider-side changes by the user after creation may break authority. No monitoring/background sync or provider/webhook is added. `drive.file` permissions are **per-file app access**; Google does not enforce PPV's folder boundary.
- On process restart, current S1 pending OAuth/revocation states and file-operation memory are lost. Persisted folder PENDING/UNCERTAIN must remain fail-closed. Root access depends on a fresh valid S1 connection and provider validation. Multi-JVM process coordination is out of scope; actual one-JVM deployment remains NOT_VERIFIED and live enablement separately gated.

## PH-02: creation-provenance proof, not a file-name convention

The root's provenance is **the durable U-specific binding (`root_file_id`, `root_binding_id`, `binding_epoch`) AND provider-echoed `appProperties` (`ppvKind=root`, `ppvRootBinding`, `ppvCreatedId`) AND actual My Drive parent/type/trashed fields under U's credential**. None is optional. A different folder with the same name or copied markers but a different provider ID is denied. The marker carries no Google subject/email; S1 owns subject verification. The root's random binding value is different for U and V and survives U's local disconnect.

Every file created by PPV in S2 must carry **`ppvKind=file`, `ppvRootBinding=<the root's UUID>`, `ppvCreatedId=<its pre-generated provider file ID>`, `ppvUploadAction=<digest of the stable caller Idempotency-Key>`**, in its `appProperties` at creation. For any file shown/downloaded (and for upload reconciliation), require fresh metadata `id,name,mimeType,size,modifiedTime,parents,trashed,appProperties` plus `md5Checksum` when reconciling original bytes. Reject if any required `appProperties` field is absent/mismatched, `ppvCreatedId != id`, `ppvRootBinding != current U-root binding`, file parent is not exactly current root, native/shortcut/folder type, trash, malformed metadata, or U's S1 authority is stale. A Google `File` resource has **no trusted `google_sub` field**: use the current verified S1 credential/subject and the root-bound private proof. The public list/download DTO exposes **none** of these internal markers.

A previously PPV-created U file placed under V's root still has U's `ppvRootBinding` and fails under V, even if the same OAuth project can read both objects. A manual external file or manually copied Google Drive file without matching identity-bound creation metadata also fails. `appProperties` are private *to this app*, but **not** a replacement for subject/epoch/root-parent/file-ID checks; assume only this trusted backend writes PPV marker keys. Do not claim cryptographic provider attestation.

## Minimum deterministic negative tests

- Concurrent first ensure from same account/slot and cross-slot reconnect: only one binding/provider identity, no duplicate root on late/ambiguous response.
- Same sub U disconnect/reconnect into different slot: previous root reused after verification; subject V cannot access or replace it.
- Wrong root type, deleted, moved, missing/mismatched mandatory `appProperties` (including `ppvCreatedId`), missing Google authority, external name collision and provider `404/403/429/5xx`: no folder substitution or unbounded requests.
- Disconnect or epoch refresh while create in flight: no successful local root authority if S1 authority changed; reconcile leaked/unknown remote folder without claiming rollback.
