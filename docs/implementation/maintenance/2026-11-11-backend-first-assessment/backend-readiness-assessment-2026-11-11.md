## 6. Prioritized next slice — proposal only

**Proposed ID:** `BF26-V1-RECYCLE-BROWSE` — **one authenticated, read-only Vault Recycle Bin collection endpoint**. Objective: discover deleted Vault identities and use the existing restore API without remembering IDs. This completes part of an existing blueprint capability with one owning module and no new dependency edge.

| Option | Work / benefit / tradeoff | Recommendation |
| --- | --- | --- |
| Continue existing APIs only | Zero source changes; restore works if IDs were retained, but no trash discoverability | Valid if Owner does not need browsing yet |
| Vault trash browse | One additive read query/public operation/DTO/controller path; focused PostgreSQL + HTTP tests; no new deps/table/module | **Recommended smallest useful implementation**, subject to explicit Owner scope/frozen-boundary approval |
| Dashboard aggregate first | Useful only after choosing cards, privacy, freshness and limits; existing Inbox/Radar/due APIs cover much already; new aggregate adds orchestration | Next broader planning option, not assumed necessary or authorized |

### Proposed contract and acceptance criteria

These criteria are **not an executable handoff** and do not amend accepted contracts until Owner selects the scope.

1. Add `GET /api/v1/vault/trash?limit=…&cursor=…` in the existing Vault owner. Return the existing `ApiResponse` with a page of **identity metadata only**: ID, entry type and deletion timestamp; optional created/updated timestamps only if reusing `VaultEntryView` is simpler. No content, titles, Private/NSFW details, tokens, credentials or cross-module enrichment. An identity-only page is intentionally less convenient than a fully titled trash UI; Owner must accept that tradeoff before implementation.
2. Return only `deleted_at IS NOT NULL`; default limit 25, valid range 1–100. Use `id DESC` keyset traversal and fetch at most `limit + 1` rows per page. ID order avoids a new composite timestamp index; it is **not deletion-time order**. Cursor must be bounded and versioned, with deterministic malformed/unsupported handling; no offsets, total count or whole-table in-memory filtering. Explicitly document weak consistency across concurrent trash/restore; no cross-request snapshot or exactly-once traversal promise.
3. With more than two pages of mixed active/deleted entries, traverse all matching entry types in strict stable order with no duplicates/skips **when membership is unchanged**; empty/exhausted pages have no next cursor. Restoring an item excludes it from subsequent reads; retrashing preserves existing mutation semantics. Concurrent changes do not cause unbounded replay or mutation by a read.
4. Unauthenticated/expired bearer gives the canonical 401; authenticated reads return DTOs only. Validate limits/cursors through existing canonical error handling. Metadata-only output must not bypass any existing accepted authorization rule; no new private-PIN model or credentials in cursors/logs.
5. GET has zero writes, provider requests, new jobs or RAG calls. Keep trash/restore idempotence, metadata retention, source-edit/reservation guards and race behavior unchanged. Existing active-only search continues to exclude trash. No permanent deletion, purge, cascade policy or frontend behavior in this slice.
6. Verify with real PostgreSQL repository tests and HTTP tests for page boundaries, malformed cursor/limit, auth failure, restore-between-pages and no-write behavior; reuse accepted lifecycle/concurrency tests and run relevant Modulith/API inventory/OpenAPI checks. Run only focused suites necessary for changed behavior; no full frontend/RAG/QA/model gate. Test execution requires the future handoff and bounded runner; this assessment runs none.
7. No Flyway/schema/DBML change expected: existing `vault_entries` ID and `deleted_at` are sufficient for the proposed bounded query. Selectivity/large-trash query cost is **not measured**. Inspect the actual plan on representative synthetic data during the future slice; if an additional index or changed ordering is necessary, STOP for separate approved schema/contract impact rather than silently adding it.

**Expected edit boundary:** Vault `entry` public API, internal repository/read service, response/mapper/controller, owning tests, affected API docs/manifest and scoped delivery records. No frontend, auth/security policy, Drive, Feed, Finance, RAG, frozen evidence, new module or build dependency. No title-enrichment calls into feature modules. If preparation finds an existing equivalent route or an unmet authorization invariant, revise/stop the proposal before implementation.

**Effort estimate (not a commitment):** one bounded slice, roughly 6–10 production source files plus 2–4 test/docs/API-inventory files depending on record reuse. Main uncertainty is current API-inventory coupling and read-query cost, not algorithmic complexity. Prefer existing validation/paging conventions where equivalent; do not introduce a shared cursor framework merely for this endpoint.
