## Reviewed source risks and concrete adjudications needed

- **R1 / PH-02 — False off-state or cross-module registration:** a source's scheduled flag already exists in DB, but global OFF must prevent the **Feed-private** timer from existing/registering and any automatic network work. Global ON must **not** import `@EnableScheduling` and activate existing RAG `@Scheduled` reconciliation. Spring `@EnableScheduling` scans all managed beans in that context, not just a conditional Feed package. Verify actual annotation-processor absence/negative effects and timer lifecycle with ON/OFF fake Spring-context tests.
- **R2 / PH-01 — Starvation:** the current public null-first due query is not the scheduler query. The initial `(nextFetchAt,id)` rotating keyset was **rejected** by the reviewer's all-success 30-source trace (26 never attempted). **Propose** scheduler-only `ORDER BY id ASC` with `id > lastExaminedId`, 20-row page, last-*examined* advancement and two-invocation cap. On empty page, wrap next tick. Compare both all-success and five-failure/two-busy scenarios on real PostgreSQL; no new table or public API ordering change.
- **R3 — Wrong transaction authority:** both provider services internally own admission and both finalizers only check provider source authority, not the scheduling flag. Avoid duplicate admission, stale scheduled commit and transaction-proxy bypass; assert real PG PID/XID identity and lock through commit.
- **R4 — Source disable and interval edit races:** source CRUD uses `findByIdForUpdate`; after the HTTP wait, a scheduled-only finalizer must observe the actual latest row. Specify handling if interval edit moves the next due time into the future; an already admitted scheduled refresh may finish while scheduling stays enabled, then recompute next due using the authoritative updated interval. No mutation of accepted manual behavior.
- **R5 — Repeated failure:** source next due remains due after failed provider attempt; bounded scheduler-local retry delay is needed without touching committed fetch-success timestamps. Restart loses backoff, explicitly accepted limitation for single process.
- **R6 — Shutdown and resource ownership:** async worker pool is not automatically needed; favor serial bounded processing, full callback lifetime ownership, no worker runaway/leaks.
- **R7 — Process topology, OWNER_CONFIRMED_A / DEPLOYMENT_NOT_VERIFIED:** On 2026-11-05 Owner explicitly chose **A: only one active backend JVM**. This closes the *Owner-choice gap*, not the future deployment-verification gate. If runtime or deployment instructions permit overlapping active JVMs (including rolling-restart overlap), STOP; separate coordination would require a newly authorized scope. Do not claim distributed at-most-once from local admission.
- **R8 — Source preservation:** S1/S2A own HN/RSS URI/DNS/HTTPS, fixed targets, XML and provider limits. Scheduler cannot weaken them, add unapproved egress, broaden URL config validation or alter `GET /sources/due` or Radar contract.

## Scope verification and historical limitations

From inspected source, the bootstrap has only `@SpringBootApplication`; the scheduler is not present in Feed inventory. Existing application YAML has no scheduler enable flag; that flag is **new/proposed**. S2A was accepted without an active timer, and its review limits (no public provider smoke or whole-system certification) remain. Spring documents [application-context-wide `@EnableScheduling` annotation discovery](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/annotation/EnableScheduling.html) and [programmatic `TaskScheduler.scheduleWithFixedDelay(Runnable, Instant, Duration)`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/TaskScheduler.html). This validates API availability in current reference material, **not** S2B implementation, deployed topology or exact pinned binary verification.

Review should inspect root/scoped `AGENTS.md`, applicable repo skills and the current owner policy; package/module structure, test harness, OpenAPI inventory, actual Docker/boot deployment instructions, context-startup auto-work and any existing @Scheduled components. Name unsupported assumptions. Do not rewrite accepted S1/S2A reports, decrement historical counters or infer a project-wide audit.
