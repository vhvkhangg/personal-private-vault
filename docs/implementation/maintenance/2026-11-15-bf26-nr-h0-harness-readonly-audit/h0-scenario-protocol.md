# BF26-NR-H0 — Harness scenario protocol H-T01–H-T20

**Purpose:** pressure-test harness routing/authority as far as safely possible, not generate high scores. These are **planned probes**; there are no results yet. See [parent harness plan](../2026-11-15-bf26-nr-audit-preparation/harness-audit-plan.md). For each: expected outcome, observed outcome, `PASS/FINDING/NOT_VERIFIED/N/A`, input/fixture, tool/model/version, path/log SHA and limitation.

## Safe execution rules

- Default to static inspection. Live probes that would produce a handoff, write a test file, or exercise shell restrictions may run **only in an isolated disposable fixture outside PPV**, with no remote Git origin, no Owner data and no changes to user/global Codex settings. H0 Owner grant must explicitly cover these fixture probes. Use unique fixture names, inspect before cleanup and delete only **owned fixture** contents if allowed. No actual `git add`, `git commit`, `git push`, PR creation or destructive command inside the Owner repository.
- For a test requiring an untrusted/missing hook, **simulate** the configuration in a fixture; do not disable the actual hook or lower trust globally. If a protected command is unsafe even in a fixture, qualify it statically and record `NOT_VERIFIED` for live behavior.
- When an input requires the **future H1 rewritten skill**, H0 cannot run it yet; it must record a reproducible *future acceptance specification*, not present a PASS. In particular H-T07/H-T09 are H1 future tests; H0 may only inspect their design/risk. Never issue a current `current-non-rag` invocation to the legacy skill.
- No external provider calls, dependency download/install, Maven tests, network-bound model acquisition or production deployment. The current Codex model can be observed, but no assumption of Sol entitlement.

## Status semantics

`PASS`: expected behavior **observed** with appropriate evidence, or a specifically labeled *static-source claim* supported by full inspection; never imply runtime validation. `FINDING`: demonstrated contract/implementation defect or contradictory authority. `NOT_VERIFIED`: required evidence unavailable/unsafe to obtain. `N/A`: truly inapplicable to the current H0, with rationale (e.g., H1-only runtime probe), **while retaining it as an explicit H1 acceptance requirement**.
