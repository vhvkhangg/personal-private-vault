## D1 — Safe first slice and fixed Public surface

**Owner-ratified prospective choice:** deployable **DP-A** has working `PUBLIC` login/downgrade and `PRIVATE` login/elevation, but PUBLIC is authorized only for **the expressly enumerated Auth/profile operations**. The Spring request/servlet-security boundary must deny **every** business/data operation to PUBLIC, even though the old application is otherwise `authenticated()` by default. This includes direct IDs, GET/POST/PUT/DELETE, upload/stream/download, export, administrative, provider callback/handoff-to-data paths, unknown business routes, unexpected framework dispatches, and applicable async/ERROR redispatch. Private retains accepted operations/feature gates. No `permitAll` catchall; avoid accidentally applying the public business deny to legitimate unauthenticated bootstrap or approved prelogin paths. `PUBLIC` login and downgrade **must be tested as real signed tokens** before A is accepted. Opening data routes is B1/B2 work after independent acceptance.

**Owner-ratified eventual module policy (still requires exact route/field independent review before any Public grant):**

No arbitrary `visibility` field per record and no user-scoped partitions. This conservative first-release policy restricts **some otherwise shared features** for Public; it does not change shared data ownership. Any wider Public capability must be **explicitly selected as a later B2 (or separate) grant**, not inferred because it exists for PRIVATE. The existing singleton BF26-S5 Dashboard Readiness is **not** Public-profile certification.

**Field/reference rule for mixed Film/Fiction:** Public owner-local projections must not disclose unqualified `authorPersonId`, `authorGroupId`, credit `personId`, private `posterUrl`, personally identifying free-text notes, private tags, hidden parent/child IDs or dependent existence. Until the owner of each referenced resource can provide a safe public projection **without cross-module private-repository access**, omit fields in a deliberately defined compatible Public DTO/projection or **deny that Public representation**; do not silently return the existing full DTO. Film credits and nested relations are **denied for Public in B1**, including direct credit ID, until B2 proves parent gating. B1 may provide bounded read-only non-NSFW detail; Public creates/updates and reclassification are deferred to B2, where IDs/genres/author references and mutation semantics must be explicitly approved. Proposed initial safe Public fields: Fiction/Film `id`, `title`, `isNsfw=false`, and only independently qualified non-sensitive type/status fields. `description`, `review`, `posterUrl`, creator/credit IDs and nested link content are **not** automatically public just because the parent is non-NSFW. Known hidden ID and absent ID return an indistinguishable 404; whole-module authenticated-but-forbidden is 403 (401 unauthenticated), with the canonical JSON envelope and no resource-shaped error differences.

**Taxonomy/mutations:** Public cannot create/rename shared global tags, probe hidden tag IDs, attach/detach tags or mutate genre/creator/credit relationships until an owner-safe mutation path is independently accepted. Static Reference GET only is a B1 candidate; Reference writes remain PRIVATE. Do not add a reverse Vault→Fiction/Film Java dependency, a general visibility schema, a shared authorization module or unapproved cross-owner SQL. Search/Vault must qualify source ownership before ranking/offset/hasMore; until such a contract is approved, deny.

## D2 — Credentials, identifiers, bootstrapping and changes

**Owner-ratified prospective choice:** exactly one `AppUser(id=1)` and one owner dataset. Existing `POST /api/v1/auth/login` retains username-or-email + existing Owner password and yields a **PRIVATE** session after cutover. It is not implicitly callable with Public credential. A new explicit `POST /api/v1/auth/profiles/login` accepts `profile=PUBLIC` and its separately configured Public password (no username required for the fixed Public identity); either restrict a `PRIVATE` branch here or reject it as duplicate of the legacy Private login. Exact DTO, validation and operation IDs to be frozen before executable handoff. Successful Public/Private responses retain existing token envelope, with additive non-secret profile metadata only if proven needed. No second `app_users` row or general registration. The existing bootstrapping contract remains one-time and creates the singleton Owner as before.

Public password is configured/reset only in a PRIVATE authenticated session **with a fresh Private password check** and must be distinct from the current Private password. Use the existing `PasswordEncoder` matching/hashing, no secret seed, default password, plaintext persistence or password hint/oracle. A future change of either password must re-check inequality against the other credential and invalidate affected sessions/refresh lineages. No new forgotten-Private-password or self-service recovery service is authorized; the Owner retains external secure operator recovery. If Public credential is unconfigured, login/downgrade **fails closed without changing the existing PRIVATE session** (otherwise a nominal 'switch' creates an unusable state). Distinguish credential-unconfigured in authenticated owner management only; anonymous login failures remain indistinguishable.

## D3 — Per-device authority and exact switch/race policy

**Owner-ratified prospective choice:** persistent **per-login-lineage** authority, not a global switch. Each profile-bound JWT contains `sub=1`, `profile`, unguessable session/lineage identifier and monotonic generation. Each protected request validates signature/issuer/expiry plus a current persisted session/profile/generation; DB lookup failure, session expiry, revoked/old generation or missing claims => deny, not legacy full Owner access. Existing JWT access TTL and refresh TTL are preserved, with **no newly invented server idle timeout**; the historical `private_mode_auto_lock_minutes`/PIN contract is not reinterpreted as a server session TTL. Logout revokes this one lineage; other devices and logins remain unchanged. No global-revoke endpoint for this slice.

`PRIVATE -> PUBLIC` requires no password, but requires a *configured Public credential* and a valid current Private lineage; transactionally advance generation, revoke predecessor refresh lineage and issue replacement Public tokens. `PUBLIC -> PRIVATE` requires fresh verification of the existing Private password inside the same authoritative Spring transition. Failed/expired/raced switch leaves existing lineage/profile unchanged and yields no replacement privilege. Same-profile switch is rejected as 409 (no new token) unless subsequent contract review proves a strictly equivalent simpler behavior.

**Lock order proposal:** inspect token hash and resolve lineage without conferring authority, lock **session lineage first**, then refresh predecessor inside one PostgreSQL transaction, re-check all hashes/generation/profile/expiry, rotate/create successors, advance generation and commit. Any refresh/rotate/logout/switch/pw-reset of a lineage uses this order; two racing writes cannot both commit incompatible authority. A delivered switch response whose server commit succeeded is authoritative: repeating the same consumed-generation switch without a new authenticated session fails; a lost reply may require re-login, not a server-side replay acceptance. Late refresh/Google result may not replace a newer authority. Session record always has bounded expiry; exact time fields, integer overflow and row constraints require migration design review, not a generic expiry promise.

**In-flight boundary (explicit trade-off):** after switch transaction commit, **newly admitted requests** with old Private JWT must be denied at the server filter, including async redispatch; requests **already admitted before commit** may complete their current read/write/stream or deliver previously buffered bytes. We do not promise retroactive withdrawal or a global write-transaction rollback on every module. Future accepted BFF integration must cancel/drop late Private results and purge cache across tabs; this Backend preparation **does not claim** that the paused BFF has implemented it. The Owner explicitly accepted this bounded race model in D3; stronger guarantees would require a wider per-resource commit/stream fence and separate scope.

## D4 — Google identity, Drive and paused BFF

**Owner-ratified prospective choice:** Google Sign-In and Drive flags remain default OFF. DP-A must not issue an **unprofiled** session or silently map Google success to PRIVATE if the existing Google flag is enabled by operator configuration. First rollout's **explicit temporary compatibility change**: Google start/handoff issuance routes fail closed with a stable canonical error while Google mapping is not approved; no irreversible success ticket is consumed to mint an unusable role. Preserve immutable issuer+sub Owner link and the separately authorized password-verified link protocol, PKCE/state/nonce/one-use proof; do not modify Google identity or Drive slot ownership. This is an Owner-ratified prospective change from H1-AUTH enabled-mode behavior; the exact frozen-source delta still needs separate bounded approval and a focused enabled-flag negative regression; it cannot be justified merely by the default-OFF flag.

Future Google login may map **at most PUBLIC** only after a separate, independently accepted mapping and Public credential configuration; elevation to PRIVATE still requires the Private password. Browser session/cookie/cache/SID/CSRF/Host/Origin/multi-tab migration is deferred while H1-F is paused and does not become an Auth backend acceptance claim. No forced provider activation or real Cloud tests in A.

## D5 — Schema, Portability, legacy tokens and backup/restore

**Owner-ratified prospective choice:** new additive Flyway migration **after actual current tip V28**; no V1–V28 rewrites. Owner-bound distinct Public password hash, revocable per-lineage session/generation and refresh-session binding, constrained by `owner_id=1`, referential integrity/uniqueness/checks, timestamps and configured state. Do not hard-code SQL secrets. Exact column names/DDL, transitional nullability, old-row handling and order must be submitted as a **prospective** DBML/ADR/API addendum for separate Owner frozen-baseline authorization. Keep `app_users.id=1`, `password_hash`, `pin_hash` and existing domain foreign keys unchanged.

**Atomic same-slice Portability consequence:** DP-A that adds public-schema security tables **must also edit `PortabilitySnapshotAdapter.EXCLUDED_SECURITY_TABLES` and its focused integration/schema-inventory tests within the same deployable slice**. Without this, the existing strict export preflight rejects unexpected new tables; A must demonstrate Private ZIP export succeeds and the added security rows, password hashes, session generations and refresh secrets are absent from ZIP/manifest payload and ZIP inventories as designed.

**Separate backup scopes:** Portable ZIP is an application-data transfer and **excludes** security tables/creds. Restricted **full PostgreSQL disaster-recovery backup** retains necessary authentication/security tables and encrypted/host-protected external secrets under the existing operational policy; it is not the portable ZIP. Do **not** silently omit security tables from full DB backups or claim current automated backup exists. A real restore must invalidate all restored session/refresh authority and rotate the JWT signing key **before the app becomes externally reachable**, with controlled Private credential recovery. No stored old tokens become valid through an old-backup restore. Document operator runbook; do not build a backup orchestrator. Never automatically backfill old `refresh_tokens` as PRIVATE: revoke/deactivate legacy unbound refresh and reject all unprofiled access JWT at cutover, even if cryptographically valid. Plan a controlled single-node cutover; no permissive binary rollback against migrated DB.

## D6 — PIN, deferred work, harness and delivery

**Owner-ratified prospective choice:** preserve non-null `app_users.pin_hash`, existing protected PIN verify/change endpoints and `private_mode_auto_lock_minutes`. PIN endpoints are available **only to PRIVATE**, never PUBLIC; the PIN result is not an access-profile or elevation credential. No PIN retirement, field removal, automatic server idle-lock or password recovery/global-revoke module in DP-A. The future permanent replacement of old PIN UX/behavior is a **separate proposed cleanup** after accepted dual-profile equivalence and separately approved migration. Keep normal Google/Drive/Feed flags OFF and S19-2/indexing inactive; no Frontend/BFF changes, no RAG inference, no Recycle Bin implementation and no Final Audit in this preparation.

Reuse JUnit/MockMvc/PostgreSQL Testcontainers/Modulith/OpenAPI/fixed runner; change existing tests that mint unprofiled tokens **within scoped fixture edit boundary**, never add a blanket security bypass or accept synthetic profiles without persisted authority. Antigravity implements and self-reviews only after approved handoff; separate Codex independent reviews. All old counters preserved; 0 new remediation/takeover rounds. Only Owner stages, commits and pushes reviewed work.
