# BF26-DP — recommended Authentication, session, schema and compatibility design

## Ratified design precedence — PH-01/03 closed at preparation; PH-04 correction pending independent review

Refer to [D2–D6 ratification](owner-ratification-d1-d6-2026-11-11.md) and the [exact DP-A Auth matcher/session lifecycle contract](auth-compatibility-and-session-lifecycle-2026-11-11.md). **The original conceptual options below are superseded by the Owner-ratified corrective contract wherever they conflict.** This is planning, not authority to create V29 or change accepted Auth/Google behavior.

1. **First deployable slice A is safe by itself:** any `PUBLIC` JWT from direct login or PRIVATE→PUBLIC downgrade is denied all data/business routes at the authoritative Spring security boundary, including unknown/async redispatch. The only Public operations are exact explicitly approved Authentication/profile routes. That must hold on the real filter chain while `anyRequest().authenticated()` would otherwise accept a signed Public JWT. Business guards/grants remain later B1/B2; never ship a `PUBLIC` token issuer while generic authenticated routes can return Private data.
2. **Portability is part of A:** new security tables must be added to `EXCLUDED_SECURITY_TABLES` and its strict unknown-table integration tests at the same time as Flyway migration; verify Private ZIP works and no secrets/session rows leak. This exclusion is **only for portable ZIP**, not restricted full PostgreSQL backup. Full DB recovery retains necessary auth tables and requires pre-exposure revocation of restored lineages and JWT signing key rotation; manual operator runbook, not new backup automation.
3. **Compatibility selected for preparation:** legacy `/api/v1/auth/login` remains Private with existing username/email/password; explicit profile route handles Public credential. All new access JWTs have profile/session/generation; old unprofiled JWTs and unbound refresh tokens fail closed at cutover. Public credential starts unconfigured; downgrade cannot proceed in that state and leaves Private active. Session switching is per lineage, other devices unchanged. JWT TTL/refresh TTL unchanged; **persisted authority expiry tracks the latest current refresh-token expiry, rolling on successful rotation/switch with no fixed first-login cap or new idle timer**. Public password reset is mandatory and invalidates Public-associated lineages by an epoch fence; a rotated predecessor revoke never invalidates its successor. Existing PIN APIs Private-only, no PIN elevation and no immediate schema removal.
4. **Race outcome:** acquire per-lineage lock first, then predecessor refresh lock; recheck current generation/profile/token within one PostgreSQL transaction. Failed switch leaves previous lineage valid; committed-but-lost reply requires new login rather than replaying old authority. New requests after switch commit deny old generation; pre-admitted requests may complete/finish buffered content, with no claim of retroactive rollback. BFF purge/cancellation is deferred to separately authorized frontend integration.
5. **Google:** preserve immutable Owner issuer+sub and one-use OIDC records; flag OFF by default. If toggled ON without mapping, LOGIN start fails with `503 GOOGLE_SIGNIN_UNAVAILABLE`; PRIVATE password-proved LINK initiation and its validated callback may preserve/create the one-time immutable Owner binding, but handoff rejects before ticket consumption/token issuance. LOGIN callbacks fail via fixed 303/cookie clearing; LINK callbacks retain fixed 303 and one-use proof. No PPV session is issued by Google before a separately approved mapping. This is the Owner-ratified **temporary enabled-mode alteration of accepted H1-AUTH**, needing separately authorized implementation and focused tests. Future Google login at most Public before password elevation, not automatic Private. Preserve Drive slots and no live Google tests.

**This supersedes original sequencing saying “Add Public/Private authorization checks only after login/refresh/switch invariants”: request-boundary DENY must be in slice A simultaneously with Public issuance.** D1–D6 are ratified for preparation; exact implementation contracts and any frozen-baseline modifications still require separate review/authorization.


**Status:** `TECHNICAL_PROPOSAL / NOT_AN_APPROVED_MIGRATION_OR_ENDPOINT`. The following is the smallest *currently recommended* approach for the Owner's chosen behavior. Exact column names, endpoint additions, auth mapping and roll-forward deployment require a separate frozen-boundary approval following independent review.

## Identity, credential and session model

| Layer | Current accepted shape | Recommended prospective shape |
| --- | --- | --- |
| Data Owner | `app_users.id=1` singleton, referenced by refresh/Google | **KEEP** `app_users.id=1` as only data Owner; no second `AppUser` row or tenant/user FK change |
| PRIVATE credential | `app_users.password_hash` | **KEEP** as authoritative Private password; secure password verify remains Spring-owned |
| PUBLIC credential | None | **ADD** one singleton Owner-bound *distinct* Public password hash with `configured/enabled` state; created/reset only after Private password verification; no plaintext/default password seed |
| Access identity | JWT `sub="1"`, no profile | **KEEP** `sub="1"`; **ADD** explicit `profile=PUBLIC|PRIVATE`, session ID and generation/version; reject missing/invalid/ambiguous claims after cutover |
| Refresh authorization | `refresh_tokens.user_id=1`, hashed token, transactional rotate/revoke | **ADD** binding to the server-side session/profile/generation; refresh never upgrades scope, replays old profile or resurrects revoked lineage |
| Server session | No DB-backed authorization state for a JWT's current privilege | **ADD** minimal Owner-bound, revocable login-session record; validate current profile/generation on **every protected request**, including direct API calls |
| Browser BFF | H1-F process-local `AUTHENTICATED`/`SETUP_ONLY`, volatile token fields | **DEFER** integration because H1-F paused. Do not rely on BFF-only session invalidation for Backend security |

**Why server-backed check is mandatory:** a normally signed/valid stateless JWT issued while Private would remain usable until expiration even if the UI switches to Public. Revoking a refresh token alone does not revoke that access JWT. Any implementation that only adds JWT `profile` claims or BFF state fails the Owner's immediate-downgrade requirement.

### Suggested tables (conceptual, not executable SQL)

- `ppv_public_login_credential`: unique `owner_id=1` FK, hashed public password, configured/enabled status and update timestamps; no duplicate Private hash, hardcoded default credentials or registration.
- `ppv_login_sessions`: unguessable session ID (do not use token itself as DB key), `owner_id=1`, `active_profile`, monotonically increasing generation, created/last-change/expiry/revocation timestamps. **No newly invented server idle timer;** retain existing JWT/refresh lifetimes until independently approved otherwise. If bounded session count/reaping is needed, use explicit conservative limits from existing deployment context; do not invent a distributed session service.
- `refresh_tokens`: additive session binding and/or required profile lineage columns after compatibility cutover; transactional rotation/revocation should lock the appropriate session lineage to prevent downgrade/refresh races. If compatibility requires a staging nullable column, define exact fail-closed transition and backfill; old tokens must not be defaulted to PRIVATE.
- Proposed next Flyway change **after V28** (e.g. V29, confirm version availability again at implementation entry); fresh additive DBML/ADR delta and Portability `EXCLUDED_SECURITY_TABLES` for every new security table. Do **not** alter historical V1/V28 migrations or claim the existing export recognizes new tables.

### One-time secure transition

1. Snapshot/test the real PostgreSQL **V28 baseline**, test rollback/restore on synthetic fixtures, inspect deployment status/feature flags. Do not run the migration in preparation.
2. Add the server-side schema in a future authorized migration. Current singleton `app_users` and hashed Owner password persist unchanged. Public credential remains **DISABLED/UNCONFIGURED** until a Private-authenticated, freshly password-verified setup action sets a distinct new password. A public credential must **never** be auto-copied from the Owner password, PIN, environment or migration seed.
3. Introduce explicit dual-profile auth/session contract under a controlled transition gate; define compatibility strategy for legacy `/api/v1/auth/login`, `/refresh`, `/revoke` and Google handoff. Recommended: legacy password login remains a **Private credential** emergency entry only under an explicit verified session contract. A new explicit profile-login endpoint distinguishes PUBLIC and PRIVATE.
4. Before enforcing profile authorization on business routes, reject unprofiled legacy JWTs (or transition them to a **strictly less privileged, explicitly reviewed** state); never silently treat `sub=1` as PRIVATE. Existing refresh tokens with no session binding must be **revoked/expired through a reviewed safe cutover**, not upgraded to PRIVATE. Avoid downtime surprise by an Owner-approved deployment window.
5. **In the SAME DP-A source slice as PUBLIC token issuance**, enforce the exact Public Auth-only allowlist and server-side DENY for **every** business/data/unclassified/async-dispatch route. DP-B1/B2 may subsequently authorize independently reviewed data routes. If a module is unclassified, Public access remains forbidden; never use the old `authenticated()` predicate as authorization.
6. Preserve `pin_hash NOT NULL`, existing PIN APIs and `private_mode_auto_lock_minutes` until an independently approved *later* cleanup replaces their privacy purpose without removing a separate accepted control. PIN must **not** be accepted as Private elevation after profile mode enforcement.
7. Operational rollback is **restore/redeploy of a compatible independently reviewed state**, not blindly undoing an applied Flyway migration. Downgrading binaries while leaving new security tokens active is unsafe; define token revocation, DB backup recovery and rollout order in executable handoff.

## Exact DP-A Authentication and session contract (reviewable proposal, not source)

The previously unresolved state-machine and API sketch have been replaced by the [method-specific matcher/compatibility and persisted-session lifecycle tables](auth-compatibility-and-session-lifecycle-2026-11-11.md). That contract is the controlling **prospective** DP-A design for:

- Legacy `POST /api/v1/auth/login` preserves **required** `{identifier,password}` for PRIVATE Owner username/email/password login. Distinct `POST /api/v1/auth/profiles/login` is PUBLIC-only with **exact** `{profile:"PUBLIC",password}` and **no username/email/identifier**: resolve the fixed singleton Owner on the server, verify only the separately configured PUBLIC hash, and issue PUBLIC tokens. No PRIVATE branch or fallback on the new route. Incorrect/unconfigured PUBLIC password => indistinguishable `401`; unknown `identifier` field on this new DTO => `400`, never an extra authentication factor. Existing anonymous JSON-body `/refresh` and `/revoke` signatures remain unchanged.
- PRIVATE-authenticated Public credential setup **and reset**, with fresh Private password proof; Public→Private fresh password elevation and Private→Public password-free downgrade; PIN Private-only.
- Active refresh revoke invalidates the **current persisted lineage**; old consumed/rotated token revoke remains idempotent **without** invalidating its successor. Refresh preserves profile/generation and advances session authority expiry with its rolling refresh-token lifetime.
- Access/session expiry, Public credential-reset epoch (including currently PRIVATE lineages that previously issued PUBLIC), lock/recheck ordering, stale legacy tokens, lost switch replies and the D3 already-admitted-operation boundary.
- Exact anonymous/existing/flagged Google/Drive/health/docs request matchers and selected new `ApiResponse` error semantics. No wildcard `/api/v1/auth/**` or Public business access.

**Only this concrete first-slice contract is selected for independent preparation review.** It does not pre-authorize new endpoints, schema, frozen contract edits, implementation, H1-F or live provider activation. Any contradiction in earlier unimplemented options is superseded by the linked tables; preserve historical records as review checkpoints.

## Google Sign-In, Drive, offline RAG and frontend integration

- Existing Google identity binds **issuer+subject to one Owner**, not to an arbitrary login profile. Preserve immutable binding, PKCE/state/nonce/one-use ticket and refresh transaction semantics. **Never mint `PRIVATE` merely because Google login succeeded.** The Google feature is normal-default OFF. At DP-A ON/unmapped, LOGIN start rejects without new attempt, whereas freshly password-verified PRIVATE LINK start/callback retain immutable Owner binding and one-use proof. LOGIN callback fails with fixed 303/cookie clear; LINK callback may complete binding and issue its opaque ticket but **cannot** mint PPV access/refresh. All unmapped handoff redemption rejects before consuming the ticket or issuing a token. Existing Owner issuer/sub link remains immutable. Future separately approved mapping can issue at most PUBLIC, followed by fresh Private password elevation. Do not relax existing Google link-start password proof.
- Two Google Drive **connection slots** remain separate from the two PPV login profiles. If classified Private, both provider slots must reject Public even with a known file ID; do not change provider consent, identity or stored credentials.
- RAG remains at accepted P17/P18/S19-1 only, indexing INACTIVE and S19-2 SUSPENDED/ARCHIVAL_ONLY. Do not treat the Private PPV profile as permission to ingest NSFW/private sources in violation of frozen RAG consent/source-scope rules.
- Next/BFF stays `FRONTEND_PAUSED_BY_OWNER`. Future separately approved Frontend integration must rotate SID/CSRF, cancel stale tasks, clear prefetch/cache, show explicit profile, and never install stale refresh/handoff responses after switch. Frontend tests are a future gate, not an excuse to modify H1-F now.

## Compatibility and verifiability gates

- SecurityFilter must derive authority from **validated session state** rather than trusting any client `profile` parameter/JWT role alone. Failing session lookup/DB outages must fail closed. Prevent replay of a previous `generation` with a valid HS256 signature. Avoid locking DB rows across network/stream I/O.
- Existing Google, Drive, Portability, Search, RAG and HTTP source/test contract owners must be consulted; update named module contracts/ADR/DBML **only with authorization**. The old singleton Owner identifier and stored data are invariant.
- The new `ppv_public_login_credential` and `ppv_login_sessions` are security tables: exclude from export and general data search; ensure no raw tokens/private passwords/hashed secrets appear in logs/DTO/error messages. If a retention/cleanup job is necessary, scope/test it rather than inventing a shared scheduler.
- Security posture is **password-based profile separation**, not encryption-at-rest isolation or defense against an attacker who already controls the full Owner machine/DB. Document realistic threat boundaries, not unachievable secrecy.
