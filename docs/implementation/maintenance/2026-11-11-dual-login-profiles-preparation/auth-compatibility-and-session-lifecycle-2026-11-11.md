## 1. Authentication matcher and wire-compatibility table (proposed DP-A)

**Legend:** `ANON` = no bearer; `PUB`/`PRI` = a valid, non-expired bearer whose **signed profile, persisted session, current generation and credential epoch** all agree. `Yes` means matcher permits reaching the handler, **not** that request validation or the intended authentication proof is waived. The current JSON response envelope remains `ApiResponse<T>` with `data`/`error`/`meta`; existing Google callback remains the **303 redirect exception**. Error codes prefixed `(new)` are proposed new stable codes for implementation review, **not current source facts**.

**Auth error precedence:** malformed authenticated-route body = 400 only after route-level authentication/authorization; anonymous or invalid session on protected route = 401; valid PUBLIC on a PRIVATE-only route = 403; wrong live profile for a profile-specific action = 403; wrong credential = 401 with no profile/credential-existence oracle. Preserve existing `AUTH_INVALID_REFRESH_TOKEN`, `AUTH_INVALID_CREDENTIALS`, `AUTH_ALREADY_BOOTSTRAPPED`, PIN codes and redaction. New codes above need owning Auth advice/OpenAPI review. JSON Auth failures return the normal redacted `ApiResponse` error. No blanket `/api/v1/auth/**` permit matcher.

**Infrastructure exemptions, separate from business/data authorization:** retain *only* the existing anonymous `GET/other` health and Swagger/OpenAPI matchers (`/actuator/health`, `/actuator/health/**`, `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`) as currently configured. Retain **exact `GET /api/v1/drive/oauth/callback` only with Drive enabled**, subject to its existing state/cookie protections; it does not confer Public Drive access and does not return Drive data. Google conditional exemptions are exactly the three `POST start`, `GET callback`, `POST handoff` above, never `link/start`. For every other route: ANON unauthenticated = 401; PUB = **403 default-deny for all business/data routes**, including unknown/unclassified/async and ERROR redispatch, with no bodies/bytes/side effects; PRI uses the preexisting legitimate handler contract (unknown route remains 404). No wildcards or accidental HEAD/OPTIONS bypass for PUBLIC. The 254 static route declarations are **not** all simultaneously registered; feature-flagged/dispatch/runtime tests remain future acceptance.

### PUBLIC fixed-login accepted-input example (future assertion, not executed)

```json
{"profile":"PUBLIC","password":"<configured-public-password>"}
```

The request deliberately contains **no** `identifier`. Login eligibility is based on the one fixed Owner's configured PUBLIC password hash; PRIVATE credential verification continues to require the historical `{identifier,password}` on `/api/v1/auth/login`. The new PUBLIC DTO must not silently reuse the legacy login DTO or infer PRIVATE permission from the singleton `sub`. This is a proposed API/fixture example, not an actual response or password value.

## 2. Persisted session lifetime, switches, reset and revoke (proposed DP-A)

**Existing-configured lifetimes, not new timers.** Let `A` = actual `ppv.security.jwt.access-token-lifetime` (source default **15 minutes**) and `R` = actual `ppv.security.jwt.refresh-token-lifetime` (source default **30 days**), both positive configuration values. At any successful **new login, refresh rotation or profile switch** that mints a refresh token at instant `t`:

- New access `exp = t + A`; new/current refresh `expiresAt = t + R` (as current successful rotation computes).
- Persisted session-authority `expiresAt = expiresAt of its current refresh token` (latest committed successor). **No separate absolute-from-first-login cap and no new server idle TTL**; successful rotation/switch advances this bound to `t + R`. Ordinary authenticated reads do **not** extend it. Without a valid refresh/rotation, the lineage expires at its current bound. The DB-backed session is denied at `now >= session.expiresAt`, or when revoked/epoch-invalid, **even if a presented signed JWT is otherwise unexpired**.
- The currently accepted token TTL **configuration and rolling refresh semantics are preserved**. There is no promise of a 30-day maximum absolute session age or a background idle cleanup job. Cleanup of expired rows is operationally optional and cannot change admission semantics.

**Authority:** each JWT contains immutable `sub="1"`, `profile`, random session/lineage ID, generation and `exp` (not secret raw refresh); signed claims must equal persisted, unrevoked session values on **every** admission. Refresh rows are hashed and bound to that lineage/profile and the current refresh pointer. Profile changes **increment generation** and replace access/refresh atomically; refresh rotations **do not increment generation** and cannot change profile. A lineage independently created on another device is unaffected by an ordinary switch or logout in this lineage.

**Credential reset epoch (no global revoke subsystem):** Public credential has one monotonically increasing version `publicCredentialEpoch`; every lineage that has **ever** issued PUBLIC credentials retains a non-null epoch snapshot, even after it has elevated back to PRIVATE. A PUBLIC password **reset** atomically increments the credential epoch and changes the hash. At every access/refresh/switch admission, any lineage holding a prior Public epoch is rejected (including a currently PRIVATE lineage that was previously PUBLIC); a current PRIVATE-only lineage with no Public history is unaffected. First setup initializes an epoch without existing Public lineages. The reset request's own PRIVATE lineage is also invalidated **if** it previously used PUBLIC; the caller then must re-login. This is a credential-change-specific multi-device invalidation, **not** a global profile switch. No raw password/epoch secret is exposed by a public route.

| Event/input and proof | Persisted lock/validation and exact state effect | Successful/failed reply and later authority |
| --- | --- | --- |
| Valid PRIVATE or configured PUBLIC password login | **PRIVATE legacy:** require and verify Owner username/email `identifier` plus Owner password on `/auth/login`. **PUBLIC fixed identity:** require only `profile:"PUBLIC"` and Public password on `/auth/profiles/login`, resolve the singleton Owner server-side with no identifier lookup. Create an independent profile-bound lineage at generation 1 with new pair/expiry | `200 AuthTokensResponse`; wrong/unconfigured PUBLIC password yields indistinguishable `401`. A lost initial response is **not** permission to replay token issuance; login again. |
| Valid current refresh, before expiry | Identify candidate lineage from stored token hash **without trusting it**; transaction locks lineage **first**, then candidate refresh/predecessor; verify active current token, generation, profile, Public epoch and time; rotate once, move refresh pointer, set `session.expiresAt=now+R`; **generation unchanged** | `200` same-profile pair. Replayed/rotated/legacy/unbound/expired predecessor => `401 AUTH_INVALID_REFRESH_TOKEN`; never revive session. |
| PRIVATE→PUBLIC when Public configured | Lock current lineage; validate current signed PRIVATE generation, profile, expiry and Public epoch state; mint PUBLIC pair and increment generation; set/retain Public epoch snapshot | `200` new PUBLIC pair. Old PRIVATE JWT invalid for **new admissions immediately after commit**; old refresh cannot rotate. Unconfigured => `409 AUTH_PUBLIC_NOT_CONFIGURED` with no state change. |
| PUBLIC→PRIVATE with fresh Private password | Lock current lineage; revalidate PUBLIC generation/epoch, then validate Private password freshly; increment generation, mint PRIVATE pair; **retain** the Public epoch snapshot for later resets | `200` new PRIVATE pair. PIN, old JWT, wrong password and same-profile requests cannot elevate. Failed transaction leaves prior lineage unchanged. |
| Revoke with **current active** refresh token | Hash lookup to find lineage; lock lineage first then presented token; validate it is the current pointer, active and unexpired. Set session revoked and invalidate current generation/refresh in same transaction | `200 data:null`. All subsequent access/refresh admissions for that lineage denied. Already admitted reads/writes/streams may complete per D3, without retroactive byte removal. |
| Revoke with **old rotated/consumed**, revoked, unknown or expired token | No current-lineage mutation, even if a predecessor's `replaced_by_token_id` points to an active successor. If row lookup/lock is used, do not follow successor into revocation. | Idempotent `200 data:null` for a syntactically valid input; no successor-lineage denial or replay side effect. Missing/malformed JSON remains 400. |
| Reset Public credential after fresh Private proof | Atomically change Public hash and increment Public credential epoch. Prior Public-associated lineages are invalid by epoch mismatch across all devices and all current profiles; leave unrelated PRIVATE-only lineages intact | `200 data:null`; if calling lineage is affected, its bearer is no longer usable afterward and a fresh PRIVATE login is required. Wrong proof/invalid passwords cause **no** epoch or session change. |
| Expired access JWT or expired/revoked session | Verify JWT `exp`, bound session `expiresAt`, revocation and epoch on admission | 401; never silently renew from access token. Only a valid **current** refresh can create a successor within its unexpired lineage. |
| Two competing refresh vs switch/revoke/reset operations | Resolve candidate lineage ID then serialize under **lineage lock → active refresh lock** (as applicable); revalidate after locking. Public reset also changes credential epoch transactionally; prevent any issuance using an obsolete epoch at/after reset commit | Exactly one valid serialization winner. If rotate commits before revoke, a revoke presented with now-consumed predecessor is a **no-op** (not whole-lineage logout); if revoke wins first, rotate fails. For a guaranteed logout of the now-current lineage, caller must present the current refresh token. Reset wins either before issuance (issuance fails/uses fresh epoch with valid reauthentication) or afterward (old Public-used lineage fails epoch check). |
| Transaction rollback / session DB unavailable / switch reply lost | Rollback issues no accepted new lineage or generation. DB lookup failures fail closed; do not fall back to `sub=1` full access. If switch transaction committed but reply lost, old pair is already invalid. | No forged success; client must perform fresh login after a committed-but-lost switch response, not retry with stale bearer. |

**Lock scope:** no database lock across provider network calls, streaming byte transfer, request lifetime or browser. It is sufficient to serialize **authorization state transitions**; already admitted work may complete, as Owner ratified in D3. New admission/async redispatch after commit rechecks generation. A reset checks credential epoch at the authoritative admission and issue/commit boundaries so the two independent locks cannot allow a newly committed obsolete-epoch token to remain usable. This is a reviewable invariant; the exact SQL/Java lock mechanism is an implementation detail for an authorized handoff.

**Legacy cutover/recovery:** reject every legacy JWT missing `profile`, session ID or generation, and all refresh tokens without valid persisted binding; do not infer PRIVATE from `sub=1`. Current Private password login remains the recovery route. A controlled migration/redeploy is required; restore of a restricted full PostgreSQL backup retains credentials but **must invalidate restored session/refresh authority and rotate JWT signing key before exposing the service**. Portable ZIP excludes these security tables via the same DP-A migration + Portability adapter/tests. This contract does not create automated backups, add Private password recovery/global revoke, retire PIN, or reactivate BFF/Google/Drive/RAG.

## 3. Finite acceptance references (planning only)

- **A09/A10/A12/A13/A20/A21:** actual signed and persisted profile-bound tokens, exact method-specific allowlist, selected status/envelope, old unbound token denial and logout/current-token semantics; never use permissive test-only authentication.
- **G-AUTH:** table-driven ANON/PUBLIC/PRIVATE cases for all rows above (including feature flags OFF and ON/unmapped). Mandatory PUBLIC login cases: `POST /api/v1/auth/profiles/login` with `{"profile":"PUBLIC","password":"<correct configured Public password>"}` and **no identifier** returns 200/profile-bound PUBLIC tokens; wrong and unconfigured Public passwords each return indistinguishable 401; `profile:"PRIVATE"`, missing password and extraneous `identifier` are rejected by new-route DTO validation with 400. Legacy `POST /api/v1/auth/login` continues requiring Owner `{identifier,password}` and can issue only PRIVATE. Verify invalid DTO/password/expiry and 401/403/409/422/503, Google callback 303 and existing PIN verify `200 verified:false` for an incorrect well-formed PIN. Preserve existing bootstrap, one-use and local OAuth contract where still enabled.
- **G-SWITCH:** deterministic real PostgreSQL barrier tests for rotate→revoke and revoke→rotate; old predecessor revoke no effect on current successor; reset↔refresh and reset↔elevation with epoch checks; session expiration before/after successful refresh/switch using controlled clock; downgrade stale JWT vs already-admitted in-flight request. No arbitrary sleeps, provider call or browser test in this preparation.
- **Boundaries:** A release is independently safe with PUBLIC auth-only DENY; B1/B2 grants remain separately authorized. Existing BFF remains paused. PH-04 closure is for independent documentation review, **not implementation acceptance**.
