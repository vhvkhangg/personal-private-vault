## Blocking findings

### GDI26-S3-H1-PH-03 — MEDIUM / OPEN: the selected search batch exceeds S2's real call budget

**Evidence:** [search contract](../h1-search-and-cursor-contract-v0.4.md), lines 19–26, counts root proof as one request and permits six distinct child proofs plus a list. In actual source, `DriveFolderService.ready`, lines 59–66, calls both `provider.accountRoot(...)` **and** `provider.root(...)`. `DriveFileHttpClient.accountRoot` performs a v2 About request; `root` performs a v3 file GET. Both dispatch through `DriveFileAuthority.dispatch:100–101`, which increments the same counter; `DriveFileResources.Operation.countRequest:97` rejects request 9.

**Reproducible contract consequence:** a stable provider page spanning six distinct eligible children requires **2 root-authority reads + 1 list + 6 child GETs = 9**, not 8. The sixth child proof reaches the existing cap. An explicit error avoids false completeness but does not make this normal search traversal usable. No runtime test was run and no implemented H1 search defect is alleged.

**Smallest correction:** preserve the existing root proof and eight-call ceiling; use at most **five** distinct child proofs with one list per request. A simpler selected mechanism is provider `pageSize <= min(requestedLimit,5)`, process that whole bounded page and return a possibly underfilled/empty page with the provider continuation. This eliminates unconsumed metadata-row buffering, reducing state and avoiding old rows becoming authority on a later request. It is an engineering simplification within D29, not a reduction from substring to prefix search or a new Owner capacity decision.

If retaining a larger buffered page, explicitly account for all root/list/revalidation calls, consume leftovers before another page, bound stored bytes and never treat a previous operation's file-parent metadata as fresh authority after a move. Do not remove the account-root check or raise the global cap to make the arithmetic pass. Preserve query/slot/epoch/criteria binding, empty-page progress, explicit `incompleteSearch`/token/budget errors and the non-snapshot caveat.

**Required future regression proof:** a page with six or more distinct children, late-page substring matches and empty continuation; assert actual fake-provider requests including **both** root-authority calls are <=8 per operation and every stable eligible item is reachable. Test leftover/revalidation behavior only if buffering remains. Update B-05/H1-33 and the risk/control count to the selected algorithm. No benchmark platform or catalog is needed.

### GDI26-S3-H1-PH-06 — MEDIUM / OPEN: Google login's transaction and backend exchange trust are unselected

**Evidence:** [Google identity proposal](../h1-google-sign-in-owner-identity-contract-v0.5.md), lines 17–20, assigns state/nonce/PKCE and code exchange to BFF, while lines 28–30 propose an anonymous Spring `/auth/google/login` accepting Google ID-token evidence. Lines 35 and 43 and H1-38 require replay/direct-entry-point resistance, but specify no trusted expected nonce/one-use transaction at that Spring entry point. The callback, verification library/integration and server-facing protection are still alternatives. Current `SecurityConfiguration` has no Google sign-in matcher/validator and remains stateless; nothing is implemented/exposed today.

**Impact / inference:** signature + fixed issuer/audience/expiry + bound subject establish Google token validity. They do not by themselves prove that this POST completed the BFF's current one-use browser transaction. A second POST carrying the same still-valid ID token is not distinguishable by the listed Spring checks. BFF-only callback checks cannot establish the promised direct-backend replay behavior. This is a missing security contract, **not a demonstrated account takeover**.

**Smallest correction:** select one complete protocol and one owner of login/link transactions before handoff. Specify exact start/callback/exchange routes, fixed redirect/client audience, one-use browser-bound state/nonce/PKCE lifecycle, finite attempt/key-fetch bounds and cancellation/logout fencing. If BFF owns code exchange, define how Spring authenticates/binds that exchange context and atomically consumes the trusted transaction, independently validating Google's signed evidence. A caller-supplied expected nonce or loopback address alone is not that proof. Alternatively, select a standard Spring-owned OIDC flow with a bounded one-use handover to the BFF; do not leave both as unchosen implementation options. Prefer supported library mechanisms and existing JOSE/HTTP infrastructure over parallel custom OIDC stacks.

Keep the PPV business-API JWT decoder/issuer/subject policy separate: a valid Google ID token must never authenticate an ordinary PPV/Drive bearer route. Keep S1's callback/cookie unchanged. Same-origin start/link/mutations retain BFF CSRF checks; the Google redirect uses its bound transaction rather than a fictitious same-origin Origin/header. No real Google client secret/Cloud registration is required to select and fixture-test this contract; those remain separate operational gates.

**Required future proof:** controlled signed tokens for correct/wrong issuer/audience/algorithm/nonce/subject/expiry; a valid token posted twice directly; unknown/expired/consumed/swapped transaction, concurrent callback/exchange, missing browser binding, link/login purpose mix-up, logout during code exchange, rejected provider response and disabled flag. Use actual browser redirect/cookie fixtures for the flow and direct Spring HTTP negatives for its own entry point. Google validity and BFF session establishment must not be collapsed into one mock PASS.
