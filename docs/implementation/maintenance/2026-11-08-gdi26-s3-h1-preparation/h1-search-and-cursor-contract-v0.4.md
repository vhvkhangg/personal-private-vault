# PH-03 — Scoped complete search/filter/cursor, corrected call budget (v0.6 contract)

> **CURRENT H1 PREPARATION / PH-03 CORRECTION, 2026-11-08.** File name remains `v0.4` so prior document links stay valid. This v0.6 text supersedes the **six-child-proof / buffered 50-row** mechanism; the initial review and re-review are immutable history. Independent Codex re-review remains required: this is a source-grounded proposed implementation contract, **not a verified runtime feature or closed finding**.

## 1. Authority and exact semantics (preserved D24/D25/D29)

- Selected Google account: only app-created PPV root + its app-created **one-level** child folders and original binary files inside those parents. Never search all of the human user's Google Drive; `drive.file`, immutable `ppvRootBinding`, current slot/Google `sub`, credential epoch, root identity/epoch and app provenance must all qualify.
- `scope=parent&parentId=<root-or-verified-child>` without search criteria: root returns proven child folders + original root files; child returns original direct-child files. With active search/type/date criteria, `scope=all` traverses the eligible PPV subtree independent of which folder is currently open. Do not equate name search with whole personal Google Drive.
- Name `name` after trim: 1–128 Unicode codepoints, NFC and `Locale.ROOT` lowercase, **substring** (accent-sensitive) match; no content/fullText search, and do not use Drive `name contains` because its semantics are prefix-only. `type=all|folder|image|pdf|document|text|other` maps to bounded provider MIME rules; native Workspace docs excluded except verified `application/vnd.google-apps.folder` child.
- Inclusive modified-date `from`, `to` (`YYYY-MM-DD`), one initially allowed IANA timezone `Asia/Ho_Chi_Minh`, UTC half-open `[local start, start of day after end)`; reject reversed/invalid dates, bogus zone, unsupported date filter. Folder modifiedTime requires a valid current provider value. Order by documented provider `modifiedTime desc,name`; no invented `id` ordering or stable snapshot guarantee during concurrent edits.
- Fixed Drive v3 `files.list` query: `corpora=user`, `spaces=drive`, `trashed=false`, exact escaped app-private `appProperties has { key='ppvRootBinding' and value='<approved UUID>' }` condition, plus validated exact parent clause for `scope=parent`. Do not trust provider results from predicates alone; **all** candidates undergo app-identity + current parent/provenance qualification. Provider `incompleteSearch` is an error, never silent success.

## 2. Exact S2 operation-budget accounting — PH-03 fix

The inspected S2 `DriveFolderService.ready` performs **two** provider requests: `DriveFileHttpClient.accountRoot` (`GET /drive/v2/about`), then `DriveFileHttpClient.root` (`GET /drive/v3/files/{rootId}`). Both count at `DriveFileAuthority.dispatch` → `DriveFileResources.Operation.countRequest`; the existing operation rejects the ninth provider dispatch.

| Provider request in one H1 search HTTP operation | Maximum |
| --- | ---: |
| Current account root ID verification (`accountRoot`) | 1 |
| Current PPV root metadata/provenance (`root`) | 1 |
| One bounded `files.list` call | 1 |
| Fresh `files.get` for distinct candidate child-folder authority | **5** |
| **Total permitted** | **8** |

**Selected simplest algorithm:** request **at most `min(callerLimit, 5)` provider candidates** in one `files.list` call (`callerLimit` 1..50). Qualify each candidate from the returned bounded metadata, and for each **distinct** child that must be remotely proven, make at most one `files.get` in *that same operation*, caching proof only for that operation. A page of five candidates can therefore never require more than five remote child proofs. Existing root verification, listing and candidate proof cannot trigger hidden extra calls; if a future refactor adds calls, reduce the candidate budget instead of raising S2's eight-call ceiling. Any provider/proof/network cap failure is explicit, never a successful partial page.

- This is **provider-entry count**, not "five visible results": a page may yield zero to five eligible cards because rejected/filtered entries consume slots. Continue on the provider's opaque next-page token. A sixth distinct child on an otherwise stable result set appears in a **subsequent HTTP request**, with its own fresh two-root/one-list/at-most-five-proof budget. The UI's automatic scroll may encounter empty intermediate pages with `hasMore=true`; do not invent page numbers or counts.
- **No buffering of unconsumed provider metadata rows between operations.** The provider supplies ≤5 entries and the backend handles every returned entry before issuing a continuation; never silently discard or postpone one. No previous request's verified parent metadata becomes authority for later I/O or result qualification. This deliberately removes the old 50-entry buffer plan and the stale-parent revalidation ambiguity identified in the review.
- A directly proven root file may use the current root proof + complete app markers/parent values from this list; children and child-contained files require fresh validation of the verified child's root-parent/provenance/intent identity. `files.get` is charged once per distinct child ID in the page, not once per file. No direct download/upload/thumbnail follows based only on prior list proof: each actual I/O has its own current owner/slot/parent/file proof.
- Client-visible page `limit=1..50` stays accepted, but effective provider `pageSize=min(limit,5)` is documented and bound in the continuation. Do not promise 50 returned cards per request. The existing S2 direct-root list route and its original limit/cursor behavior **remain unchanged**.

## 3. Cursor/termination/failure contract

- H1 search cursor: process-local, CSPRNG opaque **43-character** handle, expiry **300 seconds**, at most **128** outstanding. Bind owner, selected Google `sub`, slot, credential epoch, root binding/epoch, exact scope/verified parent, normalized `name`/type/from/to/timeZone, callerLimit **and effective provider pageSize**, provider token and (if needed) bounded progress metadata. Consume/rotate continuation **once per operation**; wrong subject/slot/criteria/parent/limit, expired, replayed or post-restart handle rejects `DRIVE_CURSOR_INVALID`. Never expose provider page token.
- No retained provider candidate buffer is required. `nextCursor` exists **iff** a valid next provider token exists and no provider `incompleteSearch`/mandatory verification failure occurred. An empty eligible page with provider continuation returns `items=[]`, `hasMore=true`, non-null `nextCursor`; the UI automatically requests another bounded page when applicable.
- `hasMore=false` and null cursor only when the provider has no next token **and** the returned page was fully processed with no incompleteSearch/poisoned token/unresolved mandatory proof. This describes end of one provider traversal, not a consistent snapshot across time; concurrent edits can reorder/duplicate results. UI suppresses recent duplicates in a small bounded set and displays changed-result caveat rather than pretending transactional completeness.
- Provider token loop/malformed value, invalid/reused cursor, `incompleteSearch=true`, concurrency/admission capacity, deadline or mandatory metadata failure → sanitized explicit error (`DRIVE_SEARCH_INCOMPLETE`, `DRIVE_CURSOR_INVALID`, `DRIVE_CAPACITY_EXHAUSTED` or corresponding existing safe error) with **no false complete/zero-results terminal claim**. Retrying an expired/bad chain restarts from first page; it does not reuse expired qualification.
- Per request maximum two root proofs + one provider page + five distinct child GETs = **8**, including **all** actual provider dispatches in fake-provider request-count assertions. One-page-at-a-time traversal bounds memory and call rate, not total cost over an arbitrarily large valid subtree. No Redis/global file catalog, no Drive-wide scope, no extra operation for stale candidate under the same request.
