# PH-04 — Strict private thumbnail trust and fallback contract v0.4

**Status: selected restrictive PROPOSAL / not implementation or guaranteed preview coverage.** Drive `thumbnailLink` is short-lived; private thumbnails require authorized fetches, and the provider does **not** promise a stable host in the cited Drive reference. The browser **never** receives raw Google `thumbnailLink`, provider token, `Authorization` header or arbitrary remote asset URL. Owner-approved v0.3 is aspirational on card images, not authorization to forward secrets to every URL returned by metadata.

## Selected transport and trust policy

1. Authenticated PPV JWT → current S1 slot/sub/epoch and ready root → current root or registered completed first-level child → fresh file metadata `files.get` (`id,name,mimeType,size,parents,appProperties,thumbnailLink,trashed`). A file moved out of the verified current parent, native Workspace document, foreign/malformed markers, stale root or disconnected subject **fails before any thumbnail HTTP request**.
2. Parse provider metadata link as an **untrusted URI**, without ever accepting a URL from browser. **Allowlist exactly** `https://lh3.googleusercontent.com` on implicit/explicit port `443`; reject everything else (`*.google.com`, arbitrary `googleusercontent.com` subdomain, `drive.google.com`, IP literal, loopback, non-HTTPS, username/password, `#fragment`, non-443 port, malformed/oversize URL). This is an intentionally narrow selected host policy: **not a claim** Google promises this hostname on every `thumbnailLink`. If no official/controlled fixture proves this host in a relevant scenario, return fallback rather than broadening the allowlist. Any additional provider hostname requires separate documented provenance/security re-review, not dynamic trusting of `endsWith("google.com")`.
3. The server may send Google bearer **only** to the URL after the exact-origin validation; require TLS certificate/hostname validation and fixed trusted transport (no proxy override), `GET` only, **redirects disabled**, no reusable cookies, no arbitrary request headers, no response hop to a new hostname. Never send the bearer in query, public log or error. Recheck current authority and cancellation around dispatch and completion; no shared thumbnail cache across subjects/slots. If a deployment uses a system proxy, its trust/egress policy must be separately assessed before live activation.
4. Bounded resources: one thumbnail network operation at a time per current S2 file-resource capacity; connect ≤2s, total thumbnail request ≤8s, idle ≤5s, server read/response maximum **1,048,576 bytes**; close/abort on cap, timeout, disconnect or stream error. No redirect follow, HTTP compression decode, transcoding, remote HTML rendering, PDF/DOCX parser or multi-megabyte heap caching.
5. Content policy after receipt: allow only `image/png`, `image/jpeg`, `image/webp` with a bounded valid signature/decoder sanity check where feasible; **reject SVG, HTML, XML, GIF, `image/*` wildcard**, content-type mismatch, oversized/empty/truncated or suspicious data. For supported images, proxy bytes with `Content-Type` exact safe value, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, restrictive CSP as applicable; no provider redirects/URLs in browser HTML/JSON. A response that cannot be verified is sanitized fallback (e.g. 404 `THUMBNAIL_UNAVAILABLE`) rather than redirecting browser directly to Google.
6. If no `thumbnailLink`, untrusted host, wrong MIME/size, quota failure or timeout, render the already-approved **file-type icon/placeholder** (and filename) — no fabricated preview. This conditional fallback is important: preview is available *when Google supplies a safe supported thumbnail*, not for every PDF/DOCX or every image.

**Trust limitation requiring Owner awareness:** exact-origin `lh3.googleusercontent.com` is a strict implementation **candidate**, not presently corroborated by a live owner-account thumbnail. It may lead to more fallback tiles than the v0.3 illustration. The Owner can approve this fallback interpretation via the [approval docket](owner-approval-docket-v0.4.md) or request a provider-host validation gate before claiming meaningful preview coverage. Do not widen host allowlist or build a local PDF/DOCX renderer merely to match the picture.

## H1-B/H1-F tests and proof (future, NOT_RUN)

- Fake metadata URL cases: `http://`, `https://evil...`, `https://lh3.googleusercontent.com.evil.test`, another `lhN` host, IP/localhost, encoded userinfo, fragments, explicit port `444`, invalid URI, host case/punycode, overlength query and redirect `302/307`; assert **zero bearer dispatch** to unapproved destinations. Check no credential in public response/logs.
- Same trusted exact host with explicit fake transport and real TLS policy seam (test-only), image PNG/JPEG/WEBP, short response, claimed size mismatch, >1 MiB, huge declared body, HTML/SVG/empty/truncated data, slow stream/deadline and cancel; assert bounded result or honest placeholder. A provider fixture showing different host yields **fallback**, not new trust.
- Wrong subject/epoch/root/parent, moved file and stale cursor fail before provider image HTTP; slot switching invalidates in-flight image. BFF/browser tests assert no cross-session public cache or raw provider link and appropriate fallback semantics.

**References:** Google [metadata thumbnails](https://developers.google.com/workspace/drive/api/guides/file-metadata), [files fields](https://developers.google.com/workspace/drive/api/reference/rest/v3/files). These support link expiry and credentialed fetches, **not** this application's chosen allowlist host. Any future statement that Google guarantees `lh3` needs separate evidence. This document selects *deny by default + fallback*, not universal thumbnails.
