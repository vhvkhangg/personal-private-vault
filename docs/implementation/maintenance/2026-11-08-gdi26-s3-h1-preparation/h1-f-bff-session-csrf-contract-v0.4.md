# PH-05 — Selected one-**Node-process** Next BFF session, CSRF and OAuth browser contract v0.4

**Status: concrete H1-F security PROPOSAL for Owner/independent review; not installed/tested.** Spring Authentication retains username/password validation, JWT access token, **opaque refresh token**, refresh rotation/revocation and Google authority. A browser holds **only an opaque local BFF session cookie**; no Spring or Google token is sent to JS, `localStorage`, `sessionStorage`, serialized React/RSC props, URLs, asset requests, ordinary logs or `NEXT_PUBLIC_` values.

## Exact initial origins and deployment assumptions

- **Single machine/local pilot only:** self-hosted Node BFF origin `http://localhost:3000`, Spring origin `http://localhost:8080`, **same literal hostname `localhost`** for login/authorize/Google callback; mixing `127.0.0.1`, alternate hostname or proxy is forbidden until independently reviewed. The approved S1 callback remains exactly `http://localhost:8080/api/v1/drive/oauth/callback`. Run one BFF process and one Spring JVM, no CDN/proxy-host rewrites in this approved localhost pilot. Public/remote production HTTPS is a separate security/deployment gate, not covered here.
- Authenticated local cookie: name `ppv_dev_sid`, host-only (no Domain), `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure=false` **only for the exact localhost HTTP pilot**. Hostname, port and cookie `Path` are explicitly tested. In separately approved HTTPS deployment, require `__Host-ppv_sid` with `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no Domain; do not automatically switch host/callback before a new S1 review.
- Session IDs: cryptographically random **32 bytes**, base64url (43 chars), stored only as an HMAC/SHA-256 keyed digest in the volatile session map; constant-time comparison of bearer/session proof where applicable, no enumerable numeric IDs. Server stores access JWT and opaque refresh in RAM only, never on filesystem; one process restart **logs out all browser sessions**. No Redis/DB/session microservice.
- At most **8 total** live sessions (anonymous+authenticated) in the one-Owner app; no silent LRU eviction of active sessions. Anonymous prelogin session idle 10 min / absolute 20 min; authenticated idle **30 min** / absolute **12 h**; expiry means removal and cookie invalidation. Rotate session ID and CSRF secret on successful login; old anonymous ID is invalidated, not upgraded in place. Login/logout/refresh keep immutable generation/epoch guards. Limit login attempts by existing Spring policy and local bounded anonymous admission, never bypass Spring rate limiting.

## Concrete CSRF mechanism for *prelogin and authenticated* mutations

1. Before Google Sign-In, browser GET `/login` obtains a host-only anonymous HttpOnly session plus a server-random 32-byte anti-CSRF secret bound to that session; the server delivers a derived per-session anti-CSRF token to the same-origin HTML (meta/hidden form value) without disclosing access/refresh/session ID. CSRF token is **not an authentication credential**.
2. Every **same-origin browser mutation** — Google sign-in/link **start**, `POST /logout`, authorize, disconnect, ensure-root, create-folder, upload, and any Next Server Action — requires: allowed method, authenticated or anonymous session as appropriate, exact `Origin: http://localhost:3000`, matching Host, Fetch Metadata policy (`Sec-Fetch-Site: same-origin` for capable browsers), and a valid anti-CSRF header `X-PPV-CSRF` (or same validated hidden form field). Reject absent/mismatched token/Origin and cross-site requests with 403 **before** any Spring/provider mutation. SameSite is supplemental, not the sole defense. Do not treat `Sec-Fetch-*` missing in supported older clients as an automatic pass when Origin/token are absent.
3. Token construction: a random per-session secret stored only server-side; expose a **different random** 32-byte browser-readable token which the server retains as a SHA-256 digest bound to this session generation, compare constant-time; never derive or expose the session cookie ID. Rotate both after successful Google sign-in and on logout; prevent attacker session fixation. An explicitly bounded prelogin CSRF token is required even when not authenticated.
4. Logout is an authenticated CSRF-guarded mutation. Delete/invalidate the server session **atomically before** best-effort backend `/auth/revoke`; expiry/invalidation is effective even if Spring revoke times out or returns an error. Clear cookie and close local privilege immediately. Do not wait for remote revoke to invalidate BFF authority.


**Google redirect exception — PH-06 selected correction:** **Spring**, not Next, owns one-use state/nonce/S256 PKCE, provider code exchange and ID-token signature checks at its fixed `http://localhost:8080/api/v1/auth/google/callback`. The callback is a cross-site top-level navigation: **no same-origin Origin/X-PPV-CSRF header is expected there**; instead Spring verifies bound cookie/state/nonce/code. BFF owns only CSRF-protected start/link proxies, anonymous prelogin session with independent 256-bit handoffVerifier, and single-use 60-second HttpOnly ticket-cookie completion (`/api/bff/auth/google/complete`), redeeming the ticket+verifier at Spring. Do not invent an anonymous ID-token login endpoint or expose ticket/code in BFF URL. See [selected PH-06/07 Spring-owned contract](h1-google-sign-in-owner-identity-contract-v0.5.md).

## Serialized refresh, logout and expiry ordering

- Each session is one state record `{generation,status,accessExpiresAt,accessJWT,opaqueRefresh,csrfDigest,idleDeadline,absoluteDeadline}` guarded by **one short critical-section mutex plus an atomic invalidation generation**. A backend network refresh is performed **outside** the mutex under a one-per-session singleflight token; do not hold a lock during network I/O or prevent logout from marking the session invalid. Requests are admitted only if `ACTIVE`, both deadlines valid and generation still current. A request snapshots generation; **recheck before committing any result** to client or cache.
- When access nears expiry, a **single in-flight refresh** per session rotates the opaque backend refresh token using a singleflight future and short mutex-protected commit. Other tabs await that same operation (bounded wait, no duplicate refresh). Backend response commits new tokens only if the same session ID+generation is still ACTIVE and within deadlines; invalid/replayed refresh or backend failure invalidates the local session and prompts login — never replay the old opaque refresh token indefinitely.
- **Logout wins** even if refresh already started: mark `REVOKING/INVALID` and increment generation synchronously without waiting for network I/O; the refresh continuation may finish remotely but must discard returned tokens if generation changed. If the just-rotated refresh is still available on server, best-effort revoke it in the bounded background owned operation; never reanimate session/cookie. Expiry and BFF restart have the same generation fence; no “late success” after logout.
- No global token cache, cross-session/session-slot mutable state or shared private RSC cache. Authenticated server renders, Route Handlers and responses are `Cache-Control: private, no-store`; every direct route/action reauthenticates. Next middleware/layout visibility alone is not authority. Avoid forwarding arbitrary request headers/URLs, reflecting tokens or caching private HTML/JSON/images on CDN.
- Failed login does not elevate anonymous session; rotate/discard prelogin session on appropriate failure limits. On new login, the old session ID cannot be replayed; on disconnect/switch slot, cancel old cursor/image/upload list projections but **do not** invent a new Google subject session.

## Same-browser Google OAuth cookie relay — exact S1 contract

- The browser calls **same-origin BFF** to initiate `POST /connections/{slot}/authorize` with session/CSRF, BFF authenticates and makes a server-side JWT call to Spring. The BFF forwards **only** Spring's named `PPV_DRIVE_BINDING_1` or `_2` Set-Cookie (Host-only, HttpOnly, SameSite=Lax, Path exactly `/api/v1/drive/oauth/callback`, Max-Age=300; Secure follows current backend localhost configuration), never a blanket Set-Cookie/header proxy. Validate expected slot/cookie name/attributes; reject a changed or duplicate cookie shape rather than fabricate proof. Consent URL returned to browser for deliberate navigation; Google tokens and state material are not stored in public logs.
- Browser redirects to Google then to fixed **Spring callback `http://localhost:8080/api/v1/drive/oauth/callback`** using *the same browser/host cookie jar*. Cookie host-scope is independent of port, but Path/SameSite/binding must be verified with actual Playwright/real-browser positive and wrong/absent/replaced/expired cookie tests. Backend returns fixed `text/plain` status. User returns to PPV explicitly after this callback; do not silently introduce a different Google redirect URI or public proxy callback.
- No wildcard CORS, alternate hosts/ports, Google Picker, new OAuth scopes or implicit remote HTTPS activation. Browser status refresh via BFF cannot override S1 server-authoritative connection state.
