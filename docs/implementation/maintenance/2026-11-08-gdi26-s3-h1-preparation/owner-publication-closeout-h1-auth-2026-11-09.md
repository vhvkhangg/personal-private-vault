## Accepted delivery, not website or live Google activation

Spring Authentication now owns a gated login OIDC authorization-code transaction for the **existing singleton vault Owner**. It uses fixed login client/issuer/`sub` identity, one-use state, nonce, PKCE, browser binding, narrowly validated signed Google ID tokens and a one-use ticket plus independent BFF verifier. Initial binding requires a current Owner login **and fresh legacy password**; immutable identity prevents silent linking of a different subject or any Drive slot. Atomic handoff consumption issues canonical PPV HS256 access JWT and opaque refresh under the Authentication transaction. No new Owner, account-email takeover, arbitrary raw-ID-token login, Google rebind, Drive authority transfer or global JWT decoder widening is authorized.

The delivery adds prospective **V28** Authentication identity/attempt/ticket persistence with security-table Portability exclusion, a BOM-managed OAuth2 Client dependency, narrow feature-gated SecurityConfiguration matchers and scoped docs/tests. Existing `/api/v1/auth/login`, bootstrap, refresh, revoke and PIN remain in place; direct legacy password API is the documented operator emergency path, not a website sign-in or automatic account recovery feature.

Only `PPV_GOOGLE_SIGNIN_ENABLED=true` in controlled fixtures is covered by acceptance. In ordinary configuration keep **`PPV_GOOGLE_SIGNIN_ENABLED=false`, `PPV_DRIVE_ENABLED=false`, `PPV_DRIVE_FILES_ENABLED=false`, `PPV_FEED_SCHEDULER_ENABLED=false` (or unset)**.
