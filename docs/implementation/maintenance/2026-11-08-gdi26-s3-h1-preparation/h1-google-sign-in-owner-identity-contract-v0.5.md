# H1-AUTH — Selected Spring-owned Google OIDC, singleton Owner linking and recovery (v0.6)

> **CURRENT PH-06/PH-07 CORRECTIVE TECHNICAL CONTRACT, 2026-11-08.** Filename remains `v0.5` to preserve established links; this v0.6 content supersedes the earlier **BFF exchanges Google code + anonymous `/auth/google/login` ID-token POST** alternatives. One selected protocol; no implementation, Cloud activation or PH finding closure is claimed. D26 requires routine Google Sign-In; D27/D28 desktop-only/delegated states; D29 approves bounded local BFF design; D30 delta-only packages.

## 1. Identity and selected trust owner

**Spring Authentication owns the complete Google OIDC transaction**, provider code exchange, nonce/state/PKCE verification, signed ID-token validation, singleton binding and PPV token issuance. Next.js BFF owns only the local browser prelogin/session/CSRF, initiation proxy and one-use handoff redemption. **No anonymous endpoint accepts a raw Google ID token as PPV login proof.** Spring's business bearer decoder continues to accept only PPV-issued HS256 JWTs (issuer and canonical `sub="1"`); a Google RS256 ID token never authenticates a Drive/PPV business route.

Login Google client and S1 Drive slots remain separate: login scopes fixed `openid email` (no `drive.file`, no offline Google refresh), login OAuth client ID/secret/callback separately configured under default-OFF `PPV_GOOGLE_SIGNIN_ENABLED=false`, Drive flags remain OFF. Never infer that slot 1 or 2 is an allowed PPV login subject; email is informational only. Only one linked Google stable `sub` under permitted issuer can own **existing `app_users.id=1`**, never a second user or automatic bootstrap. Supported standard Spring Security OAuth2/JOSE validation preferred; no custom unreviewed signature engine or passive acceptance of a frontend assertion.

## 2. Selected local-only OIDC protocol: exact routes and redirects

| Caller → receiver | Endpoint / purpose | Trust boundary |
| --- | --- | --- |
| Browser → Next BFF | `POST http://localhost:3000/api/bff/auth/google/start` | Prelogin session + exact same-origin Origin/Host/CSRF; prepares server-held 256-bit `handoffVerifier`, passes only its SHA-256 challenge to Spring |
| Browser → Next BFF | `POST /api/bff/setup/legacy/login`, then `POST /api/bff/setup/google/link/start` (first-time setup **only**) | Existing username/password verified using Spring `/api/v1/auth/login`; temporary protected BFF PPV session; second request has auth session + CSRF + **fresh password re-verification** by Spring (JWT alone is insufficient) |
| Next BFF → Spring | `POST /api/v1/auth/google/start` (LOGIN) or `POST /api/v1/auth/google/link/start` (LINK) | LOGIN public but feature-gated, bounded; LINK requires canonical PPV bearer `sub=1` **and password freshly checked by Authentication**; both contain validated challenge hash, never arbitrary user ID/provider URL |
| Browser → Google → Spring | `GET http://localhost:8080/api/v1/auth/google/callback` | Exactly registered localhost login OAuth redirect; Spring validates browser-binding cookie, one-use stored state, code/nonce/PKCE and Google ID token. **Not** S1 `/api/v1/drive/oauth/callback` |
| Spring → Browser → Next BFF | Spring `303` to fixed `http://localhost:3000/api/bff/auth/google/complete` with **one-use opaque ticket in HttpOnly cookie**, not query string | No PPV/Google tokens, ticket or authorization code in redirect URL; no open redirect; BFF checks matching prelogin session/verifier |
| Next BFF → Spring | `POST /api/v1/auth/google/handoff` with ticket + raw BFF-only handoffVerifier | One-use server-side ticket + verifier hash challenge **atomically** verified/consumed under PostgreSQL lock, *then* Spring issues existing JWT access + opaque refresh via shared Authentication token-issuance path |

Only the fixed literal `localhost` hosts/ports above are in pilot scope. Login OAuth `redirect_uri` is registered **exactly** as the Spring callback on :8080; BFF completion is a fixed second local redirect, **not** the Google-registered redirect. Exact allowed origins are :3000 and :8080, no user-supplied `next`, `returnUrl`, remote host, wildcard proxy/CORS or host switching. Use host-only `HttpOnly`, `SameSite=Lax`, exact callback-path 300-second binding cookie and 60-second completion ticket cookie (`Path=/api/bff/auth/google/complete`); `Secure=false` only for explicitly approved HTTP localhost pilot. Future remote HTTPS, cookie `__Host-` names, origins, Cloud redirect registration and network topology require separate review.

**Start:** Spring makes random ≥256-bit state, nonce, PKCE verifier (S256), random browser-binding secret, and an immutable `purpose=LOGIN|LINK`, submitted challenge hash, time/expiry and (for LINK) singleton Owner ID in durable transaction record. Explicit `scope=openid email`, `response_type=code`, PKCE S256 and exact Google client ID/redirect. Max age **300 seconds**, at most **four outstanding** per singleton/login installation, bounded rate and metadata sizes. Spring returns fixed consent URL and narrowly scoped binding `Set-Cookie`; BFF proxies **only** the verified named cookie, never copies arbitrary headers. Prelogin BFF session retains raw handoffVerifier and only a bounded attempt reference, never Google tokens.

**Callback:** read `state` and browser cookie once, reject duplicate/unknown/expired/purpose-swapped/previously consumed state, invalid code/error or absent proof. Lock/fence the attempt before any outbound exchange; **one** callback claimant may dispatch a Google code exchange. Use existing Spring Security-supported OAuth2 Client/JOSE implementation for fixed Google discovery/JWKS and code+PKCE exchange; validate ID-token signature and pin allowed signing alg (Google RS256), approved issuers `https://accounts.google.com`/`accounts.google.com`, **exact login client audience**, `azp` consistency if required, expiry/not-before/issued-at clock tolerance, **exact stored nonce**, nonblank immutable `sub`, and intended successful `openid email` scope. No Google access/refresh/ID token is persisted as a login credential or handed to BFF; no trusted email matching. Restrict JWKS cache size, allowed key algorithm/issuer HTTPS origin, finite timeouts (connect 2s, bounded overall metadata/exchange ≤10s), no redirects/follow-any URL, do not enable unbounded kid cache misses/fetch loops. Provider SDK defaults must be checked against the bound. Credential/client keys remain outside Git.

**Completion:** after signed identity and owner/purpose checks, in an Authentication DB transaction: (LINK) insert-only immutable binding to singleton owner when absent; (LOGIN) compare exact previously bound issuer+`sub`; mark attempt completed and create cryptographically random ≥256-bit **one-use handoff ticket** stored **as hash only** together with its BFF handoffChallenge hash, fixed purpose, owner, expiry **60 seconds**, consumed status. If app is unbootstrapped or Google subject mismatches, fail closed; never create an Owner. Backend sets named ticket cookie, clears the callback binding cookie, emits no credential URL, and 303s to fixed BFF completion. The BFF GET validates same prelogin/session generation then redeems once; a successful exchange creates **new** authenticated BFF session and rotates cookie+CSRF; old prelogin handle is invalidated. LINK flow may preserve/rotate the already authenticated session, but cannot switch owner identity.

**Direct backend replay resistance:** `POST /auth/google/handoff` is the *only* anonymous exchange route; it accepts neither unvalidated ID token nor unsigned subject. It needs **both** unguessable ticket (stored hash) and independent BFF-only verifier whose SHA-256 equals the stored challenge, checks purpose/owner/expiry and atomically consumes the ticket under row lock. Issue PPV tokens and persist a new opaque refresh row **inside the same DB transaction** as ticket consumption (or return error and roll back, no partial success). A duplicate concurrent/replayed ticket fails without issuing more tokens. Loss of the exchange HTTP response is **not** retried to create a second token; restart a fresh Google OIDC start. No ticket, BFF verifier, Google credential or PPV refresh is logged/serialized to browser/URL. Bound handoff POST request length/attempt rate and sanitise errors; do not assume loopback IP alone provides identity/trust. Browser cannot make ordinary authenticated Spring calls with a Google ID token.

**Cancellation/logout/failed request:** BFF generation token captured at start must still be current before installing any returned PPV tokens; logout/timeout/expired anonymous session/changed login purpose invalidates old generation and any late handoff result (best-effort revoke fresh Spring refresh token if already issued). Invalid callback clears appropriate browser-binding cookie and surfaces one bounded retry action, not a false login. One-use Spring attempt states (`PENDING → PROCESSING → COMPLETED|FAILED|EXPIRED`) and ticket states prevent simultaneous code exchange or replay; expired/failed/consumed evidence retained for bounded audit, no secrets. Do not use the Spring S1 Drive callback, its slot proof or an existing PPV JWT as substitute for current OIDC transaction proof. Same-origin start/link mutations require BFF prelogin or authenticated CSRF/Origin; cross-site Google top-level callback is authenticated by Spring state+cookie+nonce/PKCE, not same-origin Origin.

## 3. Singleton first link, persistence and emergency access

**First setup is a one-time, explicit Owner action, not routine password-login UX.** Prerequisite: existing secure PPV bootstrap already created singleton owner `app_users.id=1`. A dedicated local setup screen uses existing Spring username/password login server-to-server to create a short-lived BFF setup session; then requires **a fresh password input checked again by Spring at `/auth/google/link/start`** immediately before starting the LINK transaction. Existing access JWT proves owner session but is *not* proof of recent password entry because `/auth/refresh` creates access JWTs without password. Failure/backoff must be explicitly implemented and fixture-tested for the new link operation, not assumed from an unverified existing login rate limiter: maximum five bad fresh-password LINK attempts per Owner in rolling 15 minutes, fail closed if the durable rate gate is unavailable. The existing legacy login surface is unchanged and cannot be claimed rate-limited merely by this requirement. Never print password, credential proof or session token. No arbitrary login linking from anonymous Google auth, matching email or Drive slots.

**Selected prospective V28, only after H1-B V27 is published:**

1. `public.ppv_owner_google_identities` (Authentication-owned): `owner_id SMALLINT PRIMARY KEY REFERENCES app_users(id)`, `issuer VARCHAR(128) NOT NULL`, `google_sub VARCHAR(255) NOT NULL`, `linked_at TIMESTAMPTZ NOT NULL`; checks `owner_id=1`, nonblank issuer/sub, unique `(issuer,google_sub)`. No `updated_at`/upsert/rebind path. Google email is not a binding key. Singleton row is insert-only under `app_users` row lock + DB unique constraints; concurrent distinct first links: only one commits; same-sub retry after a lost reply requires **a new fresh-password LINK transaction** and returns already-bound/same-sub success **without creating another identity**. Different-sub attempts return sanitized conflict and never replace existing binding.
2. `public.ppv_google_login_attempts`: random opaque attempt ID/hashed state+binding proof, `purpose`, `owner_id` when LINK, `handoff_challenge_hash`, PKCE verifier **AES-256-GCM encrypted at rest using a dedicated 32-byte `PPV_GOOGLE_SIGNIN_TXN_KEY_FILE` outside Git, with protected host ACL and random per-record nonce**; nonce claim and secret-binding proof are stored only as bounded values/hashes (not plaintext logs or ordinary Portability), status/expiry timestamps, claim/fencing generation. Unique hash keys; persist bounded failed LINK-password events for the selected rolling rate gate; no plaintext password/code/Google token retained. A Postgres compare-and-set or row lock on `PENDING → PROCESSING` before outbound work prevents two code exchanges; recovered `PROCESSING` fails closed/restart, never automatic re-dispatch.
3. `public.ppv_google_handoff_tickets`: random ticket **hash** PK, `attempt_id` unique FK, `owner_id=1`, `purpose`, `handoff_challenge_hash`, issued/expiry/consumed timestamps, single-use `PENDING|CONSUMED|EXPIRED` with constraints. Strict 60s TTL and atomic consume+token issue; bounded cleanup only for terminal/expired data after safe retention, no deletion of active or unresolved attempt proof.

Add all three to `PortabilitySnapshotAdapter.EXCLUDED_SECURITY_TABLES` and corresponding explicit schema/migration inventory/DBML/ADR update in H1-AUTH. This is a **proposed** migration/data classification; V1, the app-users table shape, token/JWT issuer (`sub="1"`), existing bootstrap/password-login/refresh/revoke/PIN, and Drive S1/S2 schemas or OAuth connection records remain unchanged. The new default-OFF flag does not silently permit anonymous generic OIDC URLs: SecurityConfiguration gains **only** explicitly allowed `POST /auth/google/start`, `GET /auth/google/callback`, `POST /auth/google/handoff`; authenticated `POST /auth/google/link/start` still needs PPV JWT plus fresh password. Unknown paths remain denied. Feature OFF returns no Google endpoints, no outgoing provider operation, no OIDC client/key loading; preserve existing resource-server strict issuer. Only Authentication-internal module code, tests, prospective V28, explicit Portability exclusion and narrowly needed docs are H1-AUTH scope; no general auth refactor.

**Recovery policy (selected minimum):** Owner retains existing **local backend `/api/v1/auth/login` with username/password**, `/refresh`, `/revoke`, and bootstrap/PIN mechanisms as an **operator-only emergency route**, separate from ordinary Google web sign-in. If Google identity is lost or revoked, the Owner can authenticate directly to the existing Spring API using retained legacy password and take an approved data export/backup action. **This does not rebind or unlink Google login**; normal website sign-in remains unavailable until a *separately Owner-approved* recovery/rebind maintenance process. No email-only recovery, automatic new Google `sub`, second Owner, magic link, or undocumented manual database edit is authorized. This avoids claiming a complete web login recovery function that is not implemented. Owner must retain the original password and local backup procedure; a lost password **and** lost Google identity is not recoverable by H1. Expose this limitation clearly in setup confirmation/operations docs.

**Source grounding:** inspected `AppUser.SINGLETON_ID=1`, `AppUserRepository.findByIdForUpdate`, `SessionService.login/rotate/revoke`, `JwtTokenService.issueAccessToken` and `SecurityConfiguration`; actual new transaction/token-issued-in-same-DB implementation is a prospective H1-AUTH requirement, **not present today**. Official Google [OIDC](https://developers.google.com/identity/openid-connect/openid-connect) and [web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server) define code, state, nonce, client ID/redirect requirements. The Spring-owned choice avoids accepting a replayable valid ID token at an anonymous PPV login endpoint.
