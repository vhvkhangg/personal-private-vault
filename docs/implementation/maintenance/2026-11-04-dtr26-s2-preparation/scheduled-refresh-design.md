# DTR26-S2B — Opt-in scheduled refresh contract (future gated slice)

**Status:** `PROSPECTIVE_S2B_ONLY / NOT_AUTHORIZED_FOR_IMPLEMENTATION`. The Owner requested scheduling **as part of S2 design**, but executing a scheduler waits until S2A is independently accepted, Owner-published and S2B separately authorized/rechecked. No scheduled work exists at the current source baseline.

## Reuse existing DB scheduling state

- `feed_sources.enabled`, `scheduled_refresh_enabled`, `refresh_interval_minutes`, `last_fetched_at`, `next_fetch_at` are already persisted.
- [`FeedSourceRepository.findDueSources`](../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/infrastructure/persistence/FeedSourceRepository.java) uses `enabled=true`, `scheduled_refresh_enabled=true`, and `next_fetch_at IS NULL OR <= cutoff`; deterministic null-first, time, ID order.
- [`FeedSourceService.updateSource`](../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/application/FeedSourceService.java) clears/recomputes `nextFetchAt` on schedule edit under lock. [`FeedItemService.ingestFetch`](../../../../backend/src/main/java/com/vhvkhangg/personalprivatevault/feed/internal/application/FeedItemService.java) updates last/next fetch timestamps only on successful atomic ingest. **Do not advance these timestamps on HTTP failure** to simulate a scheduler retry clock.

## Proposed single-instance execution model

1. **Two opt-ins required:** a new explicit application property e.g. `ppv.feed.scheduler.enabled=false` by default **AND** a source with `enabled=true`, `scheduled_refresh_enabled=true` and valid positive `refresh_interval_minutes`. Default startup makes **zero** automatic outbound requests even if old source records contain scheduling flags. If global property true, only HN and RSS sources are runnable in S2B; other enum values remain metadata-only.
2. **Small Feed-owned timer:** one Spring scheduler tick about every **60 seconds**, conditional on global opt-in. Task callback delegates to the same owner-local application `refresh` use cases; it never implements network/parsing/domain writes itself. No new REST endpoint or persistent job queue; no catch-up storm when app restarts.
3. **Bounded/fair due scan:** use existing due predicate and ordering, with **bounded pages and progress across ticks** so a repeatedly failing source or unsupported source cannot permanently monopolize selection. Restrict query to HN/RSS in the scheduler path (do not change the accepted `GET /sources/due` semantics). Proposed at most 20 candidate checks / tick and at most **2 accepted refreshes** in a tick; ensure every eligible source is eventually considered under a finite stable due set. Codex must supply an exact no-starvation algorithm and executable examples before S2B handoff; a permanent `LIMIT 2` over a failing null-first first page is **not acceptable**.
4. **Reuse global admission:** HN S1 uses single-JVM per-source single-flight and max **2** in-flight refreshes. S2B shares that admission with RSS and manual refresh. Do not dispatch another refresh for the same source while one is active. Do not hold DB connections or row locks while network requests run. A simple bounded worker pool/serial bounded loop is acceptable; never create unbounded threads/queues, hidden retries or asynchronous work that outlives its owner.
5. **Source authority through commit:** scheduler preflight verifies source still due/type/enabled/scheduling opt-in; after HTTP, the provider's **same-transaction** finalizer must recheck source type/enabled and, for a *scheduled invocation*, `scheduled_refresh_enabled` under the authoritative row lock before ingest commit. RSS also verifies fetched `feedUrl` still matches current stored value. Manual refresh remains usable when scheduling disabled. If schedule interval changes mid-fetch, generic ingest must use the fresh interval to calculate next due time after successful commit. Config source change/disable/scheduling toggle during fetch must have a deterministic documented outcome and a barrier test.
6. **Failure/backoff without schema:** propose one bounded per-source **in-memory** cooldown on failed/saturated attempts (e.g. 5–30 minutes with safe cap), while leaving database `lastFetchedAt`/`nextFetchAt` unchanged. Make the limits and resource bounds explicit before handoff. Restart clears cooldown; this is an intentional single-instance limitation, not durable retry certification. Do not suppress manual refresh behind scheduler-only failure cooldown. Catch/log only categorical failures, not provider XML or URLs.
7. **Limits and deployment:** one primary Spring Boot instance (single-process). In-memory source admission/cooldown is **not cross-instance mutual exclusion**; if multi-instance deployment or strict at-most-once scheduling becomes required, `OWNER_DECISION_REQUIRED` for separate DB lease/migration/operational design. Do not claim distributed safety.
8. **Stop/disable:** conditional scheduler component must be absent/idle when globally off; application shutdown must stop scheduling and bounded in-flight jobs cleanly. Disabling per-source scheduled flag blocks further dispatch and—under the scheduled finalizer's authority rule—causes an in-flight scheduled finalization to roll back; manually initiated refreshes remain independent. A valid empty feed may count as a successful fetch only if complete document/parsing/validation succeeded, then `lastFetchedAt` and `nextFetchAt` advance; invalid XML/timeouts do not.

## Compatibility and timing proof

- Existing source create/update accepts any **positive** interval; a new scheduler must **not** silently reject `refreshIntervalMinutes=1` or mutate it to a new minimum. With a 60-second tick, real execution time is **best effort** after due, not an exact-clock promise. Document positive drift from executor capacity, timeouts and app downtime.
- HN S1 fixed 24h Radar, manual endpoint/response and accepted finalizer remain unchanged except for a **separately reviewed, minimum required** scheduled-invocation guard if needed. No scheduler may mutate the HN provider's fixed target or its `ARTICLE_URL` identity.
- Starvation proof: 30 due sources including invalid/unsupported, 5 permanently failing and two busy, repeated ticks eventually visit all runnable; verify no flood on restart and no unnecessary provider calls when global/per-source disabled.
- Concurrency proof: simultaneous manual/scheduled refresh of same source; two different types consuming global capacity; interval edit, type change, RSS URL edit, disable and shutdown mid-fetch. Bounded worker cancellation and admission release. No request/transaction remains open across full HTTP.
- At most one active scheduler owner **within a single process**; no guarantee about multiple JVM instances, app restarts or persistent retry history.

## S2B decision gate

Before issuing S2B handoff, independently verify deployed process count, actual S2A source/provider path, selected fair bounded scan, in-memory failure-backoff semantics, Spring scheduling wiring and *exact* runtime testable constraints. If any requirement implies schema/API/security/accepted S1 behavior changes beyond this prospective scope, stop for explicit Owner decision rather than broadening S2A. S2B implementation and tests are **NOT_RUN** at preparation time.
