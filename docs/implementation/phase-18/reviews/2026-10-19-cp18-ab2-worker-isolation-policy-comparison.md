## 4. Candidate analysis

### A — One unique restricting SID only

**D:** Restricted tokens retain an ordinary SID check and an additional restricting-SID check; both must permit the requested access. Multiple restricting SIDs are not conjunctive gates requiring every SID on every object. The own-primary-token route has a documented SeAssignPrimaryTokenPrivilege exception, not a blanket waiver of all launch prerequisites. [Restricted Tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens), [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw).

**E/K:** This selected synthetic-SID-only configuration is incompatible with the measured file access masks under the captured unchanged DACLs. A functioning worker positive control is absent. Protected-object denial is not useful worker feasibility when Python cannot demonstrably run.

**I:** For an ordinary new object open using this token, an app-owned runtime/input object would need both ordinary rights and an effective grant matching the restricting SID, subject to deny ACEs, integrity and other checks. The same distinction applies to required section/registry/desktop objects, not just executable file ACLs. Grant only read/execute for runtime, read for exact input and narrow scratch mutation; never store/capture access.

Required OS resources have no measured synthetic grant. Changing system DLL/System32/station/host-wide ACLs is prohibited and **not recommended**. Passing an already granted narrow handle can change an individual access path, but is not a demonstrated complete CPython loader/runtime solution; it cannot be used to smuggle an original/store/Java/token handle. Copying system trees or assuming preloaded JVM DLLs solve child initialization is unjustified.

**Readiness:** **NOT READY; measured policy-access incompatibility; exact startup cause U.** No in-scope repair establishing the full required OS object closure has been specified.

### B — Restricted token with system-access principals and protected app objects

Evaluate the smallest descriptor-justified alternatives before considering broader groups. For the four measured file DACLs, **one ARAP restricting SID** (or separately AAP) could supply the missing restricting-pass read/execute match while the ordinary Users grant supplies the ordinary pass. This is **I**, not a tested token or complete OS policy. AAP/ARAP here would be entries in an ordinary restricted token; this does **not** create an AppContainer or its network/window/process rules.

No minimum set for NLS, KnownDLL sections, registry, window station and the full native closure is established. Everyone/Authenticated Users/Users, the caller/logon SID, SYSTEM or TrustedInstaller cannot be justified merely by startup success. RESTRICTED_CODE is not a path allowlist and is not present in these four retained file lists. Do not add the earlier four-SID union or an accumulating fallback list.

If the caller already has restricting SIDs, CreateRestrictedToken documents intersection with the supplied restricting list. The latest caller list is unknown: neither A nor B may assume it can replace inherited restrictions or add effective authority unavailable in that context. Inspect that prerequisite before any separately authorized design proof; do not bypass it through another caller/helper. [CreateRestrictedToken input semantics](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken).

**Known-path READ answer: yes, conditionally.** If an unrelated file grants the selected system-access SID the requested read rights and the ordinary token also permits them, that same restricting-pass grant can permit its read, subject to other effective checks. There is no “system files only” scope on the SID.

For example, assume a reachable unselected file has read ACEs for Users and ARAP, no applicable deny/no-read-up constraint, and ordinary Users remains enabled. A restricting list containing ARAP and an attempt SID can satisfy the file read through ARAP without an attempt-SID ACE. The attempt SID is not an additional mandatory gate. If the file instead has only Users and the list only ARAP/attempt SID, that second-pass grant is absent. Therefore neither “all user files exposed” nor “all other user files denied” is justified. Substituting AAP has the corresponding shared-grant problem; Users/Everyone/Authenticated Users expand it further. This is a reasoned counterexample, not a newly tested host file.

Application-owned store/temp/process objects could use protected DACLs, checked inheritance and narrow denies/grants to prevent the worker's restricting identities acquiring sensitive rights. Both ordinary and restricting lists, owner-implied rights, parent DELETE_CHILD, mandatory labels and pre-existing handles must be considered. A plain owner-only allow-list is not automatically sufficient where Java and worker share TokenUser. The handoff's OWNER RIGHTS/WRITE_DAC/WRITE_OWNER proof remains mandatory; no ability to set another account as owner nonprivileged is assumed. [DACL evaluation](https://learn.microsoft.com/en-us/windows/win32/secauthz/dacls-and-aces), [OWNER RIGHTS SID](https://learn.microsoft.com/en-us/windows/win32/secauthz/sid-strings).

**K:** Protecting only ORIGINAL_BYTES, even successfully, leaves unrelated originals, repository secrets, user data and other applications outside that policy. Changing their descriptors or protecting every future file is prohibited and cannot be replaced with a finite “we tried several paths” claim. Ordinary-group disabling might reduce some access but supplies no per-path distinction where runtime and unselected files share those same grant principals.

**Readiness:** potential runtime improvement, **not an acceptable G3 policy**. Approved-input-only confinement is not established without an additional isolation boundary or forbidden unrelated-file policy changes. No broadening is recommended.

### C — AppContainer and LPAC for the unpackaged worker

**D:** Unpackaged Win32 processes can run in AppContainer through supported APIs; MSIX/UWP packaging, a new account and a service are not inherent requirements. AppContainer identity is orthogonal to elevation/IL; its process is Low IL. This supports considering CPython, not certifying its native dependency compatibility. [AppContainer for legacy apps](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-for-legacy-applications-).

The documented launch uses STARTUPINFOEX plus SECURITY_CAPABILITIES and PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES; LPAC additionally opts out of ALL APPLICATION PACKAGES through PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY / PROCESS_CREATION_ALL_APPLICATION_PACKAGES_OPT_OUT. The ordinary/user and application/capability permissions intersect. Regular AppContainer has ambient system access that LPAC narrows. [Microsoft launch procedure](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer).

**I, prospective policy shape:** attempt-specific package SID P; no document-library/broad-filesystem/full-trust capabilities; no capability added without an identified required object. Explicit P read/execute grants on exact approved interpreter/code/native/model objects; read-only approved input if any file channel; P scratch rights only on its own attempt. Deny store/capture and omit P from every other attempt. LPAC is more relevant than regular AppContainer to challenge ambient AAP access, but still requires accounting for ARAP/capability-accessible objects and its own writable profile. Neither variant is an arbitrary namespace/path allowlist independent of the host's effective grants.

**U:** Current Low caller's existing restrictions, ability to create/use an owned per-user profile, supported LPAC attributes and ability to install/read back app-owned descriptors/labels. CreateAppContainerProfile is per-user and may return E_ACCESSDENIED; documentation does not prove success from this recorded Low context. Do not assume an unrecorded Medium helper or elevate. A fresh profile is a bounded OS resource, not a permanent Windows account. [CreateAppContainerProfile](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createappcontainerprofile).

**U:** Full 3.14.4 base/venv/native imports, model mapping and necessary system/registry/device rights without broad capability grants. Directory grants must not expose neighboring repository/user files. Native dependencies may need object access beyond the four measured DLLs. No AppContainer/LPAC worker has been run in this record.

**K/U — current transport:** The worker must both accept Java's loopback HTTP and initiate PostgreSQL loopback TCP. AppContainer network isolation is an additional constraint; internet/private-network capability names do not establish these exact loopback flows. Microsoft's IPC guidance describes default loopback blocking and administrator/debugging exemptions for interaction with unpackaged applications. That packaged guidance is not a host-specific proof for this manually created profile, but it supplies no defensible nonprivileged drop-in exception here. The loopback-config API is a debugging allowance and requires preserving existing global entries; it is not an exact Java/DB-port sandbox grant. No exemption/global network change is proposed. [Microsoft IPC/loopback guidance](https://learn.microsoft.com/en-us/windows/apps/develop/communication/interprocess-communication), [NetworkIsolationSetAppContainerConfig](https://learn.microsoft.com/en-us/windows/win32/api/netfw/nf-netfw-networkisolationsetappcontainerconfig).

Named-object IPC or broker-created sockets are narrowly relevant alternatives **within C's transport analysis**, not selected architectures. Windows documents targeted socket sharing via WSADuplicateSocket; that does not establish an AppContainer loopback bypass or existing uvicorn/psycopg adoption. Current Java HTTP client, uvicorn launch and psycopg connection() do not implement such a handoff. Both transport directions, one-use claim-before-body and restricted physical staging COMMIT would need an explicit adapter design and separate authority. No generic privileged broker, SQL proxy taking over worker authority, package conversion or weakened DSN restriction is authorized. [Socket-sharing API and lifecycle](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsaduplicatesocketw).

**I/U — process/desktop/lifecycle:** AppContainer adds documented process/window isolation, but dangerous handles and permissive IPC still require exclusion. Preserve no inherited sensitive handles, suspended attestation, job assignment and durable identity before resume; production maxProcesses=1, positive tree/task stop and drain. Regular AppContainer isolation is not permission to reuse the diagnostic default desktop without reviewing the handoff's private-desktop requirement. Verify the actual station/desktop and supported confined execution; no station ACL change or process-wide station switch in the JVM. Per-attempt profile/registry/temp resources must be inventoried and removed only after quiescence; no cross-attempt profile reuse as a shortcut. [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation).

DeleteAppContainerProfile success alone cannot prove erasure of externally granted runtime/scratch objects or removal of all attempt ACL entries. Close profile handles first; incomplete deletion is pending/unknown. [Profile deletion](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-deleteappcontainerprofile).

**Readiness:** supported mechanism; promising isolation properties; **no complete in-scope runtime/transport/access policy established**. LPAC is the more pertinent variant to examine if a separate transport-design scope is approved. No selection or execution follows.

Low IL/UIPI, a private desktop, Job Object and child-process mitigations are supporting controls, not a fourth filesystem-read sandbox. Default MIC is no-write-up, not no-read-up, and cannot distinguish approved/unselected files at the same label. A Low caller cannot simply manufacture a trusted Medium context. [MIC](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control). Job limits supervise lifetime/resources; they do not select readable paths. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). No unrelated framework, driver, permanent account or service is justified by the present evidence.

## 6. Process, token, desktop and handle feasibility

The required per-right evidence remains: PROCESS_VM_READ/WRITE/OPERATION, DUP_HANDLE, CREATE_THREAD/CREATE_PROCESS, process/thread/token security changes, and TOKEN_DUPLICATE/IMPERSONATE/ASSIGN_PRIMARY must deny against actual Java and a valid controlled trusted peer. QUERY_LIMITED_INFORMATION/TOKEN_QUERY, if deliberately allowed, are observations rather than authority takeover. Error 6 from a NULL token/process argument is invalid evidence. A failed process-open prerequisite must not be reported as an executed token test. [Process rights and duplication risk](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights).

Keep bInheritHandles=false. Any future narrowly transferred handle would require an explicit inventory, rights/type/object binding, revocation/lifetime and a separately reviewed handoff; an inherited/read-mapped store file is a confidentiality failure even if later pathname opens deny. Windows provides explicit startup handle-list attributes, but no such production transfer is currently implemented or authorized. [Process/thread attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

No candidate may obtain unrestricted peer tokens, duplicate Java handles, exploit permissive named IPC/impersonation, or create an unrestricted descendant. Remove unneeded privileges deliberately; retain SeChangeNotifyPrivilege only with truthful traversal accounting. WRITE_RESTRICTED omits the needed read boundary and is unsuitable; SANDBOX_INERT is not confinement. [CreateRestrictedToken flags](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken).

Microsoft warns restricted-token applications against sharing the default desktop.
