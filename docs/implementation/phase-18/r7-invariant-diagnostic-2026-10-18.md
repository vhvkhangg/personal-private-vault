## Microsoft guarantees and applicability

These primary documents were reviewed for this diagnostic on 2026-10-18. Documented guarantees, observed host results and untested assumptions remain distinct:

- [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) documents bidirectional sharing compatibility, existing writable mappings, and sharing options lasting until handle close. It explicitly excludes attribute/extended-attribute access from the sharing restriction. This supports the bounded **data-access** fence, not a universal metadata or namespace freeze.
- [CreateHardLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw) and [hard links/junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions) explain multiple names for one file, per-file sharing and directory-entry metadata behavior. They support no independent data-write permission from an alias. Observed DELETE-capable alias handles and alias-only POSIX changes prevent extrapolating this to “every namespace open fails.”
- [BY_HANDLE_FILE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information) describes volume/file ID comparison, link counts and timestamps; IDs are not globally permanent historical authority. [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew) supplies an observation of the current handle's name, not a lock on every ancestor.
- [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle), [FILE_INFO_BY_HANDLE_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ne-minwinbase-file_info_by_handle_class), [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), [extended rename semantics](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information), and [extended disposition](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex) identify operation-specific rights/flags. POSIX replacement can preserve old handles while changing a name's target in supported circumstances. It did **not** replace this guarded original in B6; it **did** replace only the alias in A6. Driver-level documentation does not imply all described flags/classes succeed via every user-mode call or host combination.
- [SetFileTime](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfiletime), [FILE_BASIC_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_basic_info), [SetFileAttributesW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileattributesw), and [file access rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights) distinguish write-data and write-attributes rights. Actual successful metadata calls refute a blanket sharing-based freeze; the documents do not decide which metadata the vault's consent/version contract authorizes.
- [Reparse points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points) and [FSCTL_SET_REPARSE_POINT](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_set_reparse_point) establish redirection and its native operation. D1 shows this host allowed the controlled mount-point operation without requesting elevation; B12's nonempty-directory failure does not prove general prevention. No privilege/security policy was changed. [OpenFileById](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-openfilebyid) was reviewed for identity/namespace distinction; it was **not** used or selected as a replacement guard design.
- [CreateFileMapping](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createfilemappinga) documents mapping protections/access compatibility. The harness calls the W variant with matching signature, real mapping and view APIs. A denied prerequisite open is distinguished from an executed mapping; W2 executes and retains the mapping first.

No Microsoft guarantee reviewed makes the current path-based check sequence atomic with the later open or proves its root/ancestor binding through C. No failed data-write attempt is treated as that missing guarantee. Fresh hashes, final link counts, file watchers, polling, callbacks or cached bytes provide no continuous substitute.

Fixture cleanup removes only verified owned subtree and never follows junction contents. Harness/compiler outputs remain ignored. A setup/host unsupported operation is NOT_VERIFIED, never a pass through a simpler API.

Native return success means operation executed, not invariant PASS. API not reached after denied open is recorded separately. A bounded predicate can be PROVEN only with actual observations plus applicable Microsoft documented semantics; finite examples are not universal race proof. All required but absent evidence yields NOT_VERIFIED. A reproduced authority violation yields FAIL/DISPROVEN. An incidental alias or bookkeeping change is not automatically FAIL.
