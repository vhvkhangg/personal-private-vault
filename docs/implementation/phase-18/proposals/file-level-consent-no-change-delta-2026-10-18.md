## 2. Exact proposed whole-file consent contract

The following **WF-1–WF-8** are proposed normative replacement text. They define the delta precisely; they are not implemented APIs, DB enums or owner approvals.

**WF-1 — Individually approved whole file.** The authenticated single owner MUST explicitly select and approve each external file for one finite import/update intent. The grant authorizes capture, retention and supported RAG processing of the **complete file**, including private/NSFW-marked material, hidden text/sheets/rows/cells, comments, properties, frontmatter and metadata within that file. For this source class, NON_PRIVATE/non-NSFW content classification and per-field/paragraph/region/worksheet approval MUST NOT be independent admission, retention, extraction or publication gates. A document's `private:true`, NSFW label, unknown custom property or hidden flag is **data, not a withdrawal of this grant**. No permission to read an unselected source follows.

**WF-2 — Finite source binding and one consent action.** Java MUST bind the explicit action to the target S (or first import), expected current selection/reset/authorization/policy state, allowed root, approved object/ancestor provenance and capture intent. That action authorizes one coherent complete byte stream of that correctly bound selected object in this finite operation; Java binds the resulting exact digest/length and R to the recorded whole-file grant at sealing. There is no second hidden-field/metadata/final-projection approval. Stale supplied expectations, unknown source identity/authorization, revoked/suspended source or acquisition mismatch MUST deny; a post-copy hash cannot authorize whichever object happened to open. A renewed approval after revoke remains a separate explicit authority action, never inferred from an ordinary Update command or equal bytes.

**WF-3 — Exact original-byte snapshot.** The managed snapshot payload MUST be exactly the approved captured original bytes, without privacy projection, normalization, reserialization or metadata stripping. Java MUST retain SHA-256, byte length, original provenance, consent/reset/authorization/policy binding and immutable revision/closure identity. Original and stored payload byte digests/lengths MUST agree; separate metadata/manifests are not included in the original-file digest. An old field-safe projection is not an ORIGINAL_BYTES snapshot merely because its metadata records an original digest. G1/G3/G4 protections and fresh authority remain mandatory before worker admission.

**WF-4 — Safe supported processing, no execution permission.** After approved sealing and fresh reserved one-use admission, the restricted indexing worker MAY read the complete approved file input and extract any supported in-file content. Consent is whole-file; extracted elements still carry exact source/revision and structural roles/locators. Approval MUST NOT execute scripts, macros, formulas, Dataview, embedded executable code, remote requests or external-link resolution. Document instructions are data. Resource/archive/format validation, parser isolation, finite expansion and material-fidelity failure remain mandatory. Unsupported in-file structures must be reported honestly under existing material-failure/coverage rules, not silently labelled excluded for lack of field consent. No new parser platform or engine is selected.

**WF-5 — Separate external children.** An independently accessed external file, Obsidian transclusion, linked resource or other source object MUST have its own explicit file/source approval and exact S/R/provenance. A path inside an approved directory or a link in approved content is not consent. Store reference text as inert data where supported; do not fetch targets automatically. Required authorized dependency closure, cycles, missing/unsafe targets, conflicting revisions and exact child attribution retain their existing rules. Bytes physically contained in an approved file are within its whole-file scope and may be interpreted as bounded inert in-file structures; that does not authorize opening an external target, executing an embedded object or inventing an independently approved child identity.

**WF-6 — Real denials and incident ordering.** Explicit RAG revocation/removal/suspension, missing or forged grant/source, stale reset/authorization, wrong root/object, managed-store corruption, unknown transaction/history, unauthorized external child and genuine authority uncertainty MUST still deny. Document-private/NSFW/hidden/metadata discovery alone MUST NOT create a denial, revoke, reset or incident for a valid whole-file grant. The reviewed proposal's D5 source-scoped deny-only incident fence, C_D/C_P ordering, true cancel-first revoke C_R, child-specific scope and unknown-outcome recovery remain proposed for real authority/integrity incidents. Ordinary parse/OCR/resource failure alone does not manufacture one. Vault-source privacy and field vetoes remain frozen and unchanged.

**WF-7 — NO_CHANGE.** An explicit manual Update MAY return NO_CHANGE only under every predicate in section 5, using SHA-256 and length of exact freshly captured original bytes and the verified selected ORIGINAL_BYTES snapshot. It MUST NOT allocate a new R/ordinal, increment sourceVersion, renew/reset consent, promote a generation, run OCR/parsers/embeddings or silently change a closure solely for that update. It MUST safely dispose of the new temporary capture and preserve snapshot-relative currentness with `originalFreshness=UNVERIFIED`. Equal content without valid authority is never NO_CHANGE permission. Changed bytes follow a newly approved immutable-revision path; explicit same-R reindex follows section 5 case C.

**WF-8 — Producer/publication/purge preserved.** Original-file SHA-256 MUST NOT replace exact input/scope/producer/output/locator/vector/model verification. Actual restricted worker provenance, immutable sealed staging, attempt fences, positive task/tree death, writer drain, one trusted Java physical PostgreSQL publication C, rollback and genuinely unknown-C reconciliation remain mandatory. Whole-file scope does not permit unrestricted raw content in logs, reports, public paths or exports. Revocation purges controlled whole-file snapshots and actual transitive derivatives under the reviewed channel-qualified policy; no immutable or equal-hash copy resurrects authority.

The proposed `WHOLE_FILE` consent scope is a discriminated logical contract, not an existing field name or a wildcard over business modules. A later wire/manifest version must make it explicit; unknown/legacy consent modes deny rather than infer whole-file approval. Legacy `approved_field` attribution may become a structural element kind for this source class, but cannot be mistaken for a new per-field permission requirement. Domain/Vault manifests retain their actual field scopes.

## 4. SHA-256 and digest separation

**Proposed selected algorithm: SHA-256 over the exact complete original byte stream, with byte length.** Compute it as bytes are captured from the protected stream. Do not trim spaces, rewrite CRLF/LF, transcode, normalize Unicode, decompress/repack the Office container, parse then hash extracted text, or substitute a file's name/timestamp. Hash the selected stored ORIGINAL_BYTES snapshot under G3's protected coherent integrity proof too. One-byte/one-space/newline/encoding/container-metadata changes are content changes even if rendered text is identical.

SHA-256 is deterministic cryptographic content-integrity/change comparison. Equality is relied upon under its cryptographic collision-resistance properties, **not a claim that collisions are mathematically impossible**. Length equality is an additional check, not authorization. No adversarial collision experiment or new cryptographic infrastructure is requested. BCrypt and Argon2id are password-hashing schemes; they are not selected for deterministic file content comparison. No password/security subsystem is changed.

| Digest / binding | Meaning; never substitute for another |
| --- | --- |
| `originalBytesSha256` + length | Complete freshly acquired original stream; stable sealed payload must match these bytes/digest/length. |
| Snapshot storage integrity | Protected selected R's exact stored original bytes verified against its trusted digest/length; a cached string without G3 integrity continuity is insufficient. |
| Manifest/closure/scope digest | Typed original provenance, S/R/consent/reset/authorization/incident/policy and actual child edges/revisions; not the file's content hash. |
| Worker input digest | Exact versioned Java-approved transfer envelope/bytes, including all identity/default/version fields; not simply the file hash. |
| Canonical producer/output digest | Exact actual sealed outcomes/chunk text/excerpts/structural locators/vectors/pipeline and real producer/attempt provenance. FR18-3 remains; an input-only or count-only output digest is insufficient. |

Keep sensitive raw hashes/provenance within authorized storage; no public content-addressed URLs, cross-source deduplication, shared blob ownership or hash-derived consent. Metadata records may be updated for safe operation receipts, but a validation timestamp is not a source revision or live-current certificate.

## 5. Exact NO_CHANGE, changed-input and reindex contract

### 5.1 Conjunctive NO_CHANGE predicate

For manual Update U explicitly targeting selected S/R1, return NO_CHANGE **only if all are freshly proved**:

1. Authenticated explicit whole-file Update intent targets the verified logical S and the authorized original/root/object/ancestor binding. No hash-only first import, source merge, same-path replacement or auto-rebind; supplied stale intent denies.
2. A new finite protected capture produced exact original bytes with length L and SHA-256 H; no parse/normalize/OCR/embed was used to decide equality.
3. R1 is a selected, present, legitimate **ORIGINAL_BYTES** immutable snapshot. Its protected actual bytes independently verify to the trusted selected length/digest, and those equal L/H. A projected-only legacy R, purged/missing/tampered store or unverified digest is ineligible.
4. Current whole-file consent, reset/authorization/incident state, policy version, retention, selected-R/sourceVersion and update expectations all remain valid. No grant expiry/revoke/suspension, pending uncertainty, compromised history or conflicting operation is bypassed.
5. The complete required dependency topology and independently authorized child S/R versions are still valid for the intended selected generation/closure, with no removed/readded edge or promoted/denied child hidden by today's equal bytes.
6. Relevant selection/pipeline/producer validity for the intended retained index has not changed. NO_CHANGE must not disguise an absent/invalid generation or an explicitly requested pipeline reindex; that requires the appropriate same-R reindex/authority resolution, not a useless new file revision.
7. The final check is serialized under existing source-first guards, exact operation reservations/attempt fencing and protected managed objects against consent, child, incident and concurrent selection changes. No stale prepared equality can win over a fresh denial. All required proofs missing/unknown => no NO_CHANGE success.

**Effects:** preserve S/R1, R ordinal allocation, sourceVersion, selected generation/pointers, consent/reset/authorization and actual closure. Allocate only bounded operation/temp/receipt identity as needed, **not a snapshot revision or revision ordinal**. Do not rerun parsers/OCR/embedding or publish a generation solely for this comparison. Dispose of the new temp after validation under safe task/writer proof; never adopt it as a hidden revision. Original freshness remains **UNVERIFIED**, even immediately afterward.

Whole-file content consent for U does not silently renew a revoked source or prior field-projected R. If owner explicitly renews/rebinds/migrates authority, that is a separately recorded authority change, not a hash-equality shortcut. A later valid Update may qualify only after all new expectations match. No original-to-projected equality shortcut is permitted.

### 5.3 Guarded finish, batching, crash and reporting

NO_CHANGE is a proposed **manual update/per-file disposition**, not a new DB job status, published generation or evidence of OCR success. Use the existing G4 capture/exclusion/reconciliation boundary, not a second coordinator. Prepare capture/storage hashes outside SQL row locks while their byte/identity protections remain; a short source-first writable finish validates all current predicates, records the no-change outcome and known operation result, and releases the exact capture union only after positive capture-task/writer safety. Call its actual PostgreSQL COMMIT **C_N**, distinct from publication C_P and incident/revoke C_D/C_R. It installs no selected revision/generation. Unknown C_N retains exclusion/reservations for reconciliation; no optimistic success, blind copy retry or implicit indexing. The managed-object proof must remain valid through the decision; no file hashing/process wait under SQL locks.

Safe release may precede physical temp erasure only after every consumer/writer is impossible, as in the reviewed purge contract. A known NO_CHANGE outcome must separately report pending/failed cleanup if erasure is unverified; never claim temp deletion or controlled PURGE_COMPLETE from equality. Unresolved transaction/authority outcome cannot be reported as confirmed NO_CHANGE. Current R/G are independently checked and cannot use pending uncertainty as fallback.

For an all-NO_CHANGE update, do not launch an indexing worker or synthesize a zero-generation `COMPLETED` indexing job. Reconcile/finish the existing nonpublication capture operation under G4; this delta adds no job state. In a mixed changed/unchanged multi-file workflow, retain every selected root and exact required reservation union in the immutable operation roster; mark unchanged roots explicitly, never silently discard them. Only changed/reindex work is sent in the exact authorized worker plan. Java must verify each NO_CHANGE decision independently; the worker cannot assert it to skip required output. Keep reservations for the entire admitted union until the appropriate known atomic finish; no early release of unchanged members. A later child/authority change before finish invalidates a prepared NO_CHANGE decision.

The one final indexing C publishes all validated new generations or none, records changed/failed/unchanged file outcomes and releases the entire indexed union under unchanged shared-trust rules. Counts of new published generations exclude NO_CHANGE. Existing COMPLETED/ABORTED/CANCELLED/RECOVERY_REQUIRED semantics and report-only PARTIAL_SUCCESS remain; NO_CHANGE does not turn zero new publication into COMPLETED. Later implementation must prove the precise existing-attempt mapping under G4, not invent another job engine or prematurely terminalize a live attempt. Reports distinguish `updateDisposition=NO_CHANGE`, `publishedNewGeneration=false`, selected R/G and freshly computed `SNAPSHOT_CURRENT`/other state with `originalFreshness=UNVERIFIED`; no new receipt grants read authority.

This is planning only. The later minimal change is a discriminated whole-file grant/exact-original snapshot mode, simplified capture/seal, protected streaming SHA-256/length comparison, explicit no-change operation finish/report, and exact producer/locator/closure integration in existing Java/RAG/Python boundaries. Trade-offs are explicit: whole-file consent intentionally permits material previously excluded for privacy classification/field policy, because the single owner selected that file. It reduces projection/consent complexity while increasing retained/processable content; file approval remains bounded and revocable, not permission for unauthorized disclosure or unrelated source access. SHA-256 avoids expensive comparison of decoded text and supports deterministic integrity; hashing/copying full bytes still has finite disk/CPU/time cost. NO_CHANGE saves revisions/OCR/embeddings only when **both content and authority** remain valid. Same-byte content cannot cure lost/changed policy, an invalid index or a revoked source. Keeping the original unchanged on disk says nothing about current approved child authority or the live original after capture.

The old amendment's successful ISAR re-review is reused only for unaffected contract boundaries. This delta deliberately changes reviewed ISAR-1's permission model and D5's content-trigger assumptions; it requires **its own separate independent focused review**, not an author declaration of readiness. No new policy is active before explicit owner contract approval and separately authorized canonical synchronization; those still do not automatically authorize implementation.
