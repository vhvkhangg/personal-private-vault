## 3. Proposed normative replacement contract

**Everything marked N below is proposed normative text, effective only after explicit approval and canonical synchronization.** Sections 4–12 define its terms and exact edge cases. Section 13 maps each changed obligation; section 14 specifies future evidence. No normative wording in this file changes current behavior.

**N1 — Source ownership.** An external document MUST enter Phase 18 only as an individually approved RAG-owned snapshot source, distinct from both its original external reference and any Vault source. Java MUST own its stable identity, immutable revisions, consent/reset/field epochs, reservations, selection and purge. A path, native object ID or content hash alone MUST NOT create, merge, renew or restore authorization.

**N2 — Safe intake and approval.** An explicit owner command MUST bind one selected allowed source/root/object/ancestor and finite intake intent to proposed `RAW_QUARANTINE_CUSTODY`. That permission and a distinct trusted-inspection scope MAY temporarily hold/inspect otherwise unapproved container fields only under sections 8/10; known prohibited sources remain denied and unknown classification never becomes eligibility. This is a **NEW proposed Phase 18 P17-2 applicability exception requiring D10 approval**, not indexing consent. Exact final consent MUST instead bind only the field-safe sealed S/R representation, retained/worker fields, original-to-snapshot mapping and closure/digests/epochs, with stale-intent CAS. Raw quarantine MUST be deleted before indexing eligibility. No ordinary Python worker may access raw or preapproval content; final input admission and derivative publication retain their separate N6/N8 gates. Unsupported acquisition, classification, separation, mapping or integrity MUST deny; no naive copy/hash/alias check suffices.

**N3 — Immutable revision.** Successful intake MUST produce a new immutable revision ID and integrity/provenance manifest under a RAG source ID. Once sealed, content, retained metadata and dependency edges MUST NOT change in place. Immutability MUST be enforced for supported application/worker access, not asserted from a read-only attribute. Deletion remains possible under policy. Original handles MAY be released only after capture/sealing obligations are satisfied; snapshot integrity and Java authority MUST then remain protected through worker use, publication and subsequent authorized lifetime.

**N4 — Explicit manual update.** Only an owner-initiated import/update/reindex MAY acquire new external bytes or select a new revision. No watcher, polling result, original edit/delete, startup, retry, hash equality or recovered candidate MAY automatically reimport, reapprove or promote. Each update MUST obtain fresh exact revision/field/dependency consent and compare current source/reset/authorization/selection expectations. Revision selection and new generations MUST become effective together at the single final C. Ordinary failure/cancellation MUST leave prior selection intact; previous-generation use additionally requires no implicated durable incident/uncertainty fence under section 8. Candidate-only rejection MUST NOT by itself invalidate trustworthy R1; an incident fence is not a committed revoke.

**N5 — Qualified freshness.** External snapshot generations MUST expose `freshnessBasis=RAG_SNAPSHOT`, exact source/revision/generation IDs, effective `snapshotIndexState`, and `originalFreshness=UNVERIFIED`. `SNAPSHOT_CURRENT` MUST mean only the predicate in section 6. An unqualified external `CURRENT`, `liveCurrent=true`, or a live-original freshness claim inferred from a snapshot MUST NOT be returned. Vault CURRENT retains its frozen meaning. A historical successful job MUST NOT imply either kind of currentness.

**N6 — Consent/revoke.** Every indexing root/child MUST independently satisfy current NON_PRIVATE/non-NSFW eligibility and exact item/field/revision approval. Unknown source classification or unresolved restrictive authority denies; safely separable unapproved nonrestrictive fields may be omitted. N2's raw-custody exception permits neither eligible retention nor indexing. Normal reserved source/privacy/field/revoke mutations MUST still conflict without committing, preserving cancel-first. Separately, section 8 proposes a **narrow NEW Phase 18 deny-only incident-fence exception**: implicated snapshot reads/admission/transfer/publication MUST fail closed against durable source-scoped uncertainty, including while reserved. Its physical denial COMMIT C_D orders against actual publication C; failed/busy revoke or process ACK is never revoke. Only a later successful explicit revoke/privacy/reset C commits that mutation and requires transitive purge. Incident resolution cannot resurrect old revoked authority; all exceptions require explicit owner approval, preserve Vault behavior, and remain unimplemented.

**N7 — Multi-file closure.** Admission MUST atomically reserve the exact union of distinct approved roots and all actual authorized children before any one-use indexing input. Each generation MUST retain its own immutable closure separate from that union. Capture consistency MUST be an explicitly approved vector of separately sealed revisions, not a claim of simultaneous live-filesystem capture. Shared-child updates/revocations MUST invalidate exactly true dependent generations; unrelated siblings MUST retain independent validity. Root and child content MUST keep exact owning revision locators.

**N8 — Producer/publication.** The versioned document producer contract MUST bind the full tuple in section 12 to exact input and immutable staged outcomes/chunks/vectors/locators. Actual restricted worker provenance, one-use grants, attempt fences through S physical C, positive worker/task/tree stop, writer drain/seal and trusted Java verification remain mandatory. One Java PostgreSQL physical C MUST publish all valid successes or none, record outcomes, terminalize and release the exact union atomically. E1, rollback and genuinely unknown-C recovery remain unchanged. Snapshot capture/sealing is not publication and MUST NOT be represented as a distributed transaction with PostgreSQL.

**N9 — Retention/recovery.** Selected authorized revisions and revisions still required by a legitimate actual closure/active attempt MAY retain field-safe content under the minimal policy; N2 permits raw quarantine solely for its finite custody purpose. Pending/failed/unreferenced/replaced data MUST enter bounded verified cleanup. Revocation overrides retention/references. Controlled-copy purge MUST verify active SQL derivatives and managed snapshot/projection/temp/orphan absence with no possible writers; deletion failure remains pending. Reports MUST distinguish that completion from PostgreSQL backups/WAL/remnants and owner copies outside direct erasure control, per section 9's artifact/channel table. Restart MUST recover unresolved incident fences without fallback, and never auto-index/promote; missing store or uncertain/restored authorization history MUST deny pending reconciliation/renewal/manual action.

**N10 — Unaffected acceptance.** All supported formats, Obsidian behavior, languages, native/scanned/mixed PDFs, scanned-table/merged-cell fidelity, mandatory locator/held-out oracle, one chunker/model, offline/GPU/fallback, separate 16 GB RAM/8 GB VRAM, measured finite CPU/time/disk/work limits, cancellation/reporting and the single complete P18-FINAL gate MUST remain mandatory. Live-original R7 evidence alone is proposed for deferral/replacement as precisely mapped below; no original FR18 finding is closed.

## 4. Three identities, revision and authority model

These are **logical fields/states proposed for later design/DDL**, not claims of existing APIs, enums, columns or classes.

| Object/value | Exact meaning and mapping |
| --- | --- |
| Original reference `O` | Opaque RAG intake-reference ID, selected root alias, supported native acquisition identity/ancestor chain and capture time/attempt. Path is private provenance, not a public ID or enduring authorization. O records what was selected/captured, never that the live object still exists. |
| Snapshot source `S` | Fresh server-generated UUID per explicit first import of a logical RAG document. Distinct from O, Vault ID and digest. Owner update explicitly targets S with expected selected revision/authority. A different explicit first import creates a different S even for identical bytes/path. No implicit deduplication or cross-source shared bytes. |
| Snapshot revision `R` | Server-generated immutable revision UUID plus monotonically allocated per-S ordinal, never reused after failure or purge. A successful update of S creates a new R under the same S, not a new S. Failed attempts may leave ordinal gaps. Replacing the physical original at the same path requires a newly observed O/intake binding and explicit confirmation to attach its new R to S. |
| Digests | Separate SHA-256/length for acquired original stream, sealed stored representation, exact approved worker input and closure manifest. If representation is byte-identical, record equality; if scope projection transforms it, retain exact versioned original-to-snapshot mapping and distinct hashes. Digests are sensitive, not public anonymous identifiers. |
| `sourceVersion` | Monotonic RAG authority/selection revision; advances on committed selected-R replacement or relevant graph/scope authority changes, not on observed original timestamps or pending intake. Never reused/decremented. Overflow/missing history denies. Allocation ordinal and sourceVersion are different. |
| Source reset/authorization | Retained consent-reset watermark and source authorization epoch invalidate all affected revisions on revoke/privacy/reset. They never roll back on content restore. Source-wide veto dominates all revision grants. |
| Revision consent | Fresh consent ID/epoch bound to S/R/digests, exact retained and worker field scopes, classification, closure/edge scope, expected source/reset/global epoch and policy. Approval of pending R does not silently alter the selected R or invalidate an independently authorized v1. Candidate-specific policy cannot loosen a source-wide veto. |
| Field/dependency policy | Versioned exact fields/regions and dependency edge/span selection; no wildcard from directory/parent consent. Global narrowing invalidates affected old grants. Pending revision-only choices take effect only for that revision at promotion. |
| Selected revision | At most one selected R per S. Pending approval is not selection. On first successful publication, set R1; on successful update, CAS from R1 to R2 together with generations at C. No independent earlier pointer promotion. |
| Generation `G` | Immutable derived index ID for a root S/R, exact child S/R versions/consents/fields/edges, producer/input/output and pipeline identity. Manual reindex of the **same** sealed R can create a new G without acquiring external bytes; no revision promotion or consent renewal is inferred. |

To avoid an ambiguous double epoch, revision-grant epochs and the source-wide authorization epoch MUST be compared separately. A pending grant may be new while the source-wide epoch remains unchanged. At final C, verify the pending grant, global vetoes and expected previous selection; compute/store the resulting sourceVersion and all affected closure versions consistently in the same transaction. No generation may refer to the pre-promotion sourceVersion as if it were post-promotion current.

## 5. State transitions and owner-initiated updates

Capture state is distinct from indexing/job state. Proposed revision transitions:

`OWNER_SELECTED -> CUSTODY_AUTHORIZED -> RAW_QUARANTINED -> TRUSTED_INSPECTION -> FIELD_SAFE_CANDIDATE -> SEALED_PENDING_APPROVAL -> EXACT_REVISION_APPROVED -> INDEXING_ELIGIBLE -> SELECTED`

These are proposed logical states, not new indexing job enums. Section 8 defines permissions, principals, raw-byte lifetime and cleanup at each state. Existing references below to `SEALED_APPROVED` mean EXACT_REVISION_APPROVED only; indexing eligibility additionally requires verified raw deletion and fresh admission predicates.

Any preselection state can instead become `REJECTED`, `CANCELLED` or `PURGE_PENDING`; selected data can become `SUPERSEDED`, `REVOKED` or `INTEGRITY_FAILED`, then `PURGE_PENDING -> PURGED`. Approval is invalidated if any bound bytes, provenance, scope or authority changes; a new immutable R/approval is required. No transition out of PURGED/REVOKED restores old consent. Quarantined data is never index-readable. “Sealed” means immutable storage, not eligible authorization; only **SEALED_APPROVED plus all fresh admission predicates** permits indexing. Selection requires publication C.

Generation lifecycle remains candidate/staged/sealed/verified/published-or-discarded under the existing job. Effective `SNAPSHOT_CURRENT`, `OUTDATED`, `REVOKED`, `UNAVAILABLE` and `ABSENT` are read results, not new job statuses. Proposed snapshot states MUST NOT be inserted into the frozen job enum. Existing `COMPLETED`/`ABORTED`/`CANCELLED` and nonterminal `RECOVERY_REQUIRED` remain; `PARTIAL_SUCCESS` remains report-only.

| Event | Exact proposed result |
| --- | --- |
| First import | Explicit selected intake/custody permission, safe capture, sealed preview, exact per-file approval, reserved indexing, verified atomic publication selects R1/G1. Failure leaves no selected generation. |
| Original ordinary edit | S/R1/G1 unchanged. Independently authorized G1 may remain SNAPSHOT_CURRENT. Original freshness stays UNVERIFIED. No background read/import. |
| Original move/rename/delete/inaccessible | Same result; provenance is historical. A later owner update must explicitly select/acquire an allowed object again. These events do not imply RAG removal under the recommended policy. |
| Update R1 -> R2 | Owner explicitly targets S/expected R1, selects the current original, renews exact approval for R2/children. Pending R2 does not change selected sourceVersion or G1. Success promotes selection and all valid new generations at C; G1 then becomes superseded/OUTDATED and enters cleanup unless another authorized actual closure requires R1. |
| Ordinary update extraction/OCR/resource failure or cancellation | R2 never CURRENT; cleanup failed R2/candidates. G1 remains usable only if fresh snapshot/consent/closure/retention predicates independently pass **and no implicated incident/uncertainty fence is pending or committed**. Ordinary failure alone creates no privacy incident. Report “update failed; selected revision R1” with UNVERIFIED original freshness; never present G1 as updated content. |
| Restrictive/private/NSFW/unknown-policy finding in new intake | Reject R2 and stop its processing. **Candidate-only** restriction with independently trustworthy R1 leaves R1 usable. Credible uncertainty about S/R1/approved fields/consent or actual child authority instead requires section 8's durable deny-only incident fence C_D, denying affected old reads and publication while true cancel-first revoke remains pending. Shared-child scope follows actual manifests; unrelated siblings stay unaffected. Failed/busy revoke never clears the fence or counts as committed revoke. D5 must explicitly approve this narrow exception. |
| Suspected store corruption or uncertain authorization/history | Deny affected snapshot/generations as UNAVAILABLE or REVOKED as applicable; reconcile/purge. Ordinary refresh-failure fallback does not apply. |
| Identical-byte update | Still new R/ordinal and fresh exact approval; identity/consent never inferred from hash. A transport retry with the **same** intake intent ID is idempotent and cannot create another accepted revision. No physical cross-source deduplication proposed. |
| Change -> restore or historical replay | Old R/G never automatically reselected. Explicit update imports the currently acquired approved bytes as a new R even if equal to R1. Old consent/reset histories remain invalidated. |
| Concurrent updates | Use the existing single active job/operation admission and CAS expected selection/epochs; a second conflicting operation returns bounded conflict, no queue or automatic retry. Pending intents cannot bypass the active slot to process files. Late attempts cannot promote over a newer R. |
| Reapproval after revoke | Requires safe release, fresh current source/reset/global epoch, new exact intake/revision approval and new G. Purged old R is not reused; inaccessible retained old R is not silently revived. No automatic roll-back to a historical generation. |

No second job engine is proposed. A later implementation must bind finite capture bookkeeping/cancellation to the existing single-operation exclusion, source reservations and reconciliation. A capture consumes only its explicit finite custody set (no transcluded child content); each newly selected child requires its own authorized capture. Each capture reserves that entire custody set before bytes are read, retains it until positive capture-task/writer stop and a known guarded release, and finishes before another operation begins. Once the complete approved closure exists, indexing admission reserves its full union before Python receives anything. Capture success is a snapshot-state result, never a `COMPLETED` indexing result without published generations. Capture must not create another active slot, queue or autonomous coordinator. Exact reuse of existing attempt bookkeeping is an implementation-readiness gap G4; if safe reuse cannot be established without another engine, STOP.

## 6. Exact CURRENT and reporting predicate

For an external generation G, `SNAPSHOT_CURRENT(G)` is true only if a fresh trusted read proves **all** of:

1. G is the selected active published generation for its root S/R, with known legitimate final C, sealed attempt and exact verified producer/result/pipeline manifest.
2. Root R and each actual child revision are still selected for their respective sources and present with valid integrity/protection; the exact immutable closure/edge/field scopes match the generation. A child selection change makes old dependent parents OUTDATED, even when old bytes remain.
3. Current source and revision consent, reset, authorization epoch, field policy, classification and explicit retention/selection scope match the captured manifest. Private/NSFW/unknown/revoked/missing proof denies before content/counts; unapproved but nonrestrictive safely omitted metadata is not a source-wide veto.
4. Fresh reads query the source-scoped incident/uncertainty state and monotonic incident fence for **every actual root/child**, in addition to normal authority. No implicated pending-disposition inspection, ACTIVE/UNKNOWN incident, integrity failure, authority suspension, purge requirement, replay or unknown-history condition permits use. A failed/busy revoke cannot authorize fallback while that fence remains. Completed work TTL/session/boot expiry alone does not invalidate a valid persistent index.

This predicate contains **no live-original equality/existence check**. `originalFreshness=UNVERIFIED` remains mandatory even immediately after capture: capture evidence describes its intake interval, not today's live state. A future live check could report a separate time-scoped observation only under a separately approved feature; no `LIVE_CURRENT` feature is proposed here.

Proposed external report/API semantics MUST include safe S/R/G IDs, revision ordinal, `freshnessBasis`, `snapshotIndexState`, selected-versus-pending revision, `originalFreshness`, capture provenance revision/time, update outcome/reason, consent/purge state, distinct `incidentState`/`incidentFence`, `revokeOutcome` (NONE/PENDING/BUSY/FAILED/COMMITTED/UNKNOWN), controlled-copy purge state and external-copy knowledge, and retained AC-08 measurements. Incident denial is reported as `UNAVAILABLE` with a safe uncertainty reason, never `REVOKED` until a corresponding authoritative mutation is known committed. These are proposed fields, not implemented endpoints. Public aliases MUST NOT expose private paths, denied filenames, sensitive digests or raw metadata. A generic existing `currentState` adapter MUST discriminate source kind/basis; it must never map SNAPSHOT_CURRENT to an unqualified live CURRENT. Vault reports retain their existing contract.

Missing integrity proof returns UNAVAILABLE/denied, not OUTDATED-as-usable. Superseded G is not served as CURRENT even if all bytes match. Historical SUCCESS and current effective validity remain separate facts. Later Phase 19 consumers remain unauthorized and will need their own protected consumption contract.

## 7. Multi-file and Obsidian closure semantics

**Recommended explicit policy: approved revision-vector consistency, not simultaneous original-file capture (D7).** This is a precise proposed replacement of live closure lifetime. Every member has a defensible independent intake interval; the owner approves one immutable manifest listing those revision IDs, original provenance, digests, fields, edge anchors/blocks and capture times. The application MUST NOT call it a transactionally consistent snapshot of all live originals at one time.

1. Owner-selected roots create candidates only. After custody permission, bounded safe inspection of captured root bytes discovers references recursively. Such inspection is an intake function, not consent to embed/OCR arbitrary children. Discover only explicitly allowed roots/scope, never a whole-directory crawl or remote URL fetch.
2. Resolve each included child to an independently acquired/approved S/R and exact anchor/block/region. Reuse an already selected authorized child R only by explicit manifest selection; it is not silently reread or refreshed. New or changed child bytes require that child's own capture and approval. Child classification is never inherited from parent.
3. Record canonical reference resolution from **captured** parent text to child identity/revision. New references discovered beyond the approved closure require explicit selection/approval; otherwise fail the dependent parent. Cycles, missing/ambiguous references, unsafe paths, depth/size excess or unprovable omission fail the affected parent, without leaking denied child names/content. No partial closure is labelled complete.
4. Capture files separately. An original may change after its member was sealed; that does not mutate the captured member. If a member changes **during** its capture, reject it. Concurrent edits between members do not establish or invalidate a nonexistent simultaneous-source claim; the exact version vector must be displayed/approved. A policy requiring simultaneous external closure capture would need another proposal and proof, not repeated polling.
5. Seal the entire finite manifest only when every included root/child has immutable representation, correct provenance/mapping and independent approval. Its approval CAS includes every member plus expected current selected revisions/epochs. At admission reserve the complete union atomically. Conflicting versions of a shared S in one batch are rejected, not duplicated or silently resolved.
6. Each published file/root has an independent G and its actual closure. An embedded child need not have a standalone G merely to authorize its included bytes, but it must have its own S/R/consent; if selected as an independent root, its G has an independent outcome. Failed child staging invalidates all roots relying on that child result; unrelated roots may publish only with valid isolation proof. Shared producer/fence failures publish none.
7. A root-only refresh does not automatically refresh shared children. Explicit child refresh promotes that child's new selected R only at C; all parents pinned to its older R become OUTDATED unless replacement parent generations binding the new R publish in that same C. No auto-reindex of other parents and no silent in-place substitution.
8. Root removal removes its selection/edges/generations and purges its exclusive bytes; independently approved shared children survive. Child revoke denies/purges all actual transitive parent derivatives, regardless of other roots' consent. Reference counts cannot preserve revoked child content. Unrelated sources and parents whose actual manifests exclude the child remain unaffected.

## 8. Consent, privacy, cancellation and revocation

### 8.1 Proposed raw custody, trusted inspection and final permissions — ISAR-1

**RAW_QUARANTINE_CUSTODY is NEW / PROPOSED, requiring explicit D10 approval and a named Phase 18 P17-2 applicability override.** It permits temporary opaque acquisition and strictly bounded trusted inspection of otherwise unapproved fields solely to classify/separate one individually owner-selected source within its finite intake intent. It does **not** reinterpret frozen P17-2 as already permitting those bytes. The grant binds exact I0 selection/root/object authority, S/intake ID, custody purpose, allowed inspection operations, authoritative finite expiry, byte/expansion/disk/time budgets and cancellation/cleanup owner. Unknown/missing limits deny; no numerical limit is selected here. No directory blanket grant, known-prohibited source, alternate source, child, arbitrary caller bytes or worker path inherits it.

Five permissions are distinct: **(1)** explicit owner raw acquisition/custody, **(2)** explicit bounded trusted inspection for classification/safe projection, **(3)** exact final owner consent to retain the field-safe sealed representation, **(4)** fresh reserved one-use transfer to the indexing worker, and **(5)** trusted verified publication at physical C. **Trusted inspection boundary:** only Java-owned capture and a narrowly reviewed, Java-controlled local intake-inspection adapter within the same active operation may read quarantine. It has no ordinary Python indexing-worker identity/grant, embedding/search/publication capability, business SQL, network, document execution or autonomous lifecycle. Java decides policy/eligibility; a parser can only return bounded typed observations and an exact scope/mapping candidate, never authorize itself. If an implementation uses a native parser/rendering component, its principal/handles/process/resources/temporary bytes must remain confined to that same trusted intake task and G3/G4 supervision; no separate engine/service is approved. Owner preview is a trusted intake-only, noncached authorized view of the selected material; no general download/report/debug endpoint may expose raw bytes or denied hidden fields. Classification preview of unresolved material requires that inspection permission and never establishes indexing eligibility.

### 8.2 Proposed restrictive-discovery incident fence — ISAR-2

**D5 proposes a NEW, narrow external-snapshot exception to ADR-0020 decision 2, P17-2/P17-3 busy-mutation rules and D18-A.2/.8.** It allows only trusted Java to record a source-scoped **deny-only incident/uncertainty fence while a snapshot source is reserved**. It does not change source classification, consent/reset, normal authorization epoch, revision selection or reservations, cannot grant/clear authority, cannot bypass normal revoke, and gives Python no mutation right. Vault-source rules remain frozen. This is neither approved nor implemented.

Classify scope explicitly: **case 1**, rejected/unapproved R2 alone with independently trustworthy R1 => candidate cleanup only, no automatic S/R1 suspension; **case 2**, validated credible uncertainty in S/R1/retained fields/classification/consent => fence that authority; **case 3**, implicated child => fence the child's authority and exact true dependent generations/attempts from their historical manifests, not unrelated siblings; **case 4**, ordinary extraction/OCR/resource failure => ordinary failure/fallback, no privacy incident. A malformed R2 property alone is not evidence that R1's authority is invalid. Missing/unprovable affected scope denies the bounded potentially affected closure until scope is resolved, never asserts unrelated sources safe.

**Durable boundary and ordering:** use the existing stable RAG snapshot source authority/guard slot, with a retained monotonic incident fence and safe incident scope/reason/disposition metadata, not a new global coordinator/table/queue. Fresh currentness/reads, admission, transfer and finalization must query this state for every actual root/child. Java records trusted validation plus ACTIVE/UNKNOWN uncertainty under the applicable source-first guards (graph where needed -> sorted Vault guard subset -> sorted snapshot source guards -> later policy/attempt/generation guards only if needed). Recording is a narrowly audited deny-only route permitted despite reservations; it does not release them or wait backwards. A completed attempt-only stop-request remains a separate TX before later source/process control. No hashing/parsing/process wait occurs under SQL row locks.

The exact global deny linearization point is **physical COMMIT C_D** of that guarded uncertainty state, not raw parser observation, an in-memory flag, log, stop request or failed transaction. The publishing transaction must hold the **same source authority guards through actual physical C_P**, reload incident state after waits and reject an active/changed incident fence. Thus C_D before C_P wins denial; if C_P holds the guards first, C_D cannot commit until C_P resolves, and that real historical publication precedes denial. A last SELECT without the retained guard is insufficient. Future reads after C_D always deny even if G remains historically PUBLISHED. No ability to retract bytes already lawfully delivered before C_D is claimed.

Inspection capable of adjudicating **already selected** authority must first durably record a scoped INSPECTION_UNRESOLVED fence under those same guards before that authority-sensitive inspection begins. It requires a concrete recorded source/field/child reason; merely inspecting an independent R2 candidate does not impose it on trustworthy R1. It is deny-only and makes a crash before final incident classification fail closed. On subsequent validation, keep ACTIVE uncertainty or resolve the candidate-only/false-positive case under the guarded resolution rule below. An unexpected candidate observation implicating existing authority is not allowed to return success or continue protected use from its originating operation before C_D is known. Between an observation and C_D other operations are ordered by actual guard/C; no instantaneous cross-process denial from volatile knowledge is claimed. Failed/unknown recording denies the originating operation, retains the durable unresolved inspection/operation obligation and requires recovery; if the necessary pre-inspection uncertainty/recovery proof cannot be provided, G4 remains unresolved and the inspection path MUST NOT be used.

## 9. Purge, retention and proof

Recommended minimal retention (D6): selected authorized R plus revisions genuinely required by current approved manifests or active attempts; no owner-visible historical-content archive, automatic historical rollback or cross-source content deduplication. During pending update, keep authorized R1 and one finite R2 attempt. After successful replacement, superseded content is denied and cleanup-required when no legitimate dependency needs it; after ordinary failure/cancel, discard R2. No arbitrary days/GB/count quota is selected here; approved measured capacity/cleanup limits are required before activation.

Revocation, privacy reset, manual RAG removal or explicit revision removal overrides ordinary retention. Removing a revision still used by a parent must invalidate that parent, never leave a dangling authorized reference. Source revoke targets all its revisions and actual transitive derivatives; root-specific removal alone does not revoke independently approved shared children. A new revision is never a way to inherit a revoked grant.

Delete failure/open writer/outage in that controlled scope is PURGE_PENDING and inaccessible. ### 9.2 Restore consequences and proposed D9 choice

- PG source/approval/chunk/vector rows restored **without matching verified sealed R/mapping bytes** are UNAVAILABLE/denied, never SNAPSHOT_CURRENT. Do not reread O, auto-recapture, auto-adopt a candidate or serve old chunks to repair missing storage. Owner must explicitly reimport/approve a new revision and manually index if needed.
- Old sealed files returning **without trustworthy current consent/reset/revocation/incident history** remain denied orphan/quarantine data. Byte/hash equality and an old backed-up approval cannot restore authority; suspend, reconcile against trustworthy history, otherwise require fresh owner intake/approval/manual reindex.
- Restoring PG history may lose a later revoke/incident even when files match. Declared restore suspends affected snapshot reads/admission/publication until operator reconciliation and renewed approval as required; unknown history fails closed. Required cleanup and anti-replay state are not rolled back into permission.
- B's proposed exclusions mean ordinary application archives do **not** promise complete historical snapshot recovery. Channel C may preserve SQL without files, while E may preserve files without reliable authority; neither is a consistent authorized snapshot backup.
- A future snapshot-aware backup/restore policy and any frozen portability change require a **separate explicit owner decision/scope**. D9 approves only the exact channel/default/qualified-reporting policy if later accepted, not backup implementation or automatic restore.

## 11. Minimal storage and operational lifecycle

Java `rag` owns local snapshot files and metadata. Use one explicitly configured private RAG-managed root outside source trees, web static roots, repository fixtures, shared TEMP and worker writable scratch. Physical entries use opaque S/R/attempt IDs with validated containment, not owner basenames or raw paths. Logical records remain in the existing RAG PostgreSQL schema; bytes remain outside PostgreSQL. No Media/S3/cloud ownership, new module dependency, service, distributed queue, global coordinator or synchronization daemon is proposed.

Managed subareas need only isolated RAW_QUARANTINE_CUSTODY capture/inspection, field-safe candidates/sealed revisions and bounded attempt scratch. Raw quarantine is excluded from eligible storage/worker input, expires under 8.1 and must be verifiably deleted before indexing eligibility. These are logical responsibilities, not prescribed extra services/tables. Storage setup must verify the root's identity/ACL/reparse properties and fail closed on replacement/unsupported volume. Java alone can create/seal/delete; Python receives exact bounded approved input over the existing transfer, not arbitrary store/source paths or a directory grant. The supervisor/process boundary must deny arbitrary worker filesystem reads as well as SQL reads; current same-user execution must not be assumed to provide this isolation automatically (G3).

Disk admission must account for existing retained snapshots, pending replacement, failed purge backlog, worker temp, archive/image expansion and final output space. Establish finite per-source/closure/job/storage growth and cleanup-work bounds from representative measurements and owner review; reserve/check capacity and fail safely on disk-full/low-headroom. Do not evict authorized selected content or expand a quota silently. Existing 100-source/1 MiB/15-minute Foundation path limits remain unchanged; candidate v3 constants are not accepted general workload limits.

Filesystem seal and PostgreSQL metadata are reconciled with explicit pending/known states, not a two-phase commit platform. Files first become immutable/verified, then a guarded DB record references them; an interrupted step leaves inaccessible temp/orphan/pending metadata. A DB row cannot assert SEALED_APPROVED if exact bytes/manifest/durability are unavailable. Final publication checks/pins the managed object, approval and immutable manifest so store replacement/deletion cannot race C. No file I/O/hash/process wait under SQL row guards; prepare outside and revalidate protected identity/versions under guards.

Normal restart preserves freshly provable selected snapshot authority/completed generations independently of prior worker boot/TTL **only after querying durable incident/unresolved-inspection fences**. Controller death before formal revoke C cannot clear incident denial or enable fallback. Expired/interrupted raw custody is cleanup-only, never auto-resumed; old capture-task/writer uncertainty retains exclusion. Interrupted indexing is discarded only after existing positive process/task/SQL proof; no auto-resume. Unknown C uses durable generation/selection/terminal/reservation evidence to determine what actually committed; absent/uncertain storage or outcomes deny and retain recovery obligations. Never assume rollback from a lost response, or auto-promote a sealed revision.

Declared DB/store restore, rolled-back metadata/incident history, missing sealed bytes/mappings or uncertain epochs suspends affected snapshot authority under section 9's channel-specific policy. PG chunks/approval rows alone cannot produce SNAPSHOT_CURRENT; no automatic original-file reread repairs them. Returned old files without trustworthy reset/revocation/incident history are denied, not adopted. Reconcile durable control history and exact files, preserve nonleaking tombstones, and require fresh owner approval/manual import/reindex where authority or content cannot be established. D9's managed-file exclusion sacrifices complete ordinary snapshot recovery; it does not exclude RAG SQL from whole-DB backup/WAL or control owner copies. Future snapshot-aware backup or portability changes need separate owner scope.

## 12. Producer, staging, finalizer and physical-C dependencies

**FR18-3 remains mandatory and separate.** A snapshot digest authenticates neither Python's actual output nor arbitrary staged claims. Java's present `expectedOutput = digest("DOCUMENT_V3:" + expectedInput)` and Python's count-based response do not bind exact output; runtime staging DML and self-reported chunk attribution are not fixed by changing the source model.

The later versioned document input/receipt/manifest must bind, for every root/child:

`sourceKind=RAG_SNAPSHOT, S, R, ordinal, resulting sourceVersion, source reset/global epoch, current expected incident fence/disposition, revision consent ID/epoch, field-policy version, exact retained/worker fields and regions, original provenance revision, stored/input digests and lengths, closure IDs/edges/anchors/digest, job/attempt/one-use grant, protocol discrimination, parser/OCR/chunker/model/tokenizer artifact identities`.

Exact output verification additionally binds ordered file outcomes, normalized elements, chunk text and excerpts, original/snapshot source spans and mapping revision, locators/table structure, exact finite vectors/dimension/model, warnings and necessary safe resource report. Canonical encoding must reject duplicate/unknown/ambiguous identity fields, defaults that invent approval, mixed protocol/grant kinds and wrong-field/source/revision attribution. Raw hashes cannot replace checks of what a locator/excerpt actually denotes.

Use the existing versioned v3 document family with an explicit snapshot discriminator/version negotiation; do not silently reinterpret an old 3.0 live/DOMAIN payload. Exact wire version is a later reviewed compatibility detail; no caller may use its absence to select “latest.” Preserve unchanged v2 Foundation and its original encoding/limits. No signing infrastructure is needed or proposed.

Before C: freshly validate section 8.2's incident/unresolved-inspection fence for the exact root/child scope under the same source guards held through physical C; C_D-first denies and C_P-first preserves historical outcome with subsequent read denial. This proposed D5 exception changes no normal source mutation/release authority. Prove actual bound launcher/sender/task/tree stop; drain prior SQL writers and seal immutable committed staged results under the attempt fence. Verify exact producer receipt against actual sealed rows, Java-prepared snapshot authority and mandatory locator oracle. Runtime-forged `worker_receipt=true`, an input-only digest, correct count/dimension or arbitrary source identity must fail. Validate expensive content/hashes outside row locks with a stable seal; under short source-first guards compare exactly that sealed revision/output proof and fresh authority.

Final TX preserves graph -> sorted Vault stable sources -> sorted RAG external/snapshot source slot -> Vault lifecycle -> owner projection -> RAG policies -> job/attempt -> generation/staging/run; applicable subsets only, canonical bytewise source ordering and existing NOWAIT backstops. No attempt-first wait for sources. Worker keeps attempt -> staging through S C; separate attempt-only stop-request finishes before source/process control.

The one final **physical PostgreSQL C** atomically installs all validated successful Gs, promotes only their intended root/child selections/versions, invalidates affected old active pointers, records every file outcome, terminalizes and releases the exact reserved union. Selection/generation changes dependent on a failed child cannot sneak into the success set. Shared trust/fence/cancel/SQL failure publishes none. Failed independent files leave their prior selected revisions unchanged if still authorized. File outcomes retain existing job-state mapping.

Known rollback installs no new selection/generation. Abort/release requires safe quiescence/fences. Genuinely unknown C retains nonterminal recovery/exclusivity until durable outcome is reconciled; no blind finalization replay. Managed snapshot bytes may survive controller death, but native protection, process stop and SQL outcome may not be assumed to survive. E1 permits timely validated late C only under all unchanged authority/snapshot protections. A TransactionTemplate callback/marker/ACK is not physical C.
