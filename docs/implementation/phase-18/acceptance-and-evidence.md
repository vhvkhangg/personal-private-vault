## Meaning of the remaining security and storage guarantees

- **Trusted application code, untrusted document content/results.** The worker is the user's own Python process; Windows does not restrict it to approved paths. Do not claim otherwise. SQL least privilege (`rag_worker`) and Java trusted finalization **remain mandatory**, and actual produced chunks/excerpts/locators/vectors must be validated; hash-of-input alone cannot close FR18-3.
- **Application immutability is conditional.** Unique temp capture → checksum/length → no-overwrite sealed ORIGINAL_BYTES R/manifest → integrity check before use. A malicious same-user process can edit after verification and before use; this is accepted, not an ignored violation. Ordinary detected mismatch fails closed. SQL and filesystem are not atomically committed; reconcile after crashes and keep incomplete revisions/indexes invisible.
- **Whole-file authority is never implied by a checksum or file path alone.** Independent child approvals, guarded selected revision, source-first lock ordering, revoke/incident/read denial, actual closure and NO_CHANGE prerequisites remain. In-file Private/NSFW markers are authorized data, not a separate privacy veto for the approved file; Vault field privacy remains frozen.
- **Do not implement new security machinery merely to satisfy an old receipt.** Preserve working protections that do not interfere with the revised contract; prioritize bugs, file content fidelity, recovery and publication semantics. CP18-AB-2 old OS isolation requirement is superseded prospectively, not retroactively proved. Other CP/FR findings must be individually reclassified with code evidence.
