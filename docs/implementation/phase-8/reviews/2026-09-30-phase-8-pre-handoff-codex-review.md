2. **Medium — parent facade type boundary is underspecified.** `docs/implementation/phase-8/README.md` (Parent Knowledge facade and Proposed package direction) requires top-level `feed`, `importdata`, and `search` callers to use the parent facade, but says it should return “public views/commands” without requiring those method signatures to use parent-owned API types. In Spring Modulith's [nested-module access model](https://docs.spring.io/spring-modulith/reference/fundamentals.html#_nested_application_modules), nested types are available to the parent and exposed sibling modules, not arbitrary top-level modules. If parent methods expose `knowledge.study.*`, `knowledge.note.*`, etc. command/view types to future top-level callers, the facade is not a usable closed-module boundary and architecture verification can fail. State that externally consumable facade signatures must use types exposed by `knowledge` itself (with deliberate, small mapping/delegation), while nested public contracts remain parent/sibling-facing. Add a handoff test expectation that a representative external module can consume only the parent API without referencing a nested package. Do not make `knowledge` open or duplicate nested validation/persistence to solve this.
3. **Medium — “due Vocabulary items” has no query semantics.** `docs/implementation/phase-8/README.md:261` promises a bounded due-item read ordered by `next_review_at` and ID, but `next_review_at` is nullable and new items default to `NEW` with null review time in Schema v1. The preparation never says whether these new items are due, whether other null-time states qualify, or whether the cutoff is inclusive. Implementers could return incompatible result sets and tests could bless either behavior. Define the due predicate, treatment/order of null-time `NEW` items, cutoff semantics, and deterministic tie-break before handoff; retain a bounded read without choosing an automatic SRS scheduling algorithm.
