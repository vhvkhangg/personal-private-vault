## Exact *prospective* minimal persistence/guard delta (only if current primitives cannot prove it)

This is an **Owner-approved prospective design boundary**, not an existing schema/API, an applied migration or permission to implement. The exact migration, guard integration and runtime lifetime remain subject to Codex feasibility/pre-handoff review and a separately authorized executable slice. A single RAG-owned durable Q&A reader record is sufficient; avoid a generic query job engine. Its minimum logical fields are `reader_id` (opaque UUID), `reservation_token`, state (`ADMITTED`, `CONSUMING`, `STOP_REQUESTED`, `EMITTING`, `RECOVERY_REQUIRED`, `TERMINAL`), immutable digest-bound list of **all** root/child source IDs and selected revision + source version/epoch/reset + generation IDs, owned local process/request identity or verified-context-disposal evidence, and last transition/emission status. Include bounded creation/update times for diagnosis **without** treating a deadline as authority to release. No question/answer/snippet/raw path is persisted.

Admission `C_A` must guard exactly those source IDs/children and atomically record this reader plus incompatible-mutation exclusion; mutation SQL/Java owners consult the same guarded reader/source-reservation state and return the existing no-change `409 BUSY` for a normal conflicting mutation. Terminal release `C_RL` requires verified context/worker and HTTP sender quiescence *after* `C_E`, then atomically closes the reader/exclusion. Incident denial and crash/unknown-C reconciliation must not delete unproven readers; failed stop leaves `RECOVERY_REQUIRED` and blocked reads/mutations until verified repair. Prefer reusing `RagExternalFileAuthority` source-reservation functions only after checking their exact tokens, exclusivity and recovery; otherwise authorize the smallest new RAG reader registry/guard integration via a **new additive migration after the actual last applied migration**, never rewriting frozen applied files. No writes to `vault`, Fiction, Film, history or unrelated schemas beyond the narrow guard necessary for this existing cross-source mutation boundary.

Before implementation, Codex must identify exact affected guarded SQL functions, Java owner mutations, table/migration and runtime lifecycle in the executable handoff; any wider change returns to Owner. The Owner approves **only** this precise logical state/guard delta, not arbitrary DB rearchitecture.

## Owner decision — APPROVED / option A

**Owner choice (2026-10-27):** The Owner explicitly approves **option A** as the prospective *design boundary*: one durable, source/dependency-scoped active Q&A reader under short authoritative guards, exclusion lasting through actual non-streamed HTTP emission and verified quiescence; conflicting normal revoke/edit/update may return `409 BUSY` without mutation, followed by manual cancel-first/retry if needed. Reuse accepted source-reservation/mutation guards wherever independently proven correct; **only the minimum additive reader record/SQL guarding** is approved at design level if direct reuse cannot provide durable, crash-recoverable exclusion. No long SQL locks, ephemeral/TTL-only release, automatic queue, new general-purpose job engine, or implicit reapproval of frozen Phase 17/18 code.

**Authorization boundary:** This is a *prospective design decision*, **not** permission to execute source/migration changes, activate indexing/Q&A, create an implementation handoff immediately, or declare P19-PR-01 closed. Codex must inspect actual guarded source owners, DB/HTTP sender lifecycle, viable minimal migrations/SQL and R01–R10 before determining `READY_FOR_HANDOFF`; source work requires a separately Owner-approved executable slice after reviewed preparation is published. If actual code demands a **wider** architectural/schema/security delta than this smallest design, return the precise uncovered delta for a new Owner decision rather than silently expanding scope. A demonstrably equivalent no-migration solution is acceptable for independent review without a new technology choice.

## P19-PR-01 prospective incident-handoff clarification (not a new Owner choice)

The independent [re-review 1](reviews/2026-10-27-phase-19-independent-pre-handoff-re-review-1.md) accepted Option A but found the `EMITTING`-first case unfinished. Within Option A's already approved **minimal durable reader/guard** boundary, the [consumer contract](query-consumer-lifetime-and-selection.md#durable-incident-handoff-at-emission-p19-pr-01) now specifies: trusted Java persists a bounded pending-incident/inspection obligation (`C_I`) under the source guards **before the reader's exclusion can release**; fresh admission is denied from that COMMIT even if physical authoritative denial `C_D` must wait for existing HTTP emission and quiescence. The trusted finisher then commits real `C_D` **atomically with** `C_RL`, or preserves a durable deny barrier if two guarded commits are proven equivalent. Unknown intent/denial/finish outcomes retain reader and incident recovery; no release-before-denial and no reliance on `reserved_by IS NULL` updates affecting zero rows. A normal conflicting Owner mutation still returns `409 BUSY` without committing its requested change.

This text **documents the already selected Option A** rather than issuing new authorization, adding a second incident platform or self-closing P19-PR-01. Actual SQL/Java/HTTP mechanism feasibility and finite real-race evidence remain independently gated. If Codex finds this cannot be satisfied with the approved minimal state/guard delta without weakening existing ADR-0022 semantics, return the precise wider requirement for a separate Owner decision.
