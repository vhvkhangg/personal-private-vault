### FR17-5 — High: issued scope becomes stale before the worker's later gate

Evidence: `RagJobService.java:120` calls transactional `grants.issue(...)` at **122**, then `engineClient.triggerWorkerStage(grant)` at **123** after the issuance transaction releases the Vault/source guards. `RagWorkerGrantService.java:26` freshly verifies authority inside issuance, but the later V12 `verify_worker_grant` reads **RAG policy snapshots**, not current owning-domain NSFW/trash/content. Owning mutations acquire the common Vault guard but do not fence this already-issued attempt before Python's subsequent verification/computation/staging. `worker.py:15` accepts that stale authority and `:27` commits its receipt.

Deterministic reproduction, using fabricated content:

1. Approve Fiction title/description, admit and issue its real grant.
2. Commit `FictionOperations.update(... isNsfw=true ...)` using the genuine guarded owner API.
3. Dispatch to the real Python service using that grant and actual `rag_worker` PostgreSQL connection.
4. Observe `NSFW_AFTER_ISSUANCE_ACTUAL_PYTHON_STAGED=true`, one `worker_receipt` row, and later Java final publication denial.
5. Repeat through **`RagOperations.executeSyntheticStage` itself**, with an audit-only outer interceptor pausing after the real issuance transaction commits and applying the owner update before returning to dispatch. Observe **`CANONICAL_EXECUTION_NSFW_AFTER_GRANT_RECEIPTS=1`**. No grant, function, result or source proof was mocked or forged. The later Java receipt-validation transaction throws, after Python has already consumed the content and committed the row.

This is a later worker gate accepting stale live-domain authority. It is not a demand to retract bytes already delivered before a subsequent change: the owner mutation commits **before** Python's grant verification, synthetic computation and staging COMMIT. P17-2 §1 and P17-3 §1/§3 require current two-authority checks at these security boundaries; final activation denial cannot undo worker consumption. The prior “NSFW before execute” test mutates before `issue` and misses this interval.

**Required correction:** make worker consumption/staging depend on an enforceable current owning-domain proof, or an equivalent source-mutation invalidation fence sharing the approved source/attempt authority protocol. Merely checking again immediately before HTTP leaves another interval. Preserve the prohibition on Python/business-table SQL, reverse owner→RAG dependencies and network/model work under source DB locks. If a proposed repair needs a new frozen-boundary decision, report that specific conflict rather than weakening the contract. Until proven, the affected execution capability must fail closed.

**Required regression:** deterministic actual public execution barrier after issuance COMMIT, before worker authorization; genuine Fiction/Film NSFW, trash, revision and transitive-child changes in both orders; no unauthorized worker computation/receipt, no stale publication, and no regression in revocation/purge or caller transaction composition. Use the failed probe as the starting counterexample, not an assertion that finalization alone denies.
